# 评测（golden set）

验证的不是「代码逻辑对不对」，而是「回答好不好」。两件事必须分开：

| | 单测（`tests/`） | 判定器单测（`evals/judge.test.ts`） | 评测（`evals/golden.jsonl`） |
|---|---|---|---|
| 命令 | `npm run test` | `npm run eval` 的一部分 | `npm run eval` |
| 测什么 | 纯函数逻辑 | 判定规则会不会误判/漏判 | 检索 → 拼资料 → 生成的最终答案 |
| 依赖 | 无网络、无模型、确定性 | 无网络、无模型、确定性 | 真库、真 embedding、真模型 |
| 耗时 | ~3 秒 | ~0.3 秒 | ~4 分钟（56 条，平均 4.1s/条） |
| 进不进 `npm run check` | 进 | 不进（跟随 eval） | **不进**（结果有波动，不能卡门禁） |

## 怎么跑

```bash
npm run eval            # 基线：相关度闸门开启
npm run eval:nogate     # 对照实验：关掉闸门，其它完全一样
npm run eval:diff       # 对比 reports/ 里最近两份报告，看谁回归、谁修复
npm run eval:trend      # 生成趋势页 reports/trend.html + 终端摘要
npm run eval:nightly    # 夜间任务：跑评测 → 更新趋势 → 判回归 → 清过期报告
```

跑完控制台打印汇总，同时在 `evals/reports/<时间戳>.md` 生成报告（同目录还有 `.json`，供 `eval:diff` 与脚本比对）。

**跑之前确认两件事**：数据库里有知识库数据；管理后台至少有一个可用的 chat 模型。环境变量从 `.env.local` 自动装载（`evals/setup-env.ts`），不需要手工 export。

## 趋势、回归判定与夜间跑

三个命令分工不同，别混用：

| 命令 | 回答的问题 | 读什么 |
|---|---|---|
| `eval` | 现在多少分 | 控制台 + 单份报告 |
| `eval:diff` | 这次改动让**哪几条**变了 | 最近两份报告逐条比 |
| `eval:trend` | 最近 N 次**整体**往哪走 | 全部报告压成时间线 |

`eval:trend` 生成 `evals/reports/trend.html`（自包含，无外网依赖，直接浏览器打开），画四张图：

1. **总通过率** —— 闸门开为实线、关为虚线，两种配置不混在一条线上；
2. **应答对 vs 应拒答** —— 分开看才能定位：两者一起掉是检索/解析坏了，只有应拒答掉是模型开始编，只有应答对掉是资料进得去但没读对；
3. **平均命中片数** —— 这是**领先指标**。切片变碎、闸门失效、向量降级时，准确率往往还不掉，先动的是它；
4. **平均耗时** —— 能发现「重试了一次空回答」这类抖动。

外加一张「历史不稳定用例」表（按失败次数排序）。它比通过率更能指导行动：**稳定失败的是缺陷，间歇失败的多半是判定器或上游抖动**，两者修法不同。

### 夜间自动跑

```powershell
npm run eval:nightly
```

想每天自动跑，注册一个计划任务（管理员 PowerShell；机器须不休眠、数据库在跑）：

```powershell
$a = New-ScheduledTaskAction -Execute 'powershell.exe' `
     -Argument '-NoProfile -ExecutionPolicy Bypass -File "D:\Python WorkSpace\ai-agent-platform\scripts\nightly-eval.ps1"'
$t = New-ScheduledTaskTrigger -Daily -At 2:00am
Register-ScheduledTask -TaskName 'ai-agent-platform 夜间评测' -Action $a -Trigger $t
```

脚本参数：`-SkipEval`（只重画趋势）、`-KeepDays 14`（报告保留天数）、`-WhatIfClean`（只列出待清理文件）。退出码：`0` 正常 / `2` 疑似回归 / `3` 配置缺失 / `4` 评测进程异常 / `5` 趋势脚本异常。

**回归判定不写死分数**：模型有 ±1~2 条抖动，写死「低于 50 条就报警」会天天误报。所以比的是**同配置的上一次**，且要同时满足才报警：

- 通过数掉 **≥2 条**，或
- 平均命中片数涨 **≥0.8 片**（领先指标先恶化）

报警时写 `evals/reports/ALERT.md`（一进项目就能看见），恢复正常后自动删除——**过期的告警比没有告警更浪费时间**。

### 这一步踩的三个坑

| 坑 | 现象 | 修法 |
|---|---|---|
| **退出码不等于质量** | `eval.test.ts` 只 `console.log` 不 `assert`，56 条挂 3 条照样 `exit 0` | 夜间脚本不信退出码，只在进程异常时报 `exit 4`；质量判定交给 `trend --check` 读报告 JSON |
| **`Tee-Object` 默认写 UTF-16** | 和 `Add-Content -Encoding UTF8` 混写同一个日志 → 日志乱码，控制台还夹杂 `\r` 造成的杂字符 | 一律用 `Invoke-Logged { & cmd }` 逐行 `Add-Content`，并清掉 `\r` |
| **PS 5.1 按本地代码页解析脚本** | 无 BOM 的 UTF-8 脚本里中文全变乱码，严重时语法报错 | `.ps1` 必须存成 **UTF-8 with BOM**（`scripts/nightly-eval.ps1` 已带 BOM，改动后要复查） |

> 另外：`evals/reports/trend.html`、`ALERT.md`、`nightly-*.log` 已进 `.gitignore`（脚本可重新生成）；报告本身的 `.json/.md` 仍入库，那是可追溯的历史。**删报告等于删历史，趋势会断。**

## 当前基线（2026-10-29 最终轮，56 条）

| 指标 | 闸门开 | 闸门关 |
|---|---|---|
| 总通过 | **56/56（100%）** | 55/56（98%） |
| 应答对（answer） | 30/30 | 29/30 |
| 应拒答（abstain） | 26/26 | 26/26 |
| 检索命中 | 30/30 | 30/30 |
| 平均命中片数 | **3.41** | 5.43 |
| 平均耗时 | 4.1s | 4.0s |

**满分是个危险信号**，所以每轮都得重新归因：这批用例已经「被治好了」——2 条碎片化失败随分块修复消失，5 条「编造/答错」经查是用例本身写错（见下节），其余是判定器误伤。**满分说明的是「已知问题不复发」，不是「系统没有未知问题」**。

所以这一轮特意加了 4 条更难的（第 53~56 条），专门打「同一个知识库、但要动脑子」的位置：

| 用例 | 类型 | 考什么 | 结果 |
|---|---|---|---|
| `ans-28` 温度与功耗的单位 | 单位区分 | 别把单位一律当 ℃：功耗是 A，差 1000 倍 | 通过（花费了 2 轮才修好判定，见下） |
| `ans-29` 日均接口独有的温度字段 | 跨表比对 | 要同时读两张字段表，找出 `temp_8h`；只看一张会答成 `temp_ehi` | 闸门开通过、**闸门关失败** |
| `ans-30` dataType 取 0 与 5 | 参数表 | 键值对表的读法 | 通过 |
| `abs-30` 1 月 1—4 日逐日 EHI | 干扰抵挡 | 资料只有「轻度异常 4 天」和**未来** 7 天预报，不能把预报数字当历史 | 通过 |

`ans-29` 在两种配置下不一致，是这次最有信息量的一个数据点：**闸门不只是「少注入几片」，它挡掉的是会把人带偏的干扰片段**。关掉闸门后模型看到 5~6 片、被 `temp_ehi` 吸引，答案就错了。

同配置重跑的抖动仍在 ±1~2 条，所以：

- 别拿单次总数下结论，`100%` 与 `98%` 之间的差没有意义；
- 要看趋势就看 `eval:diff` 的「回归 / 修复」清单，那两项才是有信息的信号。

## 本轮被推翻的用例（它们本身就是错的）

评测最有价值的产出不是分数，是**发现用例写错了**。下面几条都曾被我写成「系统缺陷」：

| 用例 | 原判定 | 真相 |
|---|---|---|
| `abs-16` 甲区同期的电流 | 应拒答，模型答 22 就是编造 | 周报**表1 有 20 余个分区的读数**，甲区电流就是 22。改成 `answer` |
| `abs-12` 丙区同期的达标天数率 | 应拒答 | 资料里确有「丙区中度异常 1 天、全园 7 天」，模型据此推 6/7≈85.7% 是**正确的算术**，不是编造。判据放行 54.8 与 85.7，只抓其它凭空出现的百分数（这条反复了两次：先只抓「丙区 + 数字」，再改成「除 54.8 外都算错」，最后才承认推算结果也对） |
| `abs-26` 11 日的 EHI | 应拒答，答 65~95 是编造 | 周报末尾**「表 示例新区未来 7 天运行状态预报」给了 7 天的 EHI 区间**，1/11 正是 65-95。改成 `answer` |
| `abs-27` 这一周每天的 EHI | 应拒答 | 同上，7 天全在表里。改成 `answer`（要求首尾两个区间都对，防止错行） |
| `abs-12` 的孪生问题：`ans-13`/`ans-14` | 只认正文那一套值 | 正文与表1 同一指标有两套值（docx 合并单元格错位），只能写成「两者皆可」 |

根因是同一件事：**旧数据碎片化把表格切成了几百个碎片，模型「找不到」被误读成「资料里没有」**。数据修好之后，两个「编造」用例直接变成了「答对」。

## 闸门的真实作用（第三次修正结论）

- **对最终准确率：基本无影响。** 56 条里只差 1 条（`ans-29`，关闸门时被 `temp_ehi` 带偏）。
- **对注入质量：影响很大。** 6 条召回被完全清空，30 条被削减（20 条不变、**0 条变多**），平均命中片数 **5.43 → 3.41（-37%）**。
- **对难题的影响是「看不见的」**：`ans-29` 的差别不在注入条数（两边都是 5~6 片），而在**注入了哪几片**。这也是为什么「命中片数」只能当预警指标，不能当质量指标。

为什么准确率没差别？因为**模型本身有拒绝能力**——塞给它 6 条无关片段，它也能说「资料里没有」。闸门仍然值得留：回答里不会挂一串无关来源、少注入 token、被带偏的概率更低（最后一条是推断，未实测）。

## 本轮修掉的四个真 bug（都由评测挖出来）

### 1. 切片碎片化：711 片里 613 片不到 20 字

docx 的「一个视觉行 = 一个 `w:p`」被 mammoth 还原成「空行分隔的段落」，旧 `splitText` 一段一片 → 目录行（`1.2 获取接口验证Token 3`）也独立成片。这类碎片向量语义近乎为零，但**词面命中率极高**（问题里的词就在标题里），把含答案的长片段挤出 top-k。

修法：先把短段落贪心合并到接近 `size`，再切。实测 **711 片 → 6 片（4193 字，平均 765 字），<20 字的碎片清零**，`ans-19`/`ans-21` 随之通过。

### 2. `joinChunks` 会静默复制原文（重建切片的迁移脚本踩的）

原文没有落库，重建切片只能从现有切片反推。第一版用 `contents[i-1].slice(-overlap)` 取重叠，**当旧片本身短于 overlap 时**（碎片数据全是几字一片），拿到的是「上一片全文 + 更早一片的尾巴」，前缀不匹配 → 重叠剥不掉 → 一整轮迁移下来原文每行都变成了两行。第一轮迁完库里是 19 片、切片总字数接近原文两倍，就是这个 bug 的表象。

教训：**用「上一片的原始输入」去反推「这一片的前缀」是错的，必须用还原出来的结果迭代**。已补单测 `切片短于重叠长度时，也不会把原文复制一遍` —— 之前那条测试用的是 800 字长片，恰好绕过了这个 bug。

还有一个更贵的教训：**修好代码不会修好数据**。坏数据已经在库里，重跑 `rechunk` 只会忠实地把重复文本再切一遍；而且实际重复形态是 **3~5 行一组整块重复**，「折叠相邻重复单行」的清洗脚本命中不到。最后按「1~10 行任意长度的相邻重复块，反复删除」清干净，两篇文档回落到 **6 + 5 = 11 片**，复核项是「残留重复块 = 0」+「十个关键事实一个不少」——只验前者容易把内容删掉。

### 3. `lexicalScore` 没有上界，闸门阈值形同虚设

融合分是 `0.75×向量 + 0.25×词法`，而词法分是「查询词在片段里的**平均出现次数**」——词重复 13 次就是 13 分，融合分能到 **3.37**。于是 `score >= 0.62` 这道闸门对任何反复出现关键词的片段都无条件放行。

修法：`raw / (raw + 1)` 饱和，值域 `[0,1)`，单调性保留。评分口径统一之后，阈值才有意义。

### 4. 小数点被当成句末，正文里多了「把数字劈开」的换行

分块第一步按句切，正则写的是 `(?<=[。.！？；\n])`——**ASCII 的 `.` 也当句末**。于是 `T2.5`、`0.6`、`3.48`、版本号 `1.3.1` 全被切断；而第二步把切出来的单元又用 `\n` 拼回，断行就固化进正文：

```
0.6      → "0." | "6"        → 正文 "0.\n6"
T2.5 读数 → "T2." | "5 读数" → 正文 "T2.\n5 读数"
```

实测一篇 3354 字的周报里有 **108 处**。这份材料通篇是监测读数，几乎每个数都带小数——模型看到 `0.\n6` 是 0 还是 6？

修法：中文标点（。！？；）与换行无条件断，**ASCII 的 `. ! ?` 必须后接空白或文末才断**；存量数据用「上一行以数字+`.` 结尾、下一行以数字开头 → 合并」清洗后重切重建；补单测断言 `/\d\.\n\d/` 不出现。这次修完，`rechunk` 也变成幂等的（连跑两轮 3354 → 3354）。

## 怎么加用例

`golden.jsonl` 一行一条：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | `ans-xx` / `abs-xx`，报告里按它定位 |
| `type` | ✅ | `answer`（该答对）或 `abstain`（该说不知道） |
| `q` | ✅ | 问题。**要给全时间、地点等限定词**——评测是单轮无上下文，`这段时间` 这种指代会直接检索不到 |
| `must_contain` | answer 必填 | 二维数组：外层 AND、内层 OR。`[["64.1"]]` = 必须出现 64.1；`[["Authorization"],["X-Api-Key"]]` = 两个都要 |
| `forbidden` | abstain 可选 | 正则数组，命中即判编造。**只写「带单位的数据断言」**，见下节第 2 条 |
| `source` | answer 可选 | 期望命中的文档名片段，用于单独衡量检索质量 |
| `note` | 可选 | 这条用例的依据，方便后人核对 |

**加用例前先确认知识库里真的没有（或有）这个信息**。本轮 4 条错用例全是「以为资料里没有」。查法：直接按关键词扫 `chunks` 表，别靠印象。

## 判定器设计（`evals/judge.ts`，24 条回归测试）

`abstain` 类判定的顺序是：

1. **先看有没有编造**（`forbidden` 命中 `assertiveText`）；
2. 再看有没有表态（`ABSTAIN_PATTERNS`）；
3. 都没命中，用**结构性兜底**：全段没有具体数值 + 出现「无法/没有/查不到」这类词 → 认定已表态。

三个结构性设计，都是被真实误判逼出来的：

| 机制 | 解决什么 |
|---|---|
| `stripMarkdown()` | 模型写 `EHI：**100–130**`，`**` 会把正则挡住造成漏判 |
| `assertiveText()` | 正则 `[^。]{0,25}` 会**跨过否定句**：模型说「未提供上一周数据（引用的 54.8% 不能用于本区）」，正则却从「乙区」一路抓到 54.8% 判它编造 |
| `hasConcreteNumber()` | 剥掉日期/异常项名/章节号/序号后还剩数字，才算「给了具体值」。词表补了四轮还在漏（「无法**查到**」「未**接入**」「无法**直接**给出」），只好加一条不依赖措辞的判据 |

**代价写在注释里**：真有编造但整段不含数字（如「年终奖一般在春节前发」）会漏判；报告保留了原始回答，可以人工复核。方向是刻意选的——**误判会被写成错误的复盘结论，比漏判更贵**。

## 踩过的坑（比通过率值钱）

### 1. 判定词表永远不全，而且会与 prompt 互相打架

词表补过四轮：「无法核实」「未配置该数据源」「未取得」「未载明」「无法查到」「未接入」「无法直接给出」全是模型真实说法，每次都让通过率虚低一截。更隐蔽的一轮：刚在 `route.ts` 的作答要求里教模型说「**未取得**」，转头词表里没有——模型照着 prompt 正确回答，判定器判它不合格。

**结论：prompt 措辞与判定词表必须同步维护；词表这条路有天花板，所以加了结构性兜底。**

### 2. 正则误伤比漏判危险，因为它会被当成系统缺陷

`forbidden` 最初写成「时间词 + 附近任意数字」（`2030[^。]{0,20}\d+`），于是「未找到 2030 年 **T2.5** 探头目标」命中 `2.5`、「未找到丙区（**2024**年…）」命中括号里的年份。第一轮 6 条失败里 4 条是这种误伤，其中一条还被写成了「`abs-09` 是活教材，模型拿 2025 年数据充数」——**模型一直答对了**。

**规则：编造的「数据」必须带单位（`℃`/`A`/`%`/`次`）或带明确标记（`EHI：100`）。**

第三轮又踩了一次同类：`abs-24` 问「示例新区 GDP 排名第几」，模型正确拒答，并补了一句「现有资料仅显示设备综合指数在全园排名第 11 位，**与 GDP 排名无关**」。`第 N 位[^。]{0,10}GDP` 跨过逗号抓到这句澄清，判成「编造 GDP 名次」。

修法分两层：① 正则的跨度里排除逗号（`[^。，]`），让「第 11 位，与 GDP」不再连成一串；② 判定器把「无关 / 不能等同 / 并非同一」也算否定分句——**澄清句在语义上就是「这不是同一回事」，它能保护回答，不该被当成断言**。

### 3. 同一份周报里有两套互相矛盾的值

同一份周报里，正文写「示例新区温度 64.1、电压 80、电流 35.6」，表1 同一行却是「51、210、24」——**两套值互相矛盾**，且按表1 算出的排名与正文的「第 11 位」对不上。

原来以为是「合并单元格让表头与数据行错位」，表格按行列还原后（见下）**行不再错位，两套值依然并存**，说明是统计口径不同，不是抽取 bug。

影响：**任何「某区某指标精确值」的问题，答案都不可控**。`ans-05/06/13/14` 的 `must_contain` 都写成「两者皆可」，并在 `note` 里注明。真实业务数据里这种冲突很常见，值得当数据质量问题处理，而不是模型问题。

### 4. `maxTokens` 给小了会得到空回答

思考型模型先花 token 在 reasoning 上，`maxTokens: 700` 时出现过两次「正文为空」。这是**执行异常**，判定器单独归类，避免混进「没表态」掩盖真实故障。

额度是分两轮加上去的：700 → 2000 → **4000**。加到 4000 的直接原因是新增的 `ans-28`（问单位）连跑三轮里两轮返回空文本，耗时 30s、命中 6 片——**它在思考，只是没额度把答案写出来**。同时把「空回答重试 1 次」改成「再试 2 次」：单次抖动不该把整轮基线拉低一条，而连空两次的概率要低得多。

### 5. 表格摊平成一格一行，模型只能数格子

`mammoth.extractRawText` 把 docx 表格还原成「一个单元格一行」，20 余个分区 × 8 列变成 176 行裸数字——列对齐全靠模型数格子，合并单元格一出现就整体串列。改成走 `convertToHtml` + `htmlTablesToText()`：两列表输出「标签：值」，三列以上输出 `区域: 甲区；电流: 22` 并每 15 行重插表头。

**副作用要一起改**：表1 变得可读之后，模型更倾向引用表1 的值，`ans-06` 从答「94.1」变成答「39」——这不是退化，是同一个数据冲突的另一面，用例随之放宽成「两者皆可」。

### 6. 教模型一句话，就要检查判定器能不能认

`route.ts` 里加「资料缺失时直接说明『知识库中没有该信息』」，模型照做了，4 条 abstain 用例却齐刷刷判成「没表态」——因为词表里 `没有[^。]{0,10}(数据…)` 的跨度只有 10，而模型写的是「知识库中没有『2024 年上半年示例新区达标天数率』的数据」，对象名本身就有二十几个字。

**光加词不够，还要量跨度**；判定器要按「模型实际会怎么写」调，不是按「我以为它会写什么」。三条真实样本已进 `judge.test.ts`。

### 7. 看着一样的字，码位可能不同

`ans-28` 问「温度和功耗的单位相同吗」，模型答「温度：64.1 ℃；功耗：1 A」，还额外指出原文单位标注不一致——**答得比预期还好**，却被判「缺少关键事实 ℃｜℃」。

原因是 `℃` 的 `³` 是上标字符（U+00B3），而用例里写的是普通 `3`；`µ`（U+00B5 MICRO SIGN）和 `μ`（U+03BC 希腊字母）肉眼也完全一样。同理 `振动` 与 `振动`。

这类问题最费时间的地方在于：**回答看上去完美，你不知道该怀疑什么**。所以判定器在比较前统一归一化（上下标数字、`µ→μ`、全角斜杠与空格），而不是往每条用例里堆变体——变体堆不完，下一个上标还会漏。

### 8. `forbidden` 传成 `undefined` 会让所有回答被判成编造

`new RegExp(undefined)` 不是「不匹配任何东西」，而是**空模式**（等价 `new RegExp()`），匹配一切。写测试时把正则字符串传给只接受 `RegExp` 的辅助函数，`.source` 取到 `undefined`，整条用例毫无理由地红了。

判定器现在会跳过非字符串项，并有一条单测锁住这个行为。教训：**「看起来会失配」的默认行为，恰恰可能是「匹配一切」**，这类 API 的边界要实测，别凭直觉。

### 9. 用例失败时先怀疑用例

本轮 4 条「系统缺陷」最后全是用例写错。**先查知识库里到底有没有这个信息，再怀疑系统。**

## 边界（别过度解读）

- 只覆盖「检索 → 拼资料 → 生成」，**不含**路由层的用户信息、长期记忆、配额提示，也不测工具调用与多轮；
- 判定靠关键词与正则，不判「答得自不自然」；
- 模型有随机性，单次通过率 ±1~2 条，**比较两次改动看 `eval:diff` 的回归/修复清单，不看总分**；
- 56 条不足以支撑统计结论，它只保证「主要路径没坏 + 已知坑不复发」。

## 下一步（按性价比排序）

1. **加更难的用例**：跨表联查（「温度比青白江低的区里，综合指数最好的是哪个」）、多跳（「排名第 11 的那个区，它的电压排第几」）、换年份/换分区的相似问。当前用例已经被治到满分，继续在现有难度上加没有信息量。
2. **修表格抽取的列对齐**（`lib/ai/extract.ts`）：合并单元格导致的列错位是这一轮发现的最大数据缺陷，也是「同一指标两套值」的根源。
3. **接夜间任务**：每天跑一次 `npm run eval`，把通过率画曲线。改动 prompt 或检索参数后，通过率掉了能立刻看到。
4. **加第二意见**：规则判完，对 `answer` 类再让一个更强模型判「回答是否被资料支持」，两者不一致的进人工复核队列。先规则后模型，不要一上来全靠模型判。
