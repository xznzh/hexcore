## 二、问题清单（按价值/风险排序）

### P0 · 安全与正确性（建议本周修）

| # | 问题 | 证据 | 影响 | 修法 | 成本 |
|---|---|---|---|---|---|
| **P0-1** | **禁用/降级用户的会话在 7 天内仍然有效** | `lib/auth.ts:68` `getSession()` 只做 `jwt.verify`，**不查库、不校验 `users.status`**；`app/api/auth/login/route.ts:27` 只在登录时检查 `disabled` | 管理员禁用某人后，对方刷新页面照常用；把 admin 降为 member，对方**仍持管理员权限直到 token 过期**（7 天）。JWT 无黑名单、无 tokenVersion | ① `users` 加 `token_version`，签发时写入，`getSession` 比对；或 ② `getSession` 内按 userId 查 status（带 60s 进程内缓存，避免每请求一次 DB） | 半天（方案②）～1 天（方案①，语义更干净） |
| **P0-2** | **文件路径校验是「字符串前缀」比较，可被绕过** | `lib/storage.ts:13` `if (!abs.startsWith(DATA_DIR)) throw` | `DATA_DIR=…/data/files` 时，`…/data/files-evil/x` 也满足 `startsWith`。当前文件名经 `safeName` 过滤（`/`、`\` 被替换）所以**暂无实际利用路径**，但 `resolveSafe` 还被 `f.path`（库内值）调用，一旦有其他写入口就是任意文件读写 | 改 `path.relative(DATA_DIR, abs)` 判定「不以 `..` 开头且非绝对路径」 | 10 分钟 + 单测 |
| **P0-3** | **上传把整个文件读进内存** | `app/api/files/route.ts:48` `await req.formData()`、`:71` `Buffer.from(await f.arrayBuffer())` | 单文件上限 100MB，并发 5 个上传 = 500MB 常驻；多用户同时传会 OOM。这是**唯一无降级的资源入口** | 用 `req.body` 流式写盘 + 边写边累加 size 校验上限；或把上限降到 20MB + 前端分片 | 1 天（流式）/ 1 小时（降上限，先止血） |
| **P0-4** | **成本看板没有金额，且用量靠字符串拆分** | `app/api/admin/cost/route.ts:22-36`：只 `sum(tokens)`；模型名/标签靠 `split_part(target,' | ',1..3)` 从字符串里解出来；`models.price_in/price_out` 只有 `admin/models` 写入，**全项目无人读取** | ① 后台配了单价但看板永远没有钱数，成本管理等于摆设；② `target` 是 `model \| label \| OK \| 1200ms` 拼串，模型名含 ` \| ` 就错位；③ 想按模型聚合只能在 SQL 里拆字符串 | `operation_logs` 加 `model` / `label` / `status` / `duration_ms` 四个真列（`duration_ms` 已存在），迁移期双写；成本按 `sum(tokens × 单价)` 算，并分输入/输出 | 1 天 |

> P0-1 与 P0-4 的共同点：**「写进去了但没人读」**——`status` 字段登录读、会话不读；`price_in` 后台写、看板不读。这类"半截功能"比没写更危险，因为它让人以为已经生效。

### P1 · 工程质量（杠杆最大，建议两周内）

| # | 问题 | 证据 | 影响 | 修法 | 成本 |
|---|---|---|---|---|---|
| **P1-1** | **`strict: false`，`tsc` 0 错误的含金量有限** | `tsconfig.json:6` `"strict": false`；全项目 `: any / as any` 共 **302 处**（前端 `Chat.tsx` 14、`AdminClient.tsx` 14、`Composer.tsx` 13…） | `strictNullChecks` 关闭意味着「可能为 undefined」的访问不报错——本机跑得通、生产遇空数据就 500。这是**整个项目最大的一笔质量债**，也是「tsc 0 错误」说服力打折的原因 | 分三步，每步独立提交 + 跑全量测试：① 开 `noImplicitAny`（先修最痛的推断）② 开 `strictNullChecks`（会暴露大量 `!` 与非空断言，需逐个处理）③ 开全 `strict` | 3–5 天（③ 最难，可长期停在 ② 并接受） |
| **P1-2** | **前端没有统一请求封装，68 处散落 `fetch` + `.catch`** | `Chat.tsx:16` / `connectors/page.tsx:10` / `capabilities/page.tsx:9` / `knowledge/page.tsx:8`… 各写各的 | ① 错误提示风格不一（有的 antd message、有的静默）；② **401 不会自动跳登录**——token 过期后每个页面各自报错但不跳转；③ 无统一超时、无统一 loading | 抽 `lib/apiClient.ts`：`get/post` + 超时 + 统一错误提示 + 401 跳 `/login` + 可选 SWR 缓存（复用 `clientCache`） | 1–2 天（改造点近百处，但机械） |
| **P1-3** | **没有 traceId，日志无法跨环节串联** | 全项目 grep `traceId / requestId / x-request-id` = **0 命中**；`operation_logs` 只有 `action + target` 字符串 | 一次对话会产生「chat 埋点 + 工具调用 + 能力操作 + 记忆抽取」多条日志，**无法证明它们属于同一次请求**。排障只能靠时间戳猜 | `middleware.ts` 生成 `x-request-id`（已有中间件，加 3 行）；`operation_logs` 加 `request_id` 列；`logLlm` / `logAction` / 能力操作统一透传 | 半天 |
| **P1-4** | **没有健康检查接口** | `app/api/` 下无 `health` / `ping` | 部署到 K8s / 负载均衡时没有探针可挂；redis 挂了、pg 挂了、队列挂了都无法被外部感知（只能等用户报错） | `GET /api/health`：查 `SELECT 1` + `pingRedis()` + 队列可用性，返回 `{ok, db, redis, queue, version}`，**不鉴权但只暴露状态不暴露配置** | 半天 |
| **P1-5** | **45/68 个路由没有 try/catch，错误响应不统一** | 有 `try {` 的 route.ts 仅 23 个 | 未捕获异常由 Next 兜底成 500 + 空 body，前端 `res.json()` 直接抛，用户看到「加载失败」但拿不到原因 | ① 加统一 `withApi(handler)` 包装（鉴权 + try/catch + 统一 `{error}` + requestId）；② 或至少在 `app/error.tsx` 之外补 `app/api` 的 `instrumentation` 级兜底 | 1 天（包装器）+ 逐步迁移 |

### P2 · 架构与部署（多副本前必做，单机可暂缓）

| # | 问题 | 证据 | 影响 | 修法 |
|---|---|---|---|---|
| **P2-1** | **定时任务没有分布式锁，多副本会重复执行** | `lib/scheduler.ts` 全文件无 `lock / advisory / leader`；`globalThis.__wb_scheduler_started` 只是**进程内**防重 | 单机正常；一旦上 2 个 Pod，同一个 cron 被执行 2 次（发 2 封通知、跑 2 次技能、扣 2 次额度） | 执行前抢 PG `pg_try_advisory_lock(hashtext(scheduleId))` 或 Redis `SET NX EX`；抢不到就跳过 |
| **P2-2** | **限流器的降级方向是反的** | `lib/redis.ts:129-138`：Redis 抛错时 `return memoryLimiter.check(...)`——**每个实例各自放行 max 次** | 单机没问题；多副本时 Redis 一抖动，限流上限变成 `max × 副本数`，等于放开。且是**固定窗口**（`incr`+`expire`），窗口边界可打出 2 倍突发 | 多副本场景改为「Redis 不可用即拒绝」（fail-closed）或至少告警；算法换滑动窗口（`ZSET` 或 `redis-cell`） |
| **P2-3** | **语义缓存 key 不含对话历史，多轮会串答案** | `lib/cache.ts` `keyOf(model, system, prompt)`，无 history | 同一句话在不同上下文里问，命中同一个答案 → **答非所问**。而 chat 的 `system` 里带知识片段，所以只在"知识库为空 + 同模型 + 同问题"时命中，实际触发概率低于直觉，但一旦触发就是错答 | 把「历史轮数 + 历史摘要 hash」纳入 key；或仅首轮（history 为空）启用缓存 |
| **P2-4** | **`ensureInit()` 被 128 处调用，多副本同时启动会撞 DDL 锁** | `lib/db.ts:488`，调用点 128 个；内部是 `CREATE TABLE / ALTER / CREATE INDEX` 串行 | 单机靠 `initPromise` 幂等；多副本同时冷启动会并发执行 DDL，PG 会串行化甚至死锁，启动变慢。失败会 `initPromise=null` 允许重试（这点是对的） | 迁到独立 `migrate` 脚本（部署前跑一次），运行时只做连通性检查；至少加 advisory lock 包住初始化 |

## 三、如果只做 3 件事

按「风险 × 成本」排序，这三件最划算：

1. **P0-1 禁用用户即时失效**（半天）
   这是唯一一个「管理员以为已经处置了、实际没处置」的问题。安全类问题里，**误以为生效**比明显缺失更危险。

2. **P1-1 开 `strictNullChecks`**（2–3 天）
   它不会立刻修掉任何 bug，但会让后续所有改动**在编译期就暴露空值假设**。越晚开，改造面越大。

3. **P0-4 结构化日志列 + 成本金额**（1 天）
   一次改动同时解决「成本看不到」和「日志靠拆字符串」，而且 `operation_logs` 是 P1-3（traceId）的地基。

## 四、两个可选方案

| | 方案 A · 最小闭环（推荐） | 方案 B · 全面加固 |
|---|---|---|
| 范围 | P0 全部 4 项 + P1-4 健康检查 | P0 + P1 全部 + P2 全部 |
| 工作量 | 2–3 天 | 8–10 天 |
| 交付后状态 | 安全硬伤清零，可以放心给团队用 | 具备上多副本（K8s）的条件 |
| 不适合 | 需要立刻横向扩容 | 单人/单机使用，多副本不是近期目标 |
| 风险 | 无（都是收敛性改动） | `strict` 改造会触碰大量文件，需分批提交 |

> 我的判断：**先做 A**。P2 的前提是"要多副本"，而当前 3000 端口跑的是单实例 `next dev`——**在没有第二个副本之前，P2 全是纸上作业**。A 做完再谈扩容。

## 五、排除的误报（查证后认为**不是**问题）

诚实记录，避免下次重复排查：

| 疑似问题 | 查证结果 |
|---|---|
| `ensureInit()` 失败后永久不可用 | **不是**。`lib/db.ts:529-532` 的 `.catch` 里 `initPromise = null`，下次请求会重试 |
| NDJSON 流式解析会被半行切断 | **不是**。`Chat.tsx:584-590` 用 `buf` 保留残留 + `decoder.decode(value, {stream:true})` 处理多字节边界，逻辑正确 |
