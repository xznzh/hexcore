## 一、版本判定：小版本 v8.1.0

依据 [Git 分支与发布规范](../04-规范/Git分支与发布规范.md) §5 与语义化版本；当前最新 tag 为 `v8.0.1`。

| 候选 | 触发条件 | 本批是否满足 | 判定 |
| --- | --- | --- | --- |
| **MAJOR 9.0.0**（大版本） | 破坏性变更 / 架构大改版（对照 v8.0.0 = Next 15 + React 19 升级） | ❌ 无依赖大升级、无 API 重写、无数据结构破坏 | 否 |
| **MINOR 8.1.0**（小版本） | 向后兼容的功能新增 | ✅ 新增输出侧护栏、pgvector 检索快路径与自检、六层 QA 测试体系 | **是** |
| **PATCH 8.0.2**（补丁） | 仅向后兼容的 bug 修复 | ⚠️ 修复占大头，但确实引入了新能力 | 不推荐 |

**为什么 403→401 不算破坏性变更**：管理接口未登录时原本错误地返回 403，本批改回 401、越权才返回 403，是**修正错误码**而非新增不兼容语义；受影响的只有未登录的管理接口调用方，且平台前端重登逻辑本就按 401 设计。`GET /api/chat` 补 `Allow: POST` 属于补齐 HTTP 契约，不改变既有行为。

**为什么数据库变更也不算破坏性**：`lib/db.ts` 只做幂等 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`，旧库不迁移也能跑（无向量列时自动降级为内存余弦）。符合规范 §7「数据库变更能在旧库上幂等执行」。

**为什么不发 8.0.2**：把「pgvector 启用 + 输出护栏」压进补丁号，会让 tag 无法表达「这一版加了能力」，回溯时容易误判为纯修 bug。若维护者坚持只收修复，可改发 `v8.0.2`，但需把 `feat(retrieval)` 一组拆到下一个迭代。

> 按规范 §11.8，**版本号最终由维护者在 `release:start` 时决定**，以上为建议，不是既成事实。

### 4.2 必须先解决的流程矛盾

`release:start` 内部调用 `ensureClean('切版本分支')`，**要求工作区干净**；而当前 `main` 上有 45 项未提交改动，`pre-commit` 钩子又**禁止在 main 直接提交**。三者互相卡住，所以不能直接 `pnpm release:start 8.1.0`，也不能在 main 上先 commit。正确顺序是「暂存改动 → 切分支 → 恢复改动 → 分组提交」。

### 4.3 完整命令序列（维护者执行）

```bash
# 0) 现状确认（应显示 main / v8.0.1 / 45 项未提交）
pnpm release:status

# 1) 先跑全量门禁（新增文档后也要复跑 docs:check）
pnpm release:check

# 2) 把未提交改动连未跟踪文件一起暂存，让工作区变干净
#    -u 含 untracked；被 gitignore 的 .env.local/.next/data 不会被带走
git stash push -u -m "wip: v8.1 QA 全维度测试与缺陷修复"

# 3) 用官方脚本切分支（自动改 package.json 版本 + 生成 C0 提交）
pnpm release:start 8.1.0

# 4) 恢复改动（package.json 由脚本改过、stash 里没有它，不会冲突）
git stash pop

# 5) 按 4.1 分组提交，逐组 git add + git commit
git add app/api/chat/route.ts lib/agent/output-guard.ts tests/output-guard.test.ts
git commit -m "fix(chat): 增加输出侧护栏与空答兜底，收紧流式回答风险语境"
# C2 ~ C5 同理，路径与 message 见 4.1 表格

# 6) 提交后再跑一次门禁，确认文档链接与类型检查全绿
pnpm release:check

# 7) 推分支（pre-push 钩子会拦 push 到 main，推 release 分支不受影响）
git push -u origin release/v8.1.0
```

**备选路径（不想用 stash 时）**：`git switch -c release/v8.1.0` 可以直接带着未提交改动切分支（git 允许，只要无冲突），随后手工把 `package.json` 的 `version` 改成 `8.1.0`，并把这一步作为 C0 单独提交。缺点是绕开了 `release:start` 的 tag 存在性检查与远端同步，且不会自动生成版本号提交，不推荐。

### 4.4 合并与打 tag（需维护者明确同意后执行）

按规范 §2 步骤 4B（开了保护分支，推荐）：

```bash
# 网页开 PR：release/v8.1.0 -> main，合并方式选「保留合并提交」，不要 squash
git switch main && git pull --ff-only
pnpm release:tag 8.1.0 --push       # 在 main 的合并提交上打 annotated tag，仅维护者可执行
pnpm release:notes                  # 生成发布说明，可贴到 MR / 群
```

未开保护分支时可改用 `pnpm release:finish 8.1.0 --push`（同样需明确授权）。**tag 只打在 main 的合并提交上、只增不改**；合并后删除 release 分支。

### 4.5 提交前自查（规范 §7 / §11.5）

- [ ] `git status` 里没有 `.env.local`、`.workbuddy/`、`.next/`、`data/`、`*.log`、临时脚本
- [ ] `package.json` 的 `version` = `8.1.0`，与即将打的 tag 一致
- [ ] `docs/README.md` 索引已补本轮记录；`npm run docs:check` 0 断链
- [ ] `pnpm release:check` 结果贴进 MR；本批改了对话主流程，建议额外补 `pnpm e2e` 结果
- [ ] 数据库变更已确认在旧库上幂等（`CREATE ... IF NOT EXISTS` + `ALTER`）
- [ ] MR 里写清回滚方式：`git revert <merge-sha>`；`embedding_vec` 列是幂等新增，回滚代码不会破坏旧逻辑

### 4.6 回滚说明

代码回滚用 `git revert <merge-sha>`（保留历史，禁止改写 main）。数据库侧只新增了向量列与 HNSW 索引，旧代码不依赖它们，`embedding` JSON 向量仍在，回滚后自动退回内存余弦路径；无需删列。输出护栏回滚后 P0 场景会重新暴露，属于已知风险，回滚需在 MR 里注明。

## 六、附：本轮用到的知识点

| 概念 | 为什么学 | 落点 |
| --- | --- | --- |
| 语义化版本 MINOR vs PATCH vs MAJOR | 版本号的判定依据是「是否新增向后兼容能力」，不是「改了多少文件」；错误码修正与幂等 DDL 不算破坏性 | 本文 §一、`scripts/release.mjs` 的 `VERSION_RE` |
| 分支模型的「先切后提」 | `main` 只接受合并，`release:start` 又要干净工作区；未提交改动必须先 `stash -u` 才能走官方脚本 | 本文 §4.2/4.3、`scripts/release.mjs` 的 `ensureClean` / `guardCommit` |
| Conventional Commits 钩子 | `commit-msg` 用正则强校验，scope 只允许 `[a-z0-9\-./]`；提交信息不合规会被直接拦下 | `scripts/release.mjs:25` 的 `CONVENTIONAL_RE` |
| 流式输出的确定性护栏 | 提示词是软约束，模型会换措辞绕过；必须在 `delta` 推送前做输出侧断言 + 尾缓冲防跨 chunk 泄漏 | `lib/agent/output-guard.ts`、`app/api/chat/route.ts` |
| 「装了扩展」≠「能力可用」 | pgvector 需扩展 + 向量列 + 维度一致 + 存量回填 + HNSW 五项合取，缺一项就静默降级成死代码 | `lib/db.ts` 的 `ensureVectorColumn()`、`app/api/health/retrieval/route.ts` |
| 证据脱敏审查 | 提交前对运行产物递归查 `password/token/secret/apiKey` 类键，只报键路径与长度、不回显值 | 本文 §2.2 |
