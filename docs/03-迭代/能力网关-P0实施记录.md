# 能力网关 P0 实施记录（工具注册表 + 连接器生命周期 + 能力目录）

> 编制日期：2026-10-26 ｜ 对标：成熟网关产品的能力网关思路
> 原则：只做增量演进，不推翻现有路由与表结构；旧库通过 `CREATE TABLE IF NOT EXISTS` + 幂等 `ALTER` 平滑升级。

---

## 一、目标与范围

把「三方接口 / 内置工具」从零散的路由与提示词里抽出来，形成一套可治理的能力底座：

| 能力 | 说明 |
| --- | --- |
| 统一工具注册表 | 权限 → 审批 → 超时 → 审计，聊天 / API / 技能共用同一套语义 |
| 连接器生命周期 | 发现（discover）→ 确认安装（confirm）→ 健康检查 → 刷新（preview/apply）→ 成员授权 → 撤销 |
| 能力目录 | 目录查询、调用、异步操作、审批、调用记录、指标 |
| 调用审计 | 统一落 `operation_logs`（状态 / 耗时 / 摘要），并聚合到 `capability_operations` |

**明确不做**（与成熟网关产品的差异）：Docker 容器运行时、PPT 模板编辑器、微信/看板集成。成本高、与现有能力重叠低。

## 二、数据模型

新增 3 张表（`lib/schema.ts`，建表与迁移在 `lib/db.ts`）：

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `capabilities` | 能力定义 | `connector_id` / `key` / `method` / `path` / `parameters` / `input_schema` / `response_mapping` / `min_role` / `requires_approval` / `timeout_ms` / `fingerprint` / `status` |
| `capability_grants` | 用户/角色白名单 | `scope`（`connector` \| `capability`）、`target_id`、`subject_type`（`user` \| `role`）、`subject_id` |
| `capability_operations` | 调用 / 审批 / 指标载体 | `capability_id`（注册表工具为 `null`）、`connector_id`、`user_id`、`status`、`mode`（`sync` \| `async`）、`input`、`output`、`error`、`duration_ms`、`source`、`conversation_id`、`approved_by` / `approved_at` |

`connectors` 增列：`status`（`active` / `disabled` / `revoked`）、`spec_url`、`base_url`、`discovered_at`、`revision`、`health_status`、`health_detail`、`last_checked_at`。
`operation_logs` 增列：`status`、`duration_ms`、`detail`，`logAction()` 支持 meta。

统一约束：

- 唯一索引 `idx_capabilities_connector_key`，保证同一连接器下能力 `key` 唯一（刷新幂等）。
- 指标/记录查询相关索引：`idx_capability_ops_user`、`idx_capability_ops_status`、`idx_capability_ops_created`。
- 时间戳一律 `Date.now()` 存数字；ID 用 `newId('前缀')`。
- 删除连接器时把其能力置 `revoked`，不物理删除，避免调用记录成孤儿。

## 三、后端模块

| 模块 | 职责 |
| --- | --- |
| `lib/connectors/openapi.ts` | 解析 OpenAPI 3.x / Swagger 2.0（JSON）：`parseOpenApi`、`diffCapabilities`（纯函数，可单测） |
| `lib/connectors/service.ts` | `loadSpec` / `upsertCapabilities` / `previewRefresh` / `applyRefresh` / `checkConnectorHealth` |
| `lib/capabilities.ts` | 权限判定、参数校验 `validateCapabilityInput`、请求拼装 `buildCapabilityRequest`、真实调用 `callCapability`、`invokeCapability`（同步/异步）、`decideApproval`、`cancelOperation` |
| `lib/tools/registry.ts` | 统一工具注册表：`registerTool` / `invokeRegisteredTool`（权限、审批、超时、审计） |
| `lib/tools/capability-tools.ts` | 聊天工具 `list_capabilities` / `invoke_capability`，内部走注册表 |
| `lib/http.ts` | 复用 GBK 解码与 `applyResponseMapping`（extract / pick / limit） |

### 权限与审批

- 管理员：全量可见、可调用，**始终跳过审批**。
- 普通成员：`min_role` + 连接器 `visible_roles` + 白名单（若存在 grant，则只放行命中的用户/角色；连接器级与能力级白名单需同时通过）。
- `requires_approval=true` 的能力 / 工具：非管理员调用落 `pending_approval`（HTTP 202），管理员在「能力目录 → 待审批」批准后自动执行。
- 管理员审批只约束非管理员，避免自己给自己审批。

### 参数校验与异步执行

- **轻量校验**：`validateCapabilityInput` 按 `input_schema` 拦「必填 / 基础类型 / 枚举」，只拦明确错误；schema 之外的字段不拒绝（三方接口常有隐式参数）。API 返回 400 + `errors[]`，聊天工具返回可读提示并附参数清单。
- **后台执行**：`POST /api/capabilities/invoke` 传 `mode:'async'` 时先落 `running` 记录，再在进程内后台执行并立即返回 202 + `operationId`；前端轮询 `/api/capabilities/operations/{id}`，调用记录/待审批页每 6 秒自动刷新。
- 需审批 + 异步：审批单保存 `mode`，管理员批准后同样转后台执行，使用审批时保存的 `input`（防偷换参数）。
- 运行中被取消：`runOperation` 写回结果前复查状态，保留 `cancelled`，不被迟到结果覆盖。
- 部署提示：进程内后台执行适合本地/自托管常驻进程；无状态 Serverless 需改为 BullMQ Worker（`lib/queue.ts` 已有 Redis 队列基础）。

### 刷新语义（重点）

- **发现只读**：`/discover` 只解析并返回候选，不写库；`/confirm` 才落连接器与能力。
- **内联文档可刷新**：无 `specUrl` 时把原始 spec 缓存在 `connectors.config.spec`，刷新仍可用。
- **跳过项不复活**：`confirm` 时把未勾选的 key 存入 `config.skippedKeys`，刷新预览会过滤这些 key，不会当「新增」反复提示。
- **下架只停用**：文档中移除的能力置 `status='disabled'`，保留历史调用记录；已停用项不再在后续预览里重复报告。
- 刷新保留管理员手工配置（审批、最低角色、响应映射、超时）。

## 四、API 一览

### 连接器

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/connectors` | 列表（含能力数、健康状态）。非管理员不下发 `config`（可能含密钥） |
| POST / PATCH / DELETE | `/api/connectors` | 手动创建 / 更新 / 删除（删除时级联把能力置 `revoked`） |
| POST | `/api/connectors/discover` | 解析 OpenAPI，返回候选能力（只读） |
| POST | `/api/connectors/confirm` | 确认安装（可传 `connectorId` 追加能力） |
| POST | `/api/connectors/test` | 旧版 HTTP 连通性测试 |
| POST | `/api/connectors/{id}/health` | 健康检查并写回 `health_status` |
| POST | `/api/connectors/{id}/refresh/preview` | 对比最新文档：新增 / 变更 / 下架 |
| POST | `/api/connectors/{id}/refresh/apply` | 应用差异（可传 `decisions` 只应用部分） |
| GET / POST / DELETE | `/api/connectors/{id}/members` | 连接器白名单 |
| POST | `/api/connectors/{id}/revoke` | 撤销连接器（能力不可见） |

### 能力目录

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/capabilities` | 当前用户可见能力；`?all=1` 管理员看全部 |
| PATCH / DELETE | `/api/capabilities/{id}` | 配置（审批/超时/映射/状态）/ 删除 |
| POST | `/api/capabilities/invoke` | 调用（`name` 传 id 或能力名，`mode` 支持 `sync`/`async`）；参数不合法 400，需审批 / 后台执行返回 202 |
| POST | `/api/capabilities/approvals` | 管理员批准 / 拒绝 |
| GET | `/api/capabilities/operations` | 调用记录：`status` / `capabilityId` / `mine` / `q`（能力名、调用者、操作编号）/ `limit` / `offset`，返回 `{ items, total }` |
| GET / DELETE | `/api/capabilities/operations/{id}` | 详情 / 取消 |
| GET / POST / DELETE | `/api/capabilities/grants` | 能力级白名单 |
| GET | `/api/capabilities/metrics?days=30` | 调用量、成功率、平均耗时、待审批、Top 能力、**每日趋势 `daily[]`**（SQL `GROUP BY` 聚合，非管理员按 `user_id` 过滤） |

> 路由模板保持项目约定：`force-dynamic` → `ensureInit()` → `getSession()` 判空 401 → `NextResponse.json`。

## 七、已知限制与下一步

1. **外部网关未接**：前端占用 `/api/*`，对端的 `/api/*` 在网关侧，真实地址与用户标识头规则待对方确认。本 P0 不依赖它。
2. **异步执行为进程内后台任务**：本地/自托管常驻进程可用；无状态 Serverless 多实例下需替换为 BullMQ Worker（`lib/queue.ts` 已有队列封装与降级逻辑）。
3. **指标为实时 SQL 聚合**：已下推 `GROUP BY` 并补 `created_at` 索引，避免把明细拉回 Node；数据量再上一个量级可加日粒度汇总表。
4. **MCP 仅做连通性探测**：把 MCP tools 映射为能力是 P1 可选项。
5. **审批只约束非管理员**：若后续需要「管理员双人复核」，再加审批策略表。
6. **参数校验为轻量版**：只覆盖必填 / 基础类型 / 枚举，不做嵌套对象与 `oneOf` 等完整 JSON Schema 校验（三方接口隐式参数较多，严格校验误伤大）。

## 八、对话框调用三方能力的两个坑（2026-10-27 修复）

现场复现：同一个能力「报警导出（Excel）」，在「能力目录」页点调用 → 成功（3831ms，返回 `artifacts[].url` 下载链接）；
在对话框用 `/` 关联同一个能力 → 回「**未找到连接器：某个能力提供方。可用连接器：（暂无连接器）**」，
且输入框/气泡里露出一截 `@cap:cap_mvq90chdrvkwvv:报警导出（Excel）` 内部标记。

### 坑 1：模型把「能力」当成「连接器」去调了

| 环节 | 旧行为 | 问题 |
| --- | --- | --- |
| 硬指令 | `1. 某个能力（name 传「cap_xxx」，连接器 提供方名）` | 把「连接器 X」写进指令，等于主动提示模型去 `call_connector` |
| 工具描述 | `call_connector`：name 为连接器名称 | 模型优先选名字更贴合的旧工具 |
| 结果 | `call_connector` 的连接器名单为空 | 回「（暂无连接器）」，用户以为平台没接上 |

修法（三层一起堵）：

1. **指令去歧义**：能力清单改为 `名称｜能力标识｜提供方｜参数`，并显式写明「**严禁改用 call_connector / list_my_connectors**，提供方名字不是连接器名」。
2. **工具描述纠正**：`invoke_capability` 明说「一切能力只能走本工具」；`call_connector` / `list_my_connectors` 反向标注「不适用于能力目录」。
3. **`call_connector` 自愈**（`capabilityCallHint`）：没匹配到普通连接器时，回捞能力目录里按「能力名 / 能力 key / 连接器名」命中的项，直接把**能力标识**回给模型，下一步必然能改调 `invoke_capability`，不必再靠一次失败的往返让模型自己悟。

### 坑 2：`@cap:` 标记泄漏到用户可见的地方

旧实现是「选中能力 → 往输入框正文追加 `@cap:<id>:<name>` → 服务端正则解析并清洗」。清洗只发生在**发给模型和落库**这一层，于是漏了三处：

- 输入框里明文可见（用户以为要自己删）；
- 前端乐观渲染的用户气泡直接显示原始 `prompt`；
- **会话标题**取的是 `prompt.slice(0,20)` → 左侧会话列表标题变成 `@cap:cap_xxx:...`。

修法：**标记彻底不落地**。

- 前端：`/` 选中能力只写 `capChips` 状态，正文保持干净；发送时用结构化字段 `capIds: string[]` 随请求带上。
- 服务端：主通道读 `capIds`；同时保留 `@cap:` 正则解析做兼容，并在入口处 `cleanPrompt` 一次，标题、`estimateTokens`、落库正文统一用它。
- 回显：`messages.meta = { caps: [{id,name}] }`（原本就有），前端在用户气泡里用蓝色 Tag 回显「能力：X」，历史消息刷新后同样可见。旧数据里残留的标记在 `MessageItem` 渲染时再剥一次，兜底不露馅。
- 只关联能力、没写字就发送：前端补一句 `请使用「X」处理`，避免「点了发送没反应」。

### 顺手补的：产物下载链接

能力结果里 `artifacts[].url` 是可直接下载的文件链接，但模型常只复述文件名（`报警报告_20261026.xls`），用户拿不到链接。
`invoke_capability` 现在会解析结果 JSON，把产物整理成 `- [文件名](url)` 附在工具返回里，并明确要求模型原样给出；提示词里也加了同一条约束。

### 仍未做的

1. **没有强制 `toolChoice`**：能力关联目前仍是「强指令 + 自愈」，不是硬保证。要 100% 保证可以给 `streamText` 传 `toolChoice: { type:'tool', toolName:'invoke_capability' }`，但不少国产 OpenAI 兼容端点对强制工具支持不稳，等有真实模型可回归时再开。
2. **多能力关联**：目前最多 5 个，模型自行排序执行；没有「并行调用」编排。
3. **旧会话标题不会自动修正**：已被写成 `@cap:...` 的历史标题仍在库里，需要一次性 SQL 清洗（或改名）。
