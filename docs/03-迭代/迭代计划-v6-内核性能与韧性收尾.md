# 迭代计划 v6 —— 内核性能与韧性收尾

> 编制日期：2026-10-27 ｜ 基线：`迭代计划-v5-性能与体验收尾.md`（前端性能包已落地）
> 触发缘由：用户要求「在现有项目基础上做一轮优化，直接改代码」。
> 定位：**内核层**性能与韧性（v5 解决的是前端/接口层的卡顿，v6 补的是服务端热路径与数据有界性）。
> 原则：不推翻既有功能与路由，增量演进；每个改动保持 `typecheck` / 单测通过、可演示。

---

## 一、现状复查（v6 接手时实测发现的真问题）

本次直接读代码 + 类型检查 + 单测验证，定位到 5 个内核层可优化点（非凭空设想）：

| 编号 | 位置 | 问题 | 影响 |
| --- | --- | --- | --- |
| O1 | `lib/cache.ts` `cacheStats()` | 把整张 `operation_logs` 拉进内存再 JS 过滤命中率 | 日志增长后全表扫描，管理后台命中率统计变慢 |
| O2 | `lib/llm.ts` `resolveModelWithFallback()` | 每次对话都 `select().from(models)` 查全表，无缓存 | 每个对话请求白做 1~2 次 models 表往返 |
| O3 | `lib/observability.ts` `logLlm()` | 每次 LLM 调用写一行 `operation_logs`，表无限膨胀 | 长期运行反噬所有依赖该表的查询 |
| O4 | `app/api/chat/route.ts` 首字延迟 | 用户/用量/会话/历史/知识库/记忆/个人快照等**相互独立**的查询串行 await | 首字延迟随查询数线性叠加 |
| O5 | `lib/scheduler.ts` | 用模块级 `started` 标志，Next dev HMR 重载会重复起定时器 | 定时任务被重复注册/执行 |

## 二、优化项（✅ 本轮已全部实施并通过验证）

### O1 · 缓存命中率统计改 SQL 聚合（消除全表扫描）
- **文件**：`lib/cache.ts`、`lib/db.ts`
- **改动**：
  - `cacheStats()` 由「`select` 全表 + 内存 `filter`」改为两次 `db.$count(operationLogs, and(eq(action), eq(target)))`。
  - `lib/db.ts` 的 `INDEX_STMTS` 新增 `idx_operation_logs_action (action, created_at)`，让统计与后台日志按 action 过滤走索引。
- **收益**：命中率统计从 O(n) 全表扫描降为 O(1) 索引聚合；`operation_logs` 增长后不再变慢。

### O2 · 模型解析结果短 TTL 缓存（减少每请求 DB 往返）
- **文件**：`lib/llm.ts`
- **改动**：`resolveModelWithFallback()` 对「未指定模型」的高频路径加 30s 内存缓存（模型配置是管理员低频变更，30s 陈旧可接受）；指定模型路径仍需即时校验可见性/启停，**不缓存**。
- **收益**：对话/调度等热路径少 1~2 次 `models` 表往返；配置变更最多 30s 后生效。

### O3 · 审计日志留存防膨胀（平台 longevity）
- **文件**：`lib/db.ts`
- **改动**：新增 `trimOperationLogs({ maxRows=200000, olderThanDays=90 })`，best-effort 删除「早于 90 天」或「超过 20 万条中最旧的」记录；在 `ensureInit()` 末尾 fire-and-forget 触发（不阻塞启动）。
- **收益**：`operation_logs` 有界，长期运行的命中率统计、管理后台日志、操作审计不会被日志量拖垮。

### O4 · 对话首字延迟：独立查询并行化
- **文件**：`app/api/chat/route.ts`
- **改动**（3 处彼此独立的查询组改为 `Promise.all`）：
  1. 用户 / 用量 / 会话 三查并行（原先串行 3 次往返 → 1 次）。
  2. 历史消息 / 知识库列表 / 长期记忆 三查并行（原先串行 → 1 次）。
  3. 个人数据快照的 6 个查询（存储汇总 / 项目 / 项目成员 / 我的文件 / 技能 / 定时任务）并行（原先串行 6 次 → 1 次）。
- **收益**：对话冷请求的首字延迟显著下降（约 10 次串行 DB 往返收敛为 ~3 次并行批次），且**不改变任何业务行为**（变量与失败语义完全保留）。

### O5 · 调度器跨 HMR 单例
- **文件**：`lib/scheduler.ts`
- **改动**：启动标志由模块级 `let started` 改为 `globalThis.__wb_scheduler_started`，避免 Next dev HMR 模块重载导致多个 `setInterval` 叠加。
- **收益**：开发态不会重复注册/执行定时任务；生产态行为不变。

## 二（续）· V6.1 增量优化（✅ 已实施，用户要求「把能做的都做了」）

> 在 v6 内核包之上，继续以「AI 架构师视角」扫描内核热路径，又落地 5 项真实优化（O6–O10）。
> 思路不变：**不推翻既有功能与路由**，只收拾「全表加载 / 缺索引 / 同步埋点 / 降级路径无上限」这类隐性坑。

### O6 · 智能体引擎按名查连接器：去掉「每次工具调用加载全部连接器」
- **文件**：`lib/agent/engine.ts`
- **问题**：`runTool()` 里 `db.select().from(connectors).limit(50)).find(x => x.name === tool)` —— **每次工具节点都先把全部连接器拉进内存再 JS 过滤**。一个技能若有多个 `tool` 节点或 `loop`，就是 N 次 × 50 行的浪费。
- **改动**：改为 `db.select().from(connectors).where(eq(connectors.name, tool)).limit(1)`，直查命中对名称的索引（见 O9）。
- **收益**：工具调用路径从「加载全部 → 内存 find」降为单次索引点查；多工具 / 多循环技能尤其明显。

### O7（= 原 S1）· RAG 内存降级路径封顶：杜绝无 pgvector / 全局检索时的全表 OOM
- **文件**：`lib/ai/rag.ts`
- **问题**：`retrieve()` 的**内存降级路径**（无 pgvector、或多模型混合、或 JSON-only 向量）会 `select` 整个 `chunks` 表并逐行算余弦。最危险的是 `search_knowledge` 工具调用 `retrieve(query, 4)` **不带 kbId 过滤** → 直接全表扫描 + 全量余弦 → 知识库一大就 OOM。
- **改动**：内存路径先用**词面命中（`ILIKE`，token 取自既有 `tokenize`）**做候选召回，再在内存里算余弦/重排，并加硬上限 `LIMIT 3000`；查询无可用词面时直接 `WHERE 1=0` 不召回，彻底避免全表。
- **收益**：降级路径内存有界（最坏 3000 行），不再因全局语义检索把整张 `chunks` 拉爆；生产态（pgvector 快路径）不受影响。
- **边界**：降级路径现在要求词面重合才进入候选，召回口径与聊天层 `filterRelevantHits` 一致——纯向量语义强匹配在 pgvector 不可用时优先级降低，这是降级路径的固有取舍（生产靠 pgvector 快路径兜底）。

### O8 · 埋点写库异步化：每次 LLM 调用不再阻塞首字延迟
- **文件**：`lib/observability.ts`
- **改动**：`logLlm()` 的 `db.insert(operationLogs)` 由 `await` 改为 **fire-and-forget（`.catch(()=>{})`）**。`withObservability` 仍 `await logLlm(...)`，但函数体不再等写库完成即返回。
- **收益**：对话 / 智能体每一步都经过 `logLlm`，原先每次都要等一条 `operation_logs` 写入完成才返回；异步化后写库在后台进行，**首字延迟与每步耗时直接下降**。丢失一条 best-effort 观测记录不影响主流程（且 O3 的留存裁剪仍独立运行）。

### O9 · 补齐缺失的二级索引（直接支撑 O6 与记忆检索）
- **文件**：`lib/db.ts`（`INDEX_STMTS`）
- **改动**：新增 4 个 `CREATE INDEX IF NOT EXISTS`：
  - `idx_connectors_name ON connectors(name)` —— 支撑 O6 的按名直查。
  - `idx_memories_user ON memories(user_id)`、`idx_memories_scope ON memories(scope)`、`idx_memories_project ON memories(project_id)` —— 支撑 O10 的记忆检索以及团队/项目记忆过滤。
- **收益**：这些 `where` 过滤原先都退化为全表扫描（schema 此前几乎没有二级索引，只有 email/code/token 三个唯一约束）；现在走索引。全部幂等，老库升级自动补齐。

### O10（关联 O7）· 长期记忆检索内存封顶：团队记忆膨胀不再全表拉取
- **文件**：`lib/ai/memory.ts`
- **问题**：`retrieveMemories()` 原把「全部团队记忆 + 全部个人记忆 + 全部项目记忆」三张结果拉进内存再逐条算余弦。团队记忆随时间增长会越拉越多。
- **改动**：用查询里的关键词（`≥2` 字）做 `ILIKE` 词面预筛 + 每类硬上限 `500`（`MEMORY_CANDIDATE_CAP`）；无可用词面时退化为「按类取上限若干条」，仍保证内存有界。
- **收益**：记忆检索内存有界，团队记忆规模不再线性拖累每次对话的首字延迟。

## 二（续2）· V6.2 增量优化（✅ 已实施，收尾 §五 候选中的可安全落地项）

> 用户要求「接着做」。扫描 §五 候选 S2–S5，区分「能安全落地」与「改动风险大于收益」：
> - **S3（模型缓存失效钩子）、S4（埋点补真实 token）**：内核层、低风险、收益明确 → 本轮落地（O11 / O12）。
> - **S2（历史 ETag）、S5（能力目录查询下推）**：评估后**暂缓 / 不做**，原因见 §五（前端已有会话级缓存、权限逻辑重写风险高）。

### O11（= 原 S3）· 模型缓存失效钩子：后台改模型即时生效
- **文件**：`lib/llm.ts`、`app/api/admin/models/route.ts`
- **问题**：O2 给「未指定模型」的解析结果加了 30s 内存缓存，但只靠 TTL 过期失效。管理员在后台改默认 / 停用 / 换 Key 后，最多要等 30s 才对新对话生效，体验上有「改了没反应」的错觉。
- **改动**：
  - `lib/llm.ts` 暴露 `invalidateModelCache()`：把 `fallbackCache` 置空。
  - `app/api/admin/models/route.ts` 在 POST（新增）/ PATCH（设默认 / 启停 / 换 Key）/ DELETE（删除）**任一成功写操作后**调用，使缓存立即失效。
- **收益**：模型配置变更从「最多延迟 30s」变为**即时生效**，管理后台操作所见即所得。「指定模型」路径本就不缓存（需即时校验可见性 / 启停），不受影响。
- **边界**：缓存是**进程内内存**；多实例（多 Pod）部署时各实例缓存独立，变更会在各自下一次 TTL（≤30s）或各自收到写请求后生效。单进程 / 单 Pod 部署无此问题。

### O12（= 原 S4）· LLM 调用埋点补真实 token：补齐观测缺口、支撑成本核算
- **文件**：`lib/schema.ts`、`lib/db.ts`、`lib/observability.ts`、`lib/llm.ts`、`app/api/chat/route.ts`
- **问题**：
  1. `operation_logs` 表**此前根本没有 `tokens` 列**（v5 文档误记为「已有但未填」），`logLlm` 即便想落 token 也无法落库。
  2. `withObservability` 只记录耗时与成败，**未提取真实 token**。
  3. **更隐蔽的缺口**：chat 流式主路径**成功时完全不写 `logLlm` 埋点**（仅失败路径写了 `ok:false`），导致最高频的对话调用在「调用次数 / 延迟 / 失败率」观测与成本核算里被漏掉。
- **改动**：
  - `lib/schema.ts` 给 `operationLogs` 加 `tokens` 列；`lib/db.ts` 的 `ALTER` 迁移补 `ALTER TABLE operation_logs ADD COLUMN IF NOT EXISTS tokens INTEGER;`（老库升级自动补齐，新列 nullable 不影响既有行）。
  - `lib/observability.ts` `logLlm()` 落库补 `tokens: p.tokens ?? null`。
  - `lib/llm.ts` `withObservability()` 成功路径 best-effort 提取 `usage.totalTokens`（generateText 同步可取；streamText 的 usage 是 Promise，只读同步属性、不为埋点 await 流完成）并透传。
  - `app/api/chat/route.ts`：**补齐高频 chat 主路径的成功埋点**——流式收尾处 `await result.usage` 取真实 token，调用 `logLlm({ ok: true, tokens })`；同时把失败埋点的 `ms: 0` 改为真实计时。
- **收益**：LLM 调用埋点首次覆盖**全部**高频路径（chat / 智能体引擎 / 记忆抽取 / 定时任务调度），且带真实 token 数，可直接驱动成本核算与「按模型 / 标签」的调用量、延迟、失败率分析。
- **边界**：streamText 场景的 token 提取依赖流结束后的 `usage` resolve，best-effort；提取失败则该条记为 `null`，不影响主流程。

## 二（续3）· V6.3 增量优化（✅ 已实施，收尾「内核之外仍有价值的真问题」）

### O13（= 原 F1）· 操作日志接口服务端分页：后台不再一次性拉全表
- **文件**：`app/api/logs/route.ts`、`app/admin/AdminClient.tsx`
- **改动**：原接口 `select().from(operationLogs).orderBy(createdAt)` 后 `.reverse()` 把整张表拉进内存再灌浏览器——而 V6 的 `trimOperationLogs` 上限是 20 万行，最坏情况一次拉 20 万行 JSON。改为 `?page=&pageSize=` 的 OFFSET 分页 + `db.$count` 取总数，由 DB 按 `created_at DESC` 排序；前端 antd Table 改为受控分页（`current / pageSize / total / onChange` 触发 `loadLogs` 重新拉页）。
- **收益**：管理员日志页内存与带宽从 O(全表) 降到 O(每页 50)，并支持跳页；历史仍完整可查，只是分批加载。
- **边界**：OFFSET 深翻页在超大数据量下略慢；但日志表已被 trim 封顶、后台极少深翻，严格优于「全量加载」。

### O14（= 原 F3）· 连接器 HTTP 调用加超时保护：堵住引擎直连路径的挂死风险
- **文件**：`lib/tools.ts`（`callConnector`）
- **改动**：原 `fetch` 既无 `AbortSignal` 也无超时，下游接口挂起会让整个技能 / 对话卡死。能力网关路径（`invokeRegisteredTool`）早有 30s 超时，但引擎 `runTool` 直连 `callConnector` 绕过了它。本轮在 `callConnector` 内部为 http（15s）与 mcp（8s）两类网络调用加 `AbortController` 超时，超时返回友好失败文案而非无限挂起。
- **收益**：技能编排 / 对话中调用不可达的连接器会快速失败兜底，不再拖垮整次请求。至此五类连接器调用均有界（http 15s / mcp 8s / db `connect_timeout:5` / browser `goto timeout:20s` / sandbox 限时 1s）。
- **边界**：超时阈值（15s / 8s）为经验值；极慢但正常的下游若偶发超时，可在连接器配置侧评估放宽。

### O15（= 原 F2）· 用量累加改原子 upsert：修复并发漏算与重复行
- **文件**：`lib/util.ts`（`addUsage`）、`lib/db.ts`（去重迁移 + 唯一索引）
- **改动**：原 `addUsage` 是「查 → 改/插」竞态，并发对话会漏算 token 或在同 `(user_id, period)` 产生多行。改为单条 `INSERT ... ON CONFLICT (user_id, period) DO UPDATE SET tokens_used = tokens_used + EXCLUDED.tokens_used` 原子累加；迁移先用 CTE 按 `(user_id, period)` 合并历史重复行（累加 token）再建唯一索引 `idx_usage_user_period`。
- **收益**：配额 / 成本统计在并发下准确，且从 2 次查询收敛为 1 次原子写。
- **边界**：唯一索引建在既有数据上——迁移先用 CTE 合并重复行（仅删真重复、累加 token，无数据损失），且 `CREATE UNIQUE INDEX IF NOT EXISTS` 走 `.catch` 兜底，老库升级零风险。

## 二（续4）· V6.4 成本看板（✅ 已实施，消费 O12 的真实 token 做业务价值型可视化）

### O16 · 成本看板：把 O12 落地的真实 token 做成多维度成本报表
- **文件**：`app/api/admin/cost/route.ts`（新增聚合接口）、`app/admin/AdminClient.tsx`（新增「成本看板」Tab）
- **背景**：O12 已让 chat / 引擎 / 记忆 / 调度全路径的 LLM 调用把**真实 token 数**落进 `operation_logs`（action='llm_call'，复用既有 `idx_operation_logs_action` 索引）。但此前这些 token 只躺在日志里，没有任何视图——这是比继续抠内核更有实际收益的方向。
- **后端聚合**：`GET /api/admin/cost?days=7|30|90`，按「日 × 模型 × 用途(label)」三元组一次 SQL 聚合（`to_char` 取日、`split_part(target,' | ',1/2/3)` 解析模型名/用途/成败），行数可控（最多 days×模型×用途，30 天量级几百行），再做后端二次聚合出 `byDay / byModel / byLabel / total(含失败率)`。模型名与用途均从 `target` 解析，无需新增字段。
- **前端视图**：新增「成本看板」Tab，含 ① 区间选择（7/30/90 天，切换即 `loadCost` 重新拉取）+ 可编辑单价（¥/千 token，默认 0.012）；② 四个概览卡（Token 总量 / 调用次数 / 估算花费 / 失败率，失败率 >5% 标红）；③ 每日 Token 趋势（`MiniChart` 复用）；④ 按模型分布 + 按用途分布双表（含 Token / 调用 / 占比 / 估算金额）。金额 = 总 token ÷ 1000 × 单价，实时随单价输入变化。
- **收益**：管理员第一次能看清「钱花在哪、哪个模型/哪种用途最贵、失败率是否异常」，直接支撑选型与限流决策；全路径 token 数据至此形成闭环（O12 采集 → O16 可视化）。
- **边界**：
  - 估算金额**未区分输入/输出 token**（O12 只落 `usage.totalTokens`），单价是单一估算值，UI 已标注「仅供参考」；真实阶梯计价需后续按模型配输入/输出单价。
  - 单价存前端 state（非持久化），每次进 Tab 恢复默认 0.012；如需团队统一口径，后续可落 `settings` 表。
  - 统计口径是「真实 LLM 调用 token」，与「额度/用量」Tab 的 `usage` 表（配额口径，由 `addUsage` 累加）是两套数据：前者看实际花钱，后者看配额占用，二者天然不一致属正常。

## 二（续5）· V6.5 权限边界与断连成本治理（✅ 已实施）

> 触发点：V6–V6.4 一直在收性能与可观测，但**从未系统扫过「接口级权限边界」**。本轮按「先证明、再修」的方式全量扫了一遍 `app/api` 的删除/触发/按 id 读取接口，确认 3 处越权 + 1 处跨用户覆盖 + 1 处成本泄漏。以下每条都附带改动前的代码事实，不是推测。

### O17 · 定时任务三条接口的越权修复（安全，最高优先级）
- **证据（改动前代码事实）**：
  - `POST /api/schedules/run`：拿到 `id` 直接 `runSchedule(row)`，**完全没有归属校验**。任意登录用户可凭 id 触发**他人**的定时任务 → 消耗**他人**的模型额度，并按任务配置把结果推送到**他人**的 webhook。
  - `DELETE /api/schedules?id=`：`db.delete(...).where(eq(schedules.id, id))` **之前没有任何 owner 校验**（而同一文件里的 PATCH 反而有），任意登录用户可删除他人任务（典型 IDOR）。
  - `GET /api/schedules/runs?id=`：直接按 `scheduleId` 返回最近 30 条执行历史，**历史里含任务产出的完整正文**（可能是业务数据），同样无归属校验。
- **修复**：三处统一为「归属人 或 管理员」口径；`runs` 的读取放宽到与 `GET /api/schedules` 相同的可见性（owner / admin / team / 可访问项目），与既有 PATCH 的鉴权语义保持一致，不引入新概念。
- **收益**：堵住一条完整的越权链（读历史 → 触发执行 → 删除痕迹）。

### O18 · 客户端断连即中止上游 LLM（成本 + 资源）
- **证据**：`streamText` 只配了 `abortSignal: AbortSignal.timeout(120_000)`。用户关页面 / 点停止后 HTTP 请求已取消，但上游流仍被消费到底——继续计费、继续写库；且客户端断开后 `controller.enqueue` 会抛错，把「保存半截回答 + 记录用量」的收尾逻辑一起打断。
- **修复**：
  - 新增 `abortOnDisconnect(req.signal, timeoutMs)`，把「客户端断连」与「超时」两个中止源合并成单一 signal（手写 AbortController 合并，不依赖 `AbortSignal.any`，兼容低版本 Node）；流式与收尾合成两处都接上。
  - 断连后所有推送统一走 `send()` 包装（`clientGone` 标记 + try/catch），enqueue 不再抛错；`ReadableStream` 补 `cancel()` 钩子。
  - 收尾取值改为安全版本，上游被中止时不再整段抛错吞掉落库。
- **收益**：用户离开后 token 立刻停止消耗；已生成的部分回答仍会落库、用量仍会记账（花了钱就要记账），不再出现「断连把收尾整段打挂」。

### O19 · 能力调用入口补限流（防打爆下游）
- **证据**：`/api/chat` 有 40/60s、docs/ppt 有 20/60s 限流，唯独 `POST /api/capabilities/invoke` **一行限流都没有**——而它才是最贵的入口：每次调用都会真实打到下游连接器（外部额度、写入副作用）。
- **修复**：`checkRateLimit('ratelimit:invoke:' + userId, 60, 60)`，超限返回 429。
- **边界**：60/分钟是「手工调用 + 页面操作」的经验值；若有脚本化/批量调用场景，应按 userId 维度单独放宽，或改为按能力配额。

### O20 · 反馈去重按「消息 + 用户」收敛（跨用户覆盖）
- **证据**：`POST /api/chat/feedback` 先 `delete where messageId = ?` 再插入，**只按 messageId 删**。共享会话中 B 点踩同一条消息，会直接删掉 A 已提交的反馈。
- **修复**：删除条件改为 `and(messageId, userId)`，每个用户对同一消息各留一条最新反馈，互不覆盖。
- **边界**：同一用户重复反馈仍是「后写覆盖前写」（预期行为）。

## 二（续6）· V6.6 安全加固（✅ 已实施，收掉 §五 留下的 ④⑤⑥⑦）

> 这一轮补的是「**凭据与浏览器侧的防护**」，不是功能。四项里有三项是**沉默的风险**：平时完全看不出问题，直到库被拖走、页面被内嵌、下游挂掉才暴露。

### O21 · 会话 Cookie 加 Secure + API 层 CSRF 校验 + 弱密钥启动告警（④）
- **证据**：`setAuthCookie` 只设了 `httpOnly` / `sameSite: 'lax'`，**没有 `secure`**——HTTPS 采集点上 Cookie 仍可能经明文 HTTP 泄漏；全站**没有任何 CSRF 校验**，只靠 SameSite=Lax 单层防护；`APP_SECRET` 缺失时静默回退到 `dev-insecure-secret-change-me`（等于签名密钥公开 + 凭据可解密），且**无任何提示**。
- **修复**：
  - Cookie 增加 `secure`，生产环境默认开启；内网纯 HTTP 部署可用 `COOKIE_SECURE=0` 显式关闭（否则会「登录后立刻掉线」）。
  - `middleware.ts` 新增 API 分支做 CSRF：状态变更请求（非 GET/HEAD/OPTIONS）先看 `Sec-Fetch-Site`（浏览器强制写入、脚本无法伪造），只放行 `same-origin` / `none`；无该头时回退 `Origin` vs `Host` 比对，并支持 `APP_ORIGINS` 白名单兼容反向代理改写 Host；无 `Origin` 的服务端互调放行。API 分支只做 CSRF，不做页面跳转（否则前端拿到 302 而非 JSON）。
  - `APP_SECRET` 缺失时在生产环境启动打印安全告警（**只告警不抛错**，避免老部署升级即白屏；构建期跳过以免污染 build 日志）。
- **收益**：CSRF 从「单靠 SameSite」变成「SameSite + Fetch Metadata + Origin 校验」三层；凭据不再走明文通道；弱密钥部署不再静默。

### O22 · 全站安全响应头（⑤）
- **证据**：`next.config.mjs` 只配了编译相关项，**没有任何安全响应头**——可被第三方页面 iframe 内嵌（点击劫持）、可被 MIME 嗅探、Referrer 会把分享链接里的 token 带到外站。
- **修复**：`headers()` 全站注入 CSP + `X-Frame-Options: DENY` + `X-Content-Type-Options: nosniff` + `Referrer-Policy: strict-origin-when-cross-origin` + `Permissions-Policy`（camera / geolocation / payment / usb）+ `X-DNS-Prefetch-Control: off`。
- **取舍（如实说明）**：
  - CSP 的 `script-src` 与 `style-src` 保留 `'unsafe-inline'`（Next 内联启动脚本 + antd 运行时内联样式），因此**不具备 nonce 级严格性**；它的实际价值是拦住「加载外部脚本」「`object` 嵌入」「`base` 标签劫持」「表单外发」四类高危路径。
  - `connect-src` 在开发态额外放行 `ws: wss:`（HMR 需要），生产态只放行同源。
  - `Permissions-Policy` **刻意不限制 microphone**——对话页用了 Web Speech API 语音输入，限制后会直接失效。

### O23 · 连接器配置加密存储（⑥）
- **证据**：`app/api/connectors/route.ts` 的 `config: JSON.stringify(p.config)` 把连接器配置**以明文 JSON 落库**，而这里通常存着 `Authorization` / API Key / 数据库连接串。DB 备份、只读账号、日志转储任一环节泄漏，就是第三方凭据泄露（模型 Key 早已加密，连接器这条路径被漏掉了）。
- **修复**：
  - `lib/crypto.ts` 新增 `encryptJson` / `decryptJson`（复用既有 AES-256-GCM）。
  - 写入侧全部改密文：`connectors` 的新增/修改、`connectors/confirm` 的两处写入。
  - 读取侧统一走解密，**共 7 处**：`lib/tools.ts`（引擎直连）、`lib/capabilities.ts`（能力网关）、`lib/connectors/service.ts`（健康检查）、`connectors/test`、`refresh/preview`、`refresh/apply`、`connectors/confirm`、`chat` 路由的连接器清单。
  - `decryptJson` 兼容三种状态：密文 / 历史明文 JSON / 脏数据，**老库无需数据迁移**，下次写回时自动转密文。
- **风险点（本轮最容易被忽略的一处）**：`lib/capabilities.ts` 用的是 `safeJson(conn?.config)`（变量名不同），若漏改，配置一加密就解析失败 → 能力网关全部报「baseUrl 为空」。已逐个 grep 确认无遗漏（`grep -rn "\.config\b" lib` 仅剩已改的三处）。
- **边界**：密钥由 `APP_SECRET` 派生，**变更 APP_SECRET 会导致既有连接器配置无法解密**（表现为配置读成空对象），此时需重新填写连接器配置——已写进 `.env.example` 注释。

### O24 · 连接器熔断（⑦）
- **证据**：V6.3 的超时只解决「单次调用不会无限挂死」。下游持续 5xx / 拒绝连接时，**每次调用仍要白等一个完整超时**（引擎直连 15s、能力网关默认 30s），并把错误逐个抛给用户。
- **修复**：新增 `lib/resilience.ts`（进程内熔断）：连续失败 5 次后打开 30s，期间 `guardCircuit` 直接快速失败并返回可读中文提示；冷却期满自动半开放行，一次成功即清零。接入能力网关（`callCapability`）与引擎直连（`callConnector` 的 http 分支）。
- **口径（避免误伤）**：只有「抛异常」或「**5xx**」才算失败；**4xx 计为成功**——4xx 说明下游活着，只是我们请求不对，不该触发熔断。管理员改连接器配置、或手动「测试连接」时会主动 `resetCircuit`，保证改完立刻可重试。
- **边界**：进程内状态（多 Pod 各自计数）；阈值与冷却期是经验值，症状长期化应下调阈值或接入指标告警。

## 二（续7）· V6.7 列表接口与统计口径收尾（✅ 已实施）

> 触发问题：前六轮主要盯「对话热路径」和「安全」，**列表/统计接口**只用「看代码有没有明显毛病」的方式扫过，没系统核对过。本轮逐条核对后，发现 3 个功能性错误 + 4 处同类全表扫描。功能错误比性能问题更该先修。

### O25 · `/api/usage` 用量查询漏了 `period`（统计口径错误）
- **证据**：管理员分支 `leftJoin(usage, eq(usage.userId, users.id))` **只按 user_id 关联**，而 `usage` 表是 `(user_id, period)` 一用户一月一行 —— 有 3 个月历史用量的用户会在表格里**重复出现 3 行**；成员分支 `where(eq(usage.userId))` 后再 `limit(1)`，**既没有 period 也没有排序**，可能把上个月的用量当成当月返回。
- **修复**：管理员分支 join 条件补 `eq(usage.period, period)`；成员分支补 period 过滤并把两个查询并行。
- **收益**：用量表恢复「一人一行、当月口径」，避免管理员看到的额度占用是错的。

### O26 · `/api/usage/trend` 把区间内所有消息行拉进内存再聚合
- **证据**：`select({ts, tokens, modelId}).from(messages).innerJoin(conversations)` 后，在 JS 里按天累加。**管理员看 90 天 = 全站这 90 天的每一条消息**都进内存。
- **修复**：改为 SQL 侧 `GROUP BY to_char(created_at → UTC 日期), model_id` + `sum(tokens)`，行数被「天数 × 模型数」封顶；日期口径沿用 UTC，与原来的 `toISOString().slice(0,10)` 完全一致，**前端展示不变**。

### O27 · `/api/brief` 的 N+1 与「失败任务取错」
- **证据 1（N+1）**：`for (const c of convs)` 里逐会话查「最后一条助手消息」，5 个会话 = 5 次往返。
- **证据 2（功能错误）**：失败任务原本是「先取**全局**最近 5 条失败运行，再按我的任务名过滤」。别人任务连续失败时，**我自己的失败会被挤出 Top5**，简报直接漏报。
- **修复**：N+1 改为一条 `SELECT DISTINCT ON (conversation_id) ... ORDER BY conversation_id, created_at DESC`；失败任务改为 `schedule_runs INNER JOIN schedules` 并**在 SQL 里**限定 `owner = 我 OR scope = team`。同时把 6 个彼此独立的素材查询合并成一次 `Promise.all`。
- **收益**：简报接口从 6+N 次串行往返收敛为 1 轮并行 + 1 条聚合查询，且不再受他人任务干扰。

### O28 · 三处列表接口的全表加载 + 缺失索引
- **证据**：`/api/artifacts` 把**整张 artifacts** 拉进内存过滤，又为拿 `ownerName` **拉整张 users** 建 Map；`/api/files` GET 把该用户全部文件拉进内存再按 `conversationId` filter；`/api/files` POST 的配额校验把该用户全部文件行拉进内存 `reduce` 求和。schema 里也缺 `files(project_id)` 与 `artifacts` 的 owner/project/conversation 索引。
- **修复**：artifacts 的可见性与 `type/projectId/conversationId` 过滤**全部下推 SQL**，`ownerName` 改用 `leftJoin users` 一次带出（并加 `limit(500)` 护栏）；files GET 下推 `conversationId`、只 select 列表需要的列；files POST 配额改用 `coalesce(sum(size),0)`。补 4 个索引：`idx_files_project`、`idx_artifacts_owner`、`idx_artifacts_project`、`idx_artifacts_conversation`。
- **顺带（安全）**：`POST /api/files` 的 `projectId` / `conversationId` 原来是**客户端表单直接信任**的 —— 任何登录用户都能把文件「塞进」别人的项目文件列表或别人的会话（越权注入 + 污染他人项目视图）。现在 `projectId` 走 `canAccessProject` 校验、`conversationId` 必须是自己的会话；`scope` 改由 `projectId` 推导，不再接受客户端随意指定；另加 100MB 单文件上限（上传是整块读进内存，无上限等于留了个 OOM 入口）。
- **顺带（去重）**：`rowsOf()` 原本在 `capabilities/metrics` 与 `knowledge/.../reindex` 各抄了一份，本轮抽到 `lib/sql.ts`，三处复用。

> ① **性能**：全表扫描 / 重复查表 / 串行等待 / N+1 / 日志·检索无上限 / 缓存陈旧；
> ② **可观测**：埋点缺口（成功路径不落库）、真实 token 未采集、采集了不可视；
> ③ **安全与韧性**：定时任务三条越权、能力调用无限流、断连后仍烧 token、反馈跨用户覆盖、Cookie 无 Secure / 无 CSRF、无安全响应头、连接器凭据明文落库、下游持续故障无熔断、文件可被注入他人项目/会话；
> ④ **统计口径正确性**：用量查询漏 `period` 导致重复行/串月、简报失败任务被他人任务挤出 Top5。
