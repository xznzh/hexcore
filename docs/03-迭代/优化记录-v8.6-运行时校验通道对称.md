# 优化记录 · v8.6 运行时校验的通道对称

> v8.3 修的是「拦」，v8.4 修的是「拦得对不对」，v8.5 补的是「该拦的没拦」。
> 这一轮补的是**「看」**：同一个校验器，四条通道里只有一条在用。

## 1. 缺口的确切形状

`verifyAnswer`（运行时 V 层，确定性后校验）从 v8.3 起就存在，调用点只有一个：

```
app/api/chat/route.ts:1071   const vr = verifyAnswer({ answer: finalText, sources: sourcesList, trace });
```

| 通道 | 出口护栏（v8.3） | 运行时 V 层（本轮前） |
|---|---|---|
| 对话 `chat` | ✅ 流式机 + `verifyAnswer` | ✅ |
| 技能 `skills/run` | ✅ `finalizeChannel`（v8.4 补上下文） | ❌ |
| 定时任务 `scheduler` | ✅ `finalizeChannel`（v8.4 补上下文） | ❌ |

这是 v8.3 系列同一模式的**第四次**出现：机制存在，只装在一条路上。
前三次是 `kb-access`（检索范围）、`quota`（额度）、MCP 审批；这次是运行时校验。

为什么这条比前几条更容易被忽略：它的**缺失没有任何症状**。
护栏缺失会有用户投诉（产出被截断、或越权内容被发出去）；校验缺失只是「日志里少一类行」，
没有任何人会去查「应该有的那类行为什么没有」。

## 2. 为什么不是加一行 `verifyAnswer({ answer })` 就完事

这是本轮唯一真正的设计问题。校验器的入参是 `{ answer, sources, trace }`，
其中两条规则依赖的输入，在非对话通道里**形状完全不同**：

| 规则 | 需要什么 | 对话通道给的 | 技能通道本来有什么 |
|---|---|---|---|
| `ungrounded_capability` | `trace` 里 `type === 'tool_call' && name` 匹配 `invoke_capability`/`call_connector` | `{ type:'tool_call', name:'invoke_capability' }` | `{ type:'tool', tool:'invoke_capability', output }` |
| `fabricated_source` | `sources.length > 0` | `hits.map(h => h.source)`（文件名列表） | 只有 tool 节点的产出，没有 hits |

直接把技能轨迹塞进去会得到两个后果，**都不会报错**：

1. `type` 不是 `tool_call`、工具名在 `tool` 而不是 `name` → 这条规则对**每一次**
   声称「已使用能力」的回答报警。100% 误报。
2. `sources` 恒为空 → 只要回答里出现 `📚 **参考来源**`，就会被判成编造来源。

这正是 v8.4 那个教训的第二次出现：**空上下文不是「能力弱一点」，而是主动误伤**。
所以本轮不做「在每个调用点补参数」，而是建一个适配层 `lib/agent/channel-verify.ts`，
让「校验器该收到什么形状」只有一份答案。

### 2.1 `sources` 必须保留三态，不能看 `length`

```ts
// 正确
const sources = input.sources === undefined ? deriveSources(trajectory) : (input.sources || []).filter(Boolean);

// 错误（会悄悄放过真问题）
const sources = (input.sources || []).length ? input.sources : deriveSources(trajectory);
```

`undefined` = 通道没给来源信息 → 从工具产出推导。
`[]` = 通道明确表示「本轮没有来源」→ 就用空，此时列出参考来源才是编造。
写成 `length ? … : …`，空数组会被当成「没传」，于是「没检索却列了来源」这个**本该被抓的**
情况被静默放过。

这就是 `retrieve()`（v8.3 · R6）的同一个陷阱：**用「有没有内容」代替「有没有传」**。
本轮把它写进测试（`sources 传空数组 = 「确实没有来源」，不得回退到轨迹推导`），
并且做了反向验证。

### 2.2 V 层跑在护栏**之后**

顺序不能反。放在护栏之前，校验的是「已经不会外发的草稿」——护栏截断后的合规文本没被看过，
而被丢掉的部分反而会被记成模型的过错，日志会把护栏的功劳算成模型的错误。

### 2.3 仍然不拦截

与对话通道一致：V 层是观测层，判错就改写交付物是把风险放大。
真正决定「发不发」的是 `finalizeChannel`。技能通道已经有拦截，这里只加观测。

## 3. 改动清单

| 文件 | 改动 |
|---|---|
| `lib/agent/channel-verify.ts` | **新建**：`verifyChannelAnswer`（纯函数，轨迹归一 + 来源三态）、`recordChannelVerify`（旁路记账，动态 import `util` 以免把 DB 依赖传染给纯函数）、`auditChannelAnswer`（体检 + 记账合体，调用点首选） |
| `lib/scheduler.ts` | 把 `toolOutputs` 变量换成整条 `trajectory`，护栏与 V 层共用一份来源；护栏后调用 `auditChannelAnswer` |
| `app/api/skills/run/route.ts` | `guardRun` 内、`finalizeChannel` 之后调用 `auditChannelAnswer`（同一函数覆盖「全新运行」与「恢复续跑」两条路径） |
| `app/api/chat/route.ts` | 改走 `verifyChannelAnswer`。对本通道是**恒等翻译**（trace 已是 `tool_call` 形态、sources 显式给出），行为不变；统一的目的见下 |
| `tests/channel-verify.test.ts` | 新增 12 条：轨迹归一两形态、来源三态、空产出、记账口径 |
| `tests/scheduler-guard.test.ts` | 新增 3 条：空产出记 fail、无据的能力声明记 warn、**真有工具时不误报** |
| `tests/skills-routes-wiring.test.ts` | 新增 2 条：同上（技能路由侧） |
| `tests/source-guards.test.ts` | 新增源码守卫：`app/`、`lib/` 禁止直接调用 `verifyAnswer`（`runtime-verify.ts`、`channel-verify.ts` 除外） |

### 为什么连 chat 也改

chat 原本的写法是对的。改它不是为了修 bug，而是为了**让源码守卫可以没有例外**：
只要允许「有些通道直接调 `verifyAnswer`」，下一条新通道就会照抄 chat 的那一行，
而它没有 chat 的输入形状。守卫里留一个豁免，等于给复发留一个合法入口。
这与 v8.4 把 `finalizeChannel` 定成唯一出口是同一个理由。

## 5. 行为变更

1. **`operation_logs` 会多出 `eval_runtime` 行**，`target` 取值为 `pass_with_warn` / `fail`，
   `detail` 以 `channel · <通道>/<标签>` 开头。排查时按这个前缀与对话通道区分。
2. **只在有问题时记录**，与对话通道口径一致；pass 不写，避免把有效信号淹掉。
   所以「查不到某次任务的 `eval_runtime`」= 那次没问题，不是没跑。
3. **不拦截**。定时任务的通知标题不会因为这个变化：「已按安全策略处理」仍然只来自
   `finalizeChannel` 的拦截（v8.4）。
