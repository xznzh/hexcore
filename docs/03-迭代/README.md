# 迭代记录（首发前的开发过程）

> **版本口径先对齐**：这一层里的 `v2` ~ `v8.22` 是**公开首发前的内部迭代编号**，
> 用来区分「这一轮在解决什么问题」，不是对外发布版本。
> 对外发布从 [`v1.0.0`](../../CHANGELOG.md) 起算——它是上面所有迭代收口后的快照。
> 两套编号不要对照着看高低，看得是「问题从哪来、怎么验证、留下了什么」。

## 为什么保留这些过程记录

1. **决策留痕**：每一轮都写清「缺口的确切形状 → 为什么这么改 → 怎么验证 → 怎么回滚」，
   半年后回看不需要靠记忆复原。
2. **可复盘**：包括判断失误的轮次（比如把「缺口有界」判错、后来在同一处复发），
   成功的那半和失败的那半都留着，否则复盘只会变成自我表扬。
3. **可迁移**：换语言重写（见 [`../02-设计/Agent技术地图-Java版.md`](../02-设计/Agent技术地图-Java版.md)）时，
   真正要带走的是这些取舍理由，不是代码。

## 与 `designs/` 的分工

[`../../designs/`](../../designs) 放的是**面向未来的架构提案**（还没实现、或只实现了一部分），
这一层放的是**已经发生的改动**。提案里被采纳的部分，实施后会在这里留一条对应记录。

## 维护约定

- 新的一轮迭代**新增一篇**，不改写旧篇；判断错了就在新篇里说明「上一次错在哪」，保留原判断原文。
- 篇名格式：`优化记录-vX.Y-<主题>.md`（内部迭代号，与对外 tag 无关）。
- 对外发布时，用户可见的变化写进 [`CHANGELOG.md`](../../CHANGELOG.md)；这里只写过程。
