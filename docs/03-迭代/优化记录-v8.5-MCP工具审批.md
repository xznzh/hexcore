# 优化记录 · v8.5 MCP 工具审批

> v8.3 / v8.4 连着两轮把「MCP 审批未接」写进已知取舍。这一轮把它接上，并且刻意**不新建表、不新建页面**。

## 1. 缺口的确切形状

平台里有两类「工具」，语义却不一样：

| | 注册表工具（`lib/tools/registry.ts`） | MCP 工具（`lib/tools/mcp-tools.ts`） |
|---|---|---|
| 来源 | 我们自己写的 `ToolDef` | 第三方 MCP 服务 listTools 返回 |
| 描述与参数 schema | 我们控制 | **第三方控制**（tool poisoning 的载体） |
| 审批 | `requiresApproval` → 落 `pending_approval` → 管理员放行 → 按原参数执行 | **没有** |
| 权限 | `permission: admin/member/guest` 卡住 | 只按连接器 `visibleRoles` 过滤 |

也就是说：一个成员在对话里让模型调 `filesystem:write_file`，只要该 MCP 连接器对他可见，
就会**直接执行**——没有审批、没有二次确认，模型想调就调。

这不是「少写了一个功能」，而是 v8.3 系列同一模式的第三次出现：**机制存在，只装在一条路上**。
前两次是 `kb-access`（检索范围）与 `quota`（额度）；这次的机制是 `invokeRegisteredTool` 里的审批闸。

## 2. 设计取舍

### 2.1 复用 `capability_operations`，不新建表

审批的价值有一半在「只有一个收件箱」。管理员已经习惯在「能力 · 待审批」处理请求，
再开一张表就是两个页面、两套状态机、两份审计口径。

落库形态与注册表工具**完全同构**，只是多带一个 `mcp` 字段：

```json
{
  "tool": "mcp__demo__create_issue",
  "args": { "title": "服务挂了" },
  "mcp": { "connectorId": "conn_xxx", "toolName": "create_issue" }
}
```

为什么 `mcp` 里要单存 `toolName`：命名空间键 `mcp__<连接器>__<工具>` 是**不可逆**的
（连接器名与工具名都被 `sanitizeToolName` 净化并截断过），审批后要拿原始工具名去调远端，
只能在一开始就存下来。

### 2.2 一个执行函数，两个入口

免审批执行与「审批通过后补执行」最终都调 `executeMcpTool(connectorId, toolName, args, ctx)`。

这不是为了省代码：**审批检查在 A、真实执行在 B 是最典型的漏洞形态**。两份实现迟早漂移，
而漂移的那一侧通常是没有审计的那一侧。现在连远端、脱敏、定界、审计都只有一份。

`executeMcpTool` 按 id **现查**连接器，不用工具装配时缓存的行——审批可能几分钟后才通过，
期间管理员可能改了地址或禁用了连接器，那就该拒绝执行而不是拿旧配置连出去。

### 2.3 策略按连接器配，不搞全局开关

`connectors.mcp_approval`：`auto`（默认）| `always` | `never`。

| 值 | 行为 |
|---|---|
| `auto` | 写语义工具 → 审批；读语义工具 → 放行；**认不出来的工具 → 审批**；管理员豁免 |
| `always` | 该连接器所有工具都要审批，**管理员也不例外**（给能重启机器、能写库的服务用） |
| `never` | 不审批（确认无副作用时） |

判定顺序是**先查写、再查读**：`get_or_create_user`、`search_and_delete` 这类复合名
只做前缀判断会被整个放过。写动词集合见 `lib/mcp/approval.ts` 的 `WRITE_VERBS`。

「认不出来就审批」是刻意的 fail-closed。理由很实际：工具名是第三方起的，
猜错一个词的代价是**多一次点击**，猜反的代价是**静默执行了一次写操作**。
觉得吵的话，正确的降级动作是给这个连接器设 `never`，而不是把判定改成「猜不到就当读」。

`auto` 下管理员豁免，与注册表 `requiresApproval` 的既有语义保持一致；
确实想让管理员也被拦住，用 `always`——这是一个**显式声明**，不是默认行为。

### 2.4 入参过大就拒绝，而不是截断

审批后要「按原参数执行」，所以参数必须完整保存。超过 16000 字符的入参不落库，
直接回一句「本次入参过大，请缩小范围后重试」。

对比另一种做法——截断后落库：审批人看到的是一份被切过的参数，点通过后执行的是另一件事。
**审批的价值建立在「你批的就是要跑的那一份」上**，截断会把这条前提悄悄废掉。

## 5. 行为变更（需要知道的三点）

1. **成员侧的 MCP 写操作会开始要审批**。`auto` 是默认值，老连接器升级后立即生效。
   如果你的团队里成员用 MCP 只做检索，这不会带来任何点击。
2. **审批后结果不回灌对话**。与管理员的既有审批语义一致：放行后按原参数执行，
   结果落在「能力 · 调用记录」；那一轮对话里模型只看到「已提交审批」。
   要让结果回到对话，需要给会话加「待审批回合恢复」，属于另一件事。
3. **`always` 会拦住管理员自己**。这是刻意的——它是「我也要审」的显式声明。

## 6. 仍未闭环

1. **没有「记住这个工具的选择」**。每次写操作都要重新审批，对高频场景偏吵。
   方向是按 `connector + toolName` 落一条 grant（`capabilityGrants` 已有 scope 概念），
   让「管理员批过一次的工具」在有效期内免审。本轮没做，因为要先定过期与撤销语义。
2. **审批不可批量**。多个写工具被模型连续调用时会生成多条待审批，管理员只能逐条点。
3. **仅对话通道生效**。技能节点目前明确不支持 MCP 连接器（`executor.ts` 里直接返回提示），
   所以没有第二条通道要接；等哪天技能支持 MCP，这里必须一起改——这正是 v8.3~v8.5 反复踩的坑。
4. **`verifyAnswer` 仍未接非对话通道**（沿用 v8.4 §5 第 1 条）。
   > **v8.6 已接**：新增 `lib/agent/channel-verify.ts` 做轨迹/来源适配，
   > 技能与定时任务两条通道均已接入。详见
   > [`优化记录-v8.6-运行时校验通道对称.md`](优化记录-v8.6-运行时校验通道对称.md)。
