# 优化记录 · v8.4 护栏上下文与无人值守语义

> 承接 v8.3 的两条「已知取舍」。这一轮不加新功能，只修**同一套机制在部分入口上装错了参数**的问题。

## 1. 这一轮是从哪来的

v8.3 的临别清单里有两条挂在「已知取舍」下：

1. 非对话通道的语境类规则不生效，且「未核实引用」**没有允许名单可比对** → 定时简报里出现《XX 报告》会被判成编造而截断；
   当时的备选处理路径写着「若误伤明显，`CHANNEL_GUARD=off` 应急；或给该通道传入 `allowedCitations`」。
2. 技能在定时通道被墙钟/预算中断时的行为没人核对过。

第 1 条其实是**记错了严重性**：它写的像是「护栏弱一点」，实际是「护栏反过来咬自己人」。
第 2 条一查就是个真 bug。下面分别记。

## 2. 四条改动

### 2.1 P0 · 引用误伤：空 `GuardContext` 不是「少拦」，是「主动掐掉合规输出」

**症状**：技能或定时任务检索到了文档，模型照着文档写「按《2025 年度运营报告》，留存率 42%」，
产出从引用处被截断，替换成「本轮回答涉及未经核实的报告名称」。

**根因**：`detectUnsafeAnswer(text)` 不传 ctx 时，`allowedCitations` 为空集，而
「未核实引用」属于**无条件规则**（`unverified_citation`），它不依赖 `risk`，照样跑。
于是「源材料里明明有这个名字」和「模型凭空编一个」得到同一个判定。
对话通道一直传 `allowedCitations: hits.flatMap(h => extractCitations(h.content))`，
技能/调度通道从来没传——**这不是能力差异，是参数漏传**。

**修法**（`lib/agent/answer-guard.ts`）：

| 新增 | 作用 |
|---|---|
| `toolOutputsOf(trajectory)` | 只取 `type === 'tool'` 的节点产出。**模型自己的输出不构成出处**——把 llm 节点也算进去等于让答案自证清白 |
| `buildChannelContext({ question, toolOutputs, history })` | 由通道自身数据构建 `GuardContext`：可引用名来自工具产出，语境风险来自触发执行的原始指令 |
| `finalizeChannel(text, audit)` | 把「建上下文 + 判定 + 审计」收成一次调用，作为对外通道的**唯一出口** |

接入点：

| 文件 | 传入的上下文 |
|---|---|
| `app/api/skills/run/route.ts`（全新运行 / 恢复续跑两条路径） | `question` = 运行输入；`toolOutputs` = 本次轨迹的 tool 产出 |
| `lib/scheduler.ts`（技能型任务） | `question` = 任务 prompt；`toolOutputs` = 技能轨迹的 tool 产出 |

口径校验：引用名仍要在**源材料**里出现才算有据。测试里 `无据的引用仍然被拦` 一条专门守着这点，
避免把「有上下文」做成「随便引用都放行」。

### 2.2 P0 · 中断语义：定时通道把「被掐断」报成了「完成」

**症状**：技能型定时任务被 120s 墙钟（或 token 预算）中断时，站内通知标题是「定时任务完成」，
正文是半句话，`schedule_runs.status` 是 `ok`。

**根因**：`runSchedule` 里写的是 `const { result } = await runSkill(...)`——
解构丢掉了 `aborted` / `abortReason`。而 `skills/run` 路由对同样的情况有完整分支（429 + `aborted` 字段）。
**同一套语义只装在一条通道上**，是 v8.3 R 系列的同一个模式，只是这次落在返回值解构上。

**修法**：`lib/scheduler.ts` 捕获 `aborted` →

- `status = 'error'`、`error = abortReason`；
- 站内通知标题改为「定时任务**中断**：…」，正文给中断原因；
- `recordRun` **保留部分产出**（与 `skills/run` 一致：中断 ≠ 失败，用户可能还要那半截）；
- webhook payload 增加 `aborted: true`，调用方不必靠猜 `status` 区分「没跑完」和「跑失败」。

为什么这条在无人值守通道里更严重：对话通道中断时用户当场就知道；
定时任务把失败报成成功，用户不会去查执行历史，只会认为「这个任务一直没内容」。

### 2.3 P1 · `CHANNEL_GUARD=off` 从「静默放行」改成「观察模式」

原实现：

```ts
if (!channelGuardEnabled()) return { text: s, blocked: false };  // 连检测都不做
```

而文档写的是「只记录不拦截」。**记录在哪？没有。** 一个应急开关同时关掉了拦截和观测，
开关开过多久、期间放行了什么，事后完全查不到。

现在：命中仍判定、仍落 `guardrail_output_block` 审计（`status: 'warn'`、detail 前缀 `observe ·`），
只是不截断，返回值多一个 `wouldBlock: true`。开关的语义从「关掉护栏」变成「切到观察模式」，
误伤率与启用时长都变成可查的事实。

### 2.4 P1 · 拦截不再隐形

`skills/run` 的响应体在被拦时多一个字段：

```json
{ "result": "……（已替换的合规话术）", "guard": { "blocked": true, "rule": "unverified_citation" } }
```

定时任务的站内通知标题带「（部分内容已按安全策略处理）」。此前拦截只写在 `operation_logs` 里，
前端与 webhook 调用方都看不到——**用户会把截断当成模型能力问题**。
UI 侧的提示文案本轮未动（只补接口字段），界面改动要另走界面规范评审。

### 2.5 源码级守卫

`tests/source-guards.test.ts` 新增一条：`app/` 与 `lib/`（除 `answer-guard.ts` 自身）**禁止直接调用 `finalizeAnswer`**。

理由是 R6 的教训：*默认值站在错误一侧时，修调用点只是把复发推给下一个人*。
只要还允许调用方自己拼 context，就一定会有新入口漏传 `toolOutputs`，
然后同一条误伤以「不知道为什么产出被截断」的形式再来一次。把 `finalizeChannel` 定成唯一出口，
下一轮加通道时**不可能**绕过上下文。

## 3. 验证

| 项 | 结果 |
|---|---|
| `npx tsc --noEmit` | 0 错误 |
| `npx vitest run` | **751 通过 / 7 跳过**（新增 15 条：`answer-guard` 7、`scheduler-guard` 5、`skills-routes-wiring` 2、`source-guards` 1） |
| 反向验证 · 上下文 | 把 `finalizeChannel` 的 ctx 临时改回 `{}` → `scheduler-guard` 的「有出处引用不被误伤」「指令参与语境判定」两条**变红** |
| 反向验证 · 中断 | 把 `if (r.aborted)` 改成 `if (false && r.aborted)` → 「报中断」「webhook aborted」两条**变红** |

新增测试文件 `tests/scheduler-guard.test.ts`：调度通道此前**零测试**，
而它是唯一「无人值守 + 直接对外推送」的通道，两条结论（中断语义、护栏标题）都放在这里守。

## 4. 开关与回滚

| 开关 | 默认 | 作用 |
|---|---|---|
| `CHANNEL_GUARD` | 开 | `=off` 切观察模式（仍判定、仍审计、不截断） |

回滚粒度：

- 只想恢复「引用不误伤」之前的严格模式 → 删掉 `buildChannelContext` 里的 `allowedCitations` 即可（不推荐，会重新误伤）；
- 只想恢复旧的中断语义 → 删掉 `lib/scheduler.ts` 的 `if (r.aborted)` 分支；
- 两者都不影响对话通道（chat 走的是 `pushDelta` 流式机，本轮未动）。

## 5. 仍未闭环

1. **`verifyAnswer` 仍只在对话通道**：技能/调度通道没有「引用与来源一致性」核对。本轮补的是
   `output-guard` 的确定性规则，事实核对（`runtime-verify`）还没有对称实现。
   它的产出是「只记录不拦截」，接过去主要是补观测面，可以下一轮单独做。
2. **跨轮语境标记在通道侧偏弱**：非对话通道没有多轮用户历史，`decisionAuthority` 这类
   「用户上一轮施压、这一轮继续」的延续判定，只能看到当前任务指令。
3. **`CHANNEL_GUARD=off` 期间的命中只进日志**，没有告警。长期挂在这一档等于慢速失明，需要时再补阈值告警。
