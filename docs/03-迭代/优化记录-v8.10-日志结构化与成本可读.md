## 2. 日志落成真列

`operation_logs` 新增五列：`trace_id` / `model` / `label` / `ok` / `prompt_tokens` / `completion_tokens`。

### 2.1 为什么 `target` 不能再当机器字段用

它长这样：`${model} | ${label} | OK | ${ms}ms`。成本看板用 `split_part(target,' | ',n)` 反解。
问题不是「不够优雅」，是**错位不报错**：

```
MiniMax | M3.1 | chat | OK | 1200ms     ← 模型名本身带了一个 " | "
→ model = 'MiniMax'
→ label = 'M3.1'
→ ok    = 'chat' → 判成失败
```

成本会安静地记到另一个模型头上，失败率凭空升高，而页面上一切正常。现在结构化字段进真列，
`target` 退回它本来的职责：给人看的一句话摘要。

### 2.2 历史行怎么办

v8.10 之前的行这几列为 `NULL`。**不重写历史**——审计流水只追加是它的核心价值。
读侧用 SQL 表达式回落：`coalesce(nullif(model,''), nullif(split_part(target,' | ',1),''), 'unknown')`。

成败的回落更谨慎：

```sql
coalesce(ok,
  case when target like '% | OK | %'   then true
       when target like '% | FAIL | %' then false
       else null end)
```

判不出来就返回 `NULL`（未知），**不默认成失败**。这一条和 v8.8「不做失败率」是同一个立场：
分母不成立的时候，报表要显示「不知道」，而不是给一个看起来精确的数。

### 2.3 索引

```sql
CREATE INDEX IF NOT EXISTS idx_operation_logs_trace
  ON operation_logs(trace_id, created_at) WHERE trace_id IS NOT NULL;
```

partial 索引：历史行 `trace_id` 全为 `NULL`，建进索引只是白占空间，而等值查询照样命中。
成本看板沿用已有的 `idx_operation_logs_action (action, created_at)`，**没有新增第二个索引**。

## 3. 金额：从「手填单价 × 总 token」到「按配置单价、输入输出分开算」

原来的算法在页面上：

```ts
Math.round((cost.total.tokens / 1000) * pricePer1k * 100) / 100   // pricePer1k 是页面上的输入框
```

三个问题：

1. **后台配的单价没人读**。`models.price_in / price_out` 是管理员在「模型配置」里填的，
   全项目零引用。也就是说管理员改完单价，看板上不会有任何变化——他会以为自己改错了。
2. **输入与输出混着算**。两者的单价差 3–5 倍是常态（输出通常更贵），
   用一个混合单价乘总 token，误差方向取决于输入输出比例，不可控。
3. **它是「估算」但没有标注不确定性**，页面上那个 ¥ 数看起来像真账。

现在：`composeCostReport(rows, prices)` 纯函数按 `models` 表的单价算，
输入用 `price_in`、输出用 `price_out`，单位沿用字段定义（**分 / 千 token**），
金额以「分」返回（避免浮点在累加时漂移），前端只做 `/100`。

### 3.1 三种「算不出来」必须分开说

| 情况 | 处理 | 为什么不能按 0 元算 |
|---|---|---|
| 模型没配单价（`price_in=0 && price_out=0`） | 计入 `unpriced.noPriceTokens` | `0` 是「管理员没填」，不是「免费」 |
| 历史行只有总 token，拆不出输入/输出 | 计入 `unpriced.unsplitTokens` | 按输入价算低估、按输出价算高估，两个都是错的 |
| 拆分只覆盖一部分 | 差额计入未计价，已覆盖部分照常计价 | 重复计费比漏计更难发现 |

页面上「花费(¥)」旁边会挂一个「未计价 N」的灰标，卡片下方补一行合计。
`fullyPriced: false` 的语义是「这个金额不是全部」，不是「有问题」。

### 3.2 顺带修掉一个「单位不一致」

`MULTIPART` 之外还有一处同类问题：`usage` 的字段名。
v3/v4 是 `promptTokens/completionTokens`，v5 改成 `inputTokens/outputTokens`，
读错名不会报错，只会让输入/输出长期为 `null`——金额看起来仍然"有数"（因为 total 还在）。
抽出 `readTokenUsage()` 同时认两套名字，并用单测钉住（§7 反向验证四）。

## 4. 缓存作用域：多轮不共享

`buildCacheKey = model + system + prompt`，**不含对话历史**（历史是以 `messages` 数组另传的）。

```
会话 A：用户问「总结一下」
会话 B：用户问「总结一下」
→ 同一个 key，10 分钟内 B 拿到 A 的答案
```

这不是「命中率偏低」，是**答非所问**，而且静默——看起来只是模型理解错了上下文。
短问题（「继续」「那第二点呢」「详细说说」）最容易撞。

两个修法：

| 方案 | 代价 |
|---|---|
| 把历史摘要 hash 进 key | 每轮历史都在变 → 缓存基本不再命中，等于关掉 |
| **只在首轮启用**（选这个） | 命中率降一些，但每次命中都是「同一问题的首次提问」 |

语义缓存省的是「同一问题被反复问」的钱，而反复问通常发生在首轮（FAQ、同一批人问同一件事）。
多轮里的重复提问本来就带着上文，语料已不相同，缓存它属于用一个错的答案换一点钱。

判定抽成 `cacheDecision()` 并返回 `reason`：

```ts
{ eligible: false, reason: 'multi_turn' | 'capability_bound' | 'volatile_question' }
```

返回原因而不是布尔，是为了能回答「这轮为什么没走缓存」——布尔回答不了，而这个问题会被问。
优先级固定为 **能力 > 多轮 > 实时问题**，并有用例钉住顺序。

## 5. 上传上限：判定搬到读入之前（只做了一半）

原顺序：`formData()` → `arrayBuffer()` → 判 `size > 100MB`。
也就是说 **100MB 的上限并没有阻止 100MB 被读进内存**，它唯一的作用是把 500 变成 413。
两个前置闸门：

1. `Content-Length`（便宜，但分块上传没有这个头）
2. `File.size`（multipart 解析后就有，不必先 `arrayBuffer`）

必须两个都做：只做 1 会被 chunked 上传绕过，只做 2 则已经吃完了整包内存。

**这仍然不是流式上传**。真正的解法是用 `req.body` 流式写盘 + 边写边累加校验，
需要自己解析 multipart（现有依赖里没有流式解析库）。本轮做的是「把上限变成真的上限」，
把峰值从 3 份缓冲压到 1 份，最坏情况下的 OOM 风险下降但没有消失。已列入 §8。

## 9. 一句话总结

前几轮修的都是「错了会报错」的问题；这一轮修的是**「错了不会报错」**的问题——
字段错位、单位错、字段名对不上、字符串当结构用、上限写在读完之后。
它们的共同点是：页面上永远显示得通，只有对着数字算一遍才知道不对。
