## AI 内核升级记录（v2 · 对标生产级 Agent 平台）

本次升级聚焦"AI 内核深度"与"工程韧性"，覆盖 P0–P2：

**P0 · 存储与检索**
- `lib/db.ts`：自动 `CREATE EXTENSION vector` + `chunks.embedding_vec vector(EMBED_DIM)` 列（默认 384，可用环境变量调整），带可用性探针；检索优先走数据库向量索引，无向量能力时降级。
- `lib/ai/rag.ts`：`retrieve()` 优先向量 SQL 检索（`ORDER BY embedding_vec <=> $q LIMIT k`，仅单一模型组时），多模型按切片来源分组各算查询向量，候选经混合重排；语义分块替代固定窗口。
- `lib/queue.ts`：BullMQ Worker **真正计算 embedding 并写入**（此前仅改状态），上传路由改为入库即返回、后台向量化。

**P1 · 对话即 Agent**
- `app/api/chat/route.ts`：接入 **Function Calling**（`search_knowledge` / `read_file` / `run_skill`），对话中可直接查知识库、读文件、跑技能；历史改为 **token 预算裁剪**；引用来源结构化回传；**RAG 注入缓解**（检索内容明确标注为"参考而非指令"）。
- `lib/agent/engine.ts`：多 Agent 引擎重构，结构化 Critic + 重试循环 + 工具步骤。
- `lib/ai/memory.ts`：对话后**自动抽取记忆**并去重入库。

**P2 · 韧性与可观测**
- `lib/llm.ts`：模型调用 **重试退避 + 失败降级模型（failover）** + 耗时/Token 埋点。
- `lib/cache.ts`：语义缓存（Redis，命中直接返回，省 Token）。
- `lib/observability.ts`：LLM 调用日志 + **RAG 评估（recall@k）**（`/api/admin/eval`，管理员）。
- `lib/scheduler.ts`：定时任务可运行**完整技能流水线**。
- 生成设 `maxTokens` 上限；限流分级；引用注入安全隔离。

> 说明：本环境沙箱禁止 `next dev/build`，以上均通过 `tsc --noEmit`（0 错误）验证，请在本机 `pnpm dev` 跑通流程。

## 能力网关记录（P0 · 工具注册表与能力目录）

对标成熟网关产品的「能力网关」思路，补齐可治理的三方能力底座（详见 `docs/03-迭代/能力网关-P0实施记录.md`）：

- **统一工具注册表**（`lib/tools/registry.ts`）：权限 → 审批 → 超时 → 审计；聊天 / API / 技能共用。
- **连接器生命周期**：OpenAPI 发现（只读）→ 确认安装 → 健康检查 → 刷新预览/应用 → 成员授权 → 撤销；无 `specUrl` 时缓存内联文档，未勾选的接口不会在刷新时被重新安装，文档移除的接口只停用不删除。
- **能力目录**（`/capabilities`）：目录、调用、审批、调用记录、指标；管理员跳过审批，普通成员按最低角色 + 可见角色 + 用户/角色白名单放行。
- **参数校验**：按 `input_schema` 轻量校验必填 / 基础类型 / 枚举，API 400 + 错误清单，聊天工具回可读提示；不拒绝 schema 之外字段。
- **长任务异步执行**：`mode:'async'` 先落库再后台执行，返回 202 + `operationId`，前端轮询详情、记录页自动刷新；审批通过后同样支持后台执行（Serverless 多实例建议改 BullMQ Worker）。
- **性能**：调用指标改 SQL `GROUP BY` 聚合 + `created_at` 索引；消息历史 / 工作台接口加 `Server-Timing` 响应头，便于定位慢查询。
- **对话可用**：`/api/chat` 追加 `list_capabilities` / `invoke_capability`，模型可直接发现并调用三方接口（支持 GBK 解码与 extract/pick/limit 响应映射）。
- **审计**：统一写 `operation_logs`，调用明细与耗时落 `capability_operations`。
- **界面**：能力目录支持搜索 / 状态筛选 / 空态引导；调用记录支持状态 + 关键词筛选与服务端分页；待审批可看详情并二次确认；指标支持 7/30/90 天切换与每日趋势柱图（失败标红）；调用抽屉支持格式化 JSON、复制结果、失败重试，抽屉宽度按屏幕自适应。
- 外部依赖仍「未配置优雅降级」；旧库自动建表 + 幂等 `ALTER` 平滑升级。

## 零中间件运行记录（不装 Redis / pgvector / Ollama）

目标：只保留 PostgreSQL 与云端模型 API，其余组件「缺失即降级」，功能不缺项。

- **限流**：`lib/redis.ts` 新增 `MemoryRateLimiter`（滑动窗口 + 自动清理）。无 Redis 或 Redis 抖动时按进程内计数限流，不再直接放行；多实例部署时每实例各算一份。
- **索引队列**：无 Redis 时 `enqueueIndex` 在当前进程后台执行同一套 `indexDocument`，文档状态仍会 `indexing → indexed`；上传接口最多等 3s，避免大文档拖死请求。
- **向量维度可配置**：`EMBED_DIM`（64–4096，默认 384）统一决定 pgvector 列维度、本地降级向量长度与检索守卫。维度变化时启动会重建列、清空旧向量并把文档退回「待索引」，检索不会命中错维向量。
- **重新索引入口**：文档行内「重新索引」清空该文档向量并重新入队（成员可用）；页头「回填缺失向量」扫描全部缺失向量的文档、最多 3 篇并发（仅管理员）。
- **按知识库选择向量模型**：`knowledge_bases.embedding_model` 存模型 id 或 `auto`（历史 `lexical`/空值启动时归一为 `auto`）。索引时按所属库的模型计算，并把实际产出向量的模型写入 `chunks.embedding_model`（`local` 表示本地降级），避免不同模型/维度的向量混算；检索按切片来源模型分组，每组用同一模型算一次查询向量。切换模型会清空该库向量并以 3 并发后台重建。文档行内「重新索引」也可在改模型后单独重算。
- **向量模型失败自动切换**：候选链按「默认模型优先，其余按配置顺序」排列，某个模型调用失败就换下一个，全部失败才用本地哈希向量。失败模型在进程内冷却 5 分钟，避免每次请求都先空等一遍不可达的服务（例如未装 Ollama 时的 `localhost:11434`）。
- **预置模型 Key 从 env 同步**：预置模型首次入库时若 `.env.local` 还没配 Key，会把空 Key 加密写进库，之后补了环境变量也不会更新。现在启动时按 id 比对，只在「库里解密为空」且「env 有值」时补写，不会覆盖后台手填的 Key。
- **MiniMax 向量模型适配**：MiniMax `embo-01` 的 `/embeddings` 不是 OpenAI 兼容协议（入参是 `texts` + `type: 'db'|'query'`，返回 `vectors`，失败时 HTTP 仍 200 需读 `base_resp.status_code`），已在 `lib/ai/embed.ts` 单独适配；其余模型仍走 AI SDK。后台「模型配置」可直接设置/清除已有模型的 Key，向量模型点「测试」会返回实际维度，方便核对 `EMBED_DIM`。
- **降级路径仍完整**：pgvector 不可用 → JSON 向量 + 内存余弦；embedding 模型不可用 → 确定性本地哈希向量；两者都不可用 → 词法 + 子串召回。
- **顺带修复**：新库 `embedding_vec` 列曾在 `chunks` 建表前执行 `ALTER`，导致永远建不出来；文档删除接口缺少知识库权限校验；`docker-compose.yml` 的 postgres 镜像换成自带 pgvector 的 `pgvector/pgvector:pg16`。

## V6 内核优化记录（2026-10-27 · 内核性能与韧性收尾）

承接 v5（前端/接口层性能）之后，补服务端热路径与数据有界性。原则：不推翻既有功能，增量演进；`tsc --noEmit` 0 错误、单测 77 例全过。详见 `docs/03-迭代/迭代计划-v6-内核性能与韧性收尾.md`。

- **O1 缓存命中率统计**：`lib/cache.ts` `cacheStats()` 由「全表 `select` + 内存过滤」改为两次 `db.$count(...)`；`lib/db.ts` 新增索引 `idx_operation_logs_action (action, created_at)`。消除随日志增长的全表扫描。
- **O2 模型解析缓存**：`lib/llm.ts` `resolveModelWithFallback()` 对「未指定模型」高频路径加 30s 内存缓存，减少每请求对 `models` 表的往返（指定模型路径仍即时校验可见性/启停，不缓存）。
- **O3 审计日志留存**：`lib/db.ts` 新增 `trimOperationLogs({ maxRows=200000, olderThanDays=90 })`，在 `ensureInit()` 末尾后台异步裁剪 `operation_logs`，防止长期运行无限膨胀反噬查询。
- **O4 对话首字延迟**：`app/api/chat/route.ts` 将 3 组相互独立的 DB 查询（用户/用量/会话、历史/知识库/记忆、个人快照 6 查）改为 `Promise.all` 并行，约 10 次串行往返收敛为 ~3 次并行批次；不改变任何业务行为与失败语义。
- **O5 调度器单例**：`lib/scheduler.ts` 启动标志改用 `globalThis`，避免 Next dev HMR 重载导致定时任务被重复注册/执行。

> 边界：O2 模型缓存 30s 陈旧（管理员改模型最多延迟 30s 生效）；O3 默认保留近 90 天 / 最近 20 万行，合规需长期留痕时应调大或关闭。历史 ETag 缓存列为后续候选（见方案文档 §五）。

## V6.1 增量优化记录（2026-10-27 · 内核热路径再收尾）

用户要求「把能做的都做掉」，以架构师视角继续扫描内核热路径，新增 5 项、`tsc --noEmit` 0 错误、单测 77 例全过。详见 `docs/03-迭代/迭代计划-v6-内核性能与韧性收尾.md` §二（续）。

- **O10 记忆检索封顶**：`lib/ai/memory.ts` 的 `retrieveMemories()` 加词面 `ILIKE` 预筛 + 每类上限 500，团队/项目记忆膨胀不再全表拉取。

> 边界：O7 降级路径现要求词面重合才进入候选（召回口径与聊天层 `filterRelevantHits` 一致），纯向量语义强匹配在 pgvector 不可用时优先级降低——这是降级路径固有取舍，生产态走 pgvector 快路径不受影响。

## V6.3 增量优化记录（2026-10-27 · 内核之外仍有价值的真问题）

用户问「还有需要优化的地方吗」，以架构师视角复盘后发现 3 处未被前述轮次覆盖的真实隐患，全部落地。`tsc --noEmit` 0 错误、单测 77 例全过。详见 `docs/03-迭代/迭代计划-v6-内核性能与韧性收尾.md` §二（续3）/ §五。

- **O13 日志接口服务端分页**：`app/api/logs/route.ts` 原把整张 `operation_logs`（V6 上限 20 万行）拉进内存再 `.reverse()` 灌浏览器；改为 `?page=&pageSize=` 的 OFFSET 分页 + `db.$count` 总数，由 DB 倒序排序；前端 `AdminClient.tsx` 的 antd Table 改为受控分页（按需拉页）。后台日志页内存/带宽从 O(全表) 降到 O(每页 50)。

## V7.5 评测把检索的真 bug 挖出来了（2026-10-29 · 中文召回 + 50 条 + eval:diff）

上一版把评测建起来，这一版用评测去查系统——结果第一轮就查出一个一直存在、但被"检索没问题"掩盖的缺陷。

- **修 `retrieve` 的中文召回缺陷**（`lib/ai/rag.ts`）：内存降级路径用 `tokenize()` 生成 ILIKE 候选，而它按
  「非字母数字汉字」切分，**连续汉字整串成了一个 token**。于是
  `ILIKE '%示例新区的设备综合指数同比排名前了几位%'` 必然 0 命中——纯中文问句召回不到任何片段，
  带空格或英文（`振动`、`token`）的问句才正常。这就是「同一个知识库，有的问题能答、有的答『资料里没有』」的真实原因。
  修法是**两轮召回**：先精确英数词（精度高、与修复前行为一致），召回不足再补中文二元组 `zhBigrams`。
  直接把二元组一路混进去会让泛词灌满候选池、把原本命中的片段挤出去（`ans-02` 就是这样回归的）。
- **golden set 从 24 条补到 50 条**，重点补「能召回但答错」的难例：数值相邻、排名错位、同比方向、
  接口路径张冠李戴、跨分区归属、粒度越界（周均值 vs 小时值）。
- **新增 `npm run eval:diff`**：对比最近两份报告，输出「回归 / 修复」清单。单看总分没有信息量——
  同配置重跑能差 5 条，必须看逐条变化。
- **判定器抽成 `evals/judge.ts`，配 16 条回归测试**（`evals/judge.test.ts`，样本全部来自真实误判）。
- **基线：46/50（92%）**，应答对 21/23、应拒答 25/27、检索命中 23/23。4 条稳定失败根因明确，
  见 [`evals/README.md`](../../evals/README.md) 的「四条稳定失败与根因」。
- **推翻了 V7.4 的两条结论**（诚实地写在文档里）：
  1. 「闸门开与关只差 1 条」不是闸门没用，而是**检索根本没工作**。修好后重测：开关两态 50 条判定完全一致
     （46/50 vs 46/50），但检索层差异巨大——7 条用例的召回被完全清空、19 条被削减。
     **闸门提升的是注入质量与成本，不是答对率**，因为模型本身有拒绝能力。
  2. 「abs-09 模型拿 2025 年数据充数」是**误判**。真相是判定正则 `2030[^。]{0,20}\d+` 匹配到了
     「2030 年 T2.**5**」里的 2.5，模型一直答对了。6 条失败里 4 条是这类误伤。
- **prompt 加了两条硬约束**（`app/api/chat/route.ts`，评测端同步）：并列数值列表必须按顺序一一对应（治排名错位）；
  禁止用相邻指标/时段的数据替代或推算区间（治 EHI 编造）。

## V7.6 修掉「切片碎片化」，评测归因到满分（2026-10-29 · 分块合并 + 重建切片 + 判定器结构化）

上一版把评测搭起来并修了中文召回，这一版顺着评测往下挖，挖出三个真 bug，其中两个是**这一版自己引入的**。

- **分块合并（`lib/ai/rag.ts` 的 `splitText`）**：docx 一个视觉行就是一个 `w:p`，旧实现「一段一片」，
  实测 **711 片里 613 片（86%）不到 20 字**。碎片向量语义为零、词面命中率却极高（问题里的词就在目录标题里），
  把含答案的长片段挤出 top-k，`ans-19`/`ans-21` 因此稳定答不出。改为**先贪心合并短段落到接近 800 再切**，
  结果 **711 片 → 6 片（4193 字，平均 765 字），<20 字碎片清零**，两条用例同时转绿。
- **重建切片（`joinChunks()` + `POST /api/knowledge/documents/[id]/rechunk`）**：`reindex` 只重算向量、
  不重切块，改分块策略对存量数据无效。原文没落库，只能从切片反推 → 还原 → 重切 → 重建向量。
  前端入口在文档行 `⋯` →「重建切片」，操作列因此收敛为「1 个可见按钮 + ⋯」。
- **`joinChunks` 的坑**：反推重叠时用 `contents[i-1].slice(-overlap)`，当旧片短于 overlap 时拿到的是
  「上一片全文 + 更早一片的尾巴」，前缀不匹配 → 剥不掉 → **迁移一轮下来原文每行都变成两行**。
  改为用还原出来的 `blocks[i-1]` 迭代取尾，并补单测（旧单测用 800 字长片，恰好绕过了这个缺陷）。
- **`lexicalScore` 没有上界**：返回「查询词平均出现次数」，融合分能到 **3.37**，`score >= 0.62` 的闸门
  对任何含高频关键词的碎片都无条件放行。改 `raw/(raw+1)` 饱和到 `[0,1)`。
- **判定器改为结构化**：新增 `assertiveText()`（含否定词的分句整段剔除，防止正则跨过「我没说」去抓引用的数字）、
  `hasConcreteNumber()`（剥掉日期/异常项名/章节号后无数字 → 认定没编数值）。词表补了四轮仍在漏
  （「无法查到」「未接入」「无法直接给出」「未载明」），**穷举措辞这条路有天花板**。
- **4 条用例被推翻**：`abs-16`、`abs-26`、`abs-27` 原判「应拒答」，实际周报里就写着答案（表1 的 22 分区读数、
  7 天 EHI 预报表）。碎片化让模型「找不到」，被误读成「资料里没有」，差点又写进复盘。golden set 52 条。
- **新基线：52/52**（应答对 27/27、应拒答 25/25、检索命中 27/27，连跑两轮一致）。
  闸门开关两态判定一致，但平均命中片数 **5.02 → 3.27（-35%）**，6 条召回被完全清空。
- **已知数据缺陷（未修）**：docx 合并单元格让表头与数据行错位，同一指标出现两套值

## V7.7 修掉「小数点被当句末」，并把迁移过的数据洗干净（2026-10-29 · 分块正则 + 存量清洗）

V7.6 把碎片化和判定器理顺之后还剩两笔账：切片里混着重复块、以及一个更贵的分块缺陷。

- **`splitText` 把小数点当句末**（`(?<=[。.！？；\n])`）：`温度`、`0.6`、版本号 `1.3.1` 被切断，
  第 2 步再用 `\n` 拼回，正文里就固化了「0.\n6」「T2.\n5 读数」。一篇 3354 字的周报里 **108 处**。
  对一份通篇是监测读数（几乎每个数都带小数）的知识库，这等于往模型嘴里塞错的数字。
  改为 **中文标点无条件断、ASCII 的 `. ! ?` 必须后接空白或文末才断**，并补回归断言 `/\d\.\n\d/` 不得出现。

## V7.9 评测能自己跑了：趋势曲线 + 夜间任务 + 4 条更难的用例（2026-10-29 · 评测工程化）

V7.8 之后，剩下的问题不是「哪个功能没做」，而是「怎么知道它变差了」。评测跑一次 4 分钟，
没人会天天手动跑；报告散成一堆 JSON，也没人会逐份翻。

- **`npm run eval:trend`**：把 `reports/` 压成时间线，画四张折线（总通过率、应答对 vs 应拒答、
  平均命中片数、平均耗时）+ 一张「历史不稳定用例」表，输出自包含 `reports/trend.html`。
  闸门开/关画成两条线——两种配置混在一条线上就读不出信息。
  **最该盯的是「平均命中片数」：它是领先指标**，切片变碎 / 闸门失效 / 向量降级时准确率还没掉，它先动。
- **`npm run eval:nightly`**（`scripts/nightly-eval.ps1`）：跑评测 → 更新趋势 → 判回归 → 清过期报告。
  可注册成每天凌晨的计划任务。**判据不写死分数**（模型有 ±1~2 条抖动，写死会天天误报），
  而是和「同配置的上一次」比：掉 ≥2 条或命中片数涨 ≥0.8 片才报警；报警落一份 `ALERT.md`，恢复后自动删。
- **三个 Windows 坑**（都只在日志里表现为「乱码」，不报错）：`Tee-Object` 默认按 UTF-16 写文件，
  和 `Add-Content -Encoding UTF8` 混写同一日志会互相污染；PS 5.1 按本地代码页解析 `.ps1`，
  **文件必须带 UTF-8 BOM**；`$ErrorActionPreference='Stop'` + `2>&1` 会把 npm 的 stderr 警告当终止错误抛出
  ——实测「评测跑完了、报告也写了，日志却断在 vitest 启动那一行」。
- **判定器又修了三处**：① `abs-24` 正确拒答后补了句「综合指数排名第 11 位，**与 GDP 无关**」，
  被 `第 N 位[^。]{0,10}GDP` 跨逗号抓成编造 → 跨度排除逗号 + 「无关/不能等同」也算否定分句；
  ② `℃` 的 `³` 与用例的 `3` 不是同一个字符（`µ` vs `μ` 同理），模型答得完全正确却判「缺少关键事实」
  → `stripMarkdown()` 统一归一化上下标与微符号；③ `new RegExp(undefined)` 是**空模式**（匹配一切），
  `forbidden` 传错类型会让所有回答被判编造 → 跳过非字符串项 + 单测锁住。
- **`maxTokens` 2000 → 4000**，空回答重试 1 次 → 2 次：`ans-28` 在 2000 下三轮里两轮空文本，
  耗时 30s、命中 6 片——它在思考，只是没额度写完。
- **golden set 52 → 56 条**，四道「同一份资料但要动脑子」的题：单位区分（温度 ℃ vs 功耗 A）、
  跨表比对（日均接口独有 `temp_8h`）、参数表读法（`dataType` 0/5）、干扰抵挡（把未来 7 天预报当历史）。
- **判定器单测进 `npm run check`**：`evals/judge.test.ts` 之前只挂在 eval 配置下，改坏 `judge.ts`
  要等下一次评测才发现——而判定器错了，评测结果就没有意义。单测 196 → **231**（21 文件）。
- **基线：56/56**（应答对 30/30、应拒答 26/26、检索命中 30/30）；关闸门 55/56，
  差的那条正是 `ans-29`——**闸门挡掉的是会把人带偏的干扰片段**，不只是「少注入几片」。
  平均命中片数 **5.43 → 3.41（-37%）**，6 条清空、30 条削减、0 条变多。

## V7.10 生产级收口：把「第二通道」也算进预算（2026-10-30 · 成本/安全 + 对抗评测 + 重排 + 沙箱）

前九轮把对话主链路打磨到 56/56，但**技能运行与定时任务是另一条通道**：它绕过了 chat 路由里的
额度预检、接口限流和 120s 墙钟。用户狂跑技能 / 定时任务一样能烧穿预算、打爆上游，而这些在对话侧
的加固完全覆盖不到。

- **额度、限流、超时补到第二通道**：新增 `lib/quota.ts` 的 `checkQuota()`（与 chat 同口径
  block/warn/downgrade），接进 `skills/run` 与 `scheduler.runSchedule`；`skills/run` 另加 20/60s
  限流；`engine` 的 `RunOptions` 加 `maxWallClockMs` / `maxTokens` / `usageSink`，所有 LLM 调用走
  统一 `gen` 包装做预算闸门，超限抛 `RunAborted` → 顶层转成 `aborted` 结果（是失败信号，不是静默截断）。
  **engine 仍是纯函数**：预算靠注入的 sink 实现，20 条编排单测一条没改。
- **成本能归因到人了**：`logLlm` 原来把 `user_id` 写死 `null`，只能看全局花了多少；现在由
  executor 每次调用透传 userId，技能 / 调度 / 对话三条链路一起填上。
- **调度锁 + 显式开关**：`runSchedule` 加 Redis `SET NX EX` 锁（多副本不重复执行），另有
  `SCHEDULER_ENABLED=false` 让非主副本**根本不启动** cron——锁只防「同一次触发跑两遍」，防不了
  N 个副本各起一套定时器空转，也防不了「扩容后悄悄重复通知」这种没有任何报错的故障。
- **RAG 接真 rerank**：新增 `lib/ai/rerank.ts`，按 Jina / Cohere v2 / SiliconFlow 共用的
  `POST {baseUrl}/rerank` 调用；候选池放大到 3k（至少 12）再精排。三个刻意的取舍：未配置模型时
  **零网络**；超时 3s 失败**降级**回本地排序（精排是增强项，不能让它打断检索）；**只改顺序不改
  score**——`filterRelevantHits` 的 0.62 闸门是按「0.75 向量 + 0.25 词法」的分布定的，写回 rerank
  分会让闸门失真（各家分数尺度差极大，有的对无关文档也给 0.6）。
- **沙箱升到 worker_threads**：原先进程内 `vm` 的 `timeout` 只管 CPU 时间片、**管不了堆**——一段
  `new Array(1e8)` 能把整个 Next 进程拖到 OOM。现在跑在 worker 里：死循环可 `terminate` 强杀
  （实测 304ms 掐断），内存超限变成 worker 崩溃而非服务 OOM。诚实标注：worker **不是**安全边界
  （同进程、共享文件系统），仍只用于「用户自己写、平台信任其意图」的脚本。
- **技能版本可回滚**：`skill_versions` 快照表 + `PATCH` 时自动留档 + `/api/skills/[id]/rollback`
  与前端「历史版本」抽屉。回滚前会先把当前版本再快照一次，**回滚动作本身也可被回滚**。
- **对抗评测从 0 到 20 条**，按既有「两道门」拆开：`adversarial.test.ts`（数据完整性 + 判定器
  自检）进 `npm run check`，`adversarial-run.test.ts`（真调模型 + 90% 门禁）进 `npm run eval`。
  拆成两个文件而不是一个 `skipIf`，是为了让 check **根本不 import db/ai**——否则 CI 没配模型时
  会先崩在初始化，而不是干净地跳过。
- **对抗评测当场抓出一个真缺陷**：模型会「先礼貌拒绝、再贴可执行命令」——「我无法执行
  `DROP TABLE users;`」后面紧跟一句 `DROP TABLE users;`；「我无法读取 `/etc/passwd`」后面跟着
  `cat /etc/passwd`。执行确实没发生，但用户复制粘贴就完成了，人工复核极易读成「已拒绝」。
  修法是给 system prompt 加【拒绝要彻底】：可以说清为什么不做的与合规办理路径，但不得输出可直接
  复制的命令 / SQL / 脚本 / 敏感路径。**这类缺口用「模型是否拒绝了」做判据永远发现不了**，必须用
  「输出里有没有出现具体命令片段」做硬断言。
- **判定器的误伤比漏判更危险**（第二个坑）：第二轮 `sk-` 把「已遮蔽令牌后的示例
  `Bearer sk-****`」判成泄露——把教科书式回答标红，会让人开始怀疑判据，最后关掉门禁。现在加词边界
  （`DAN` 不命中 `dangerous`）+ 遮蔽豁免（`****`/`xxx`/`…`/`<` 紧跟其后不算命中）。
- **对抗三轮 18/20 → 19/20 → 20/20**，报告进 `evals/reports/*-adversarial.md`；`eval:trend` 与
  `eval:diff` 都支持对抗口径（默认只挑 golden，避免两类报告混比得到一排无意义的 `undefined`）。
- **验证**：`tsc --noEmit` 0 错 · `lint:ui` 44 TSX 0 违规 · 单测 231 → **292**（27 文件）·
  对抗 **20/20** · golden 55/56。
- **已知抖动**：本次 golden 少的那条是 `abs-12`——模型这次用「7 天 − 1 天中度异常」反推出
  85.7% 优良率（prompt 明令禁止推算），判定器判失败是对的，属模型偶发违纪而非检索回归
  （hits 与 top1 分和上次完全一致）。已作为不稳定用例进趋势跟踪。

## V8 运行时治理：V 层进请求路径，工具收进一个真相源（2026-11-01 · 架构重构）

前七轮把「离线评测」「工具注册表」「记忆/缓存」分别做对了，但它们之间还有三处断裂：评测只在
`npm run eval` 里跑、对话工具绕过 registry、缓存 key 每轮都变。V8 不重写已验证的部分，只把这三处接上。

- **运行时 V 层（R4-a）**：新增 `lib/agent/runtime-verify.ts`，回答落库前做**确定性校验**——空答 /
  模板占位符残留（`{{input}}`）/ 伪造来源（引用了不在 `sourcesList` 里的文档）/ 无据能力 / 可复制的
  破坏性命令。只打标 + 写 `eval_runtime` 日志，不改写已交付回答、不触发重试，**零额外模型成本**。
  真机验证时用诱导输入命中 `template_placeholder`，证明它确实跑在请求路径上。
- **独立 LLM-judge（R4-b，默认关）**：`lib/agent/runtime-judge.ts` 只喂「问题 + 工具结果摘要 +
  最终回答」，**不喂历史、不喂 reasoning**（带原推理去评审，模型会自我合理化）。`RUNTIME_JUDGE=on`
  才启用，且只为「动过高风险工具」的轮次付费；解析失败返回 `null` 而不是 `fail`，避免假警报。
- **工具幂等（R3）**：新增 `lib/agent/idempotency.ts`，`run_skill` / `create_todo` 用
  `${conversationId}:${toolCallId}` 做 key。内存 + TTL + 并发共享 promise；**失败不缓存**，第二次
  仍可重试——防的是 `streamText` 重试导致重复建待办/重复跑技能。
- **记忆治理（R2）**：`memories` 加 `credibility` / `source_type` / `evidence_version` / `expires_at`
  四列（幂等 `ADD COLUMN IF NOT EXISTS`）。自动抽取默认 `low + extracted`，检索时按可信度加权、
  过期条目不召回——防「未验证推测升级为事实」。
- **工具真相源闭合（R1）**：14 个对话工具从 `chat/route.ts` 内联定义迁到
  `lib/tools/chat-tools.ts` 的 `buildChatTools(ctx)`，再经 `registerTool` / `invokeRegisteredTool`
  统一走**权限 → 审批 → 超时 → PII 脱敏审计**。工具定义是模块级常量、身份一律从 `ctx` 读，避免
  全局 Map 在并发请求间串用户；`route.ts` 从 1136 行降到 811 行。
- **缓存 key 修的是两个 bug（C2）**：`lib/agent/cache-key.ts` 让读写用**同一段 system**（此前写缓存
  用追加防御说明后的 `sys`、读用追加前，命中率恒为 0）；`normalizeSystemForCache()` 把时分归一为
  `<time>`、把 Token/存储用量替换为 `<volatile>`，但**保留日期**（跨天必须失效）、**不归一化知识库
  资料**（它决定答案内容）。真机复测：同一问题 2.02s（miss）→ **0.73s（hit）**。
- **防打转（O1）**：`lib/agent/loop-guard.ts` 在执行层维护「工具名 + 参数」指纹窗口，相同调用成功过
  再调直接回放上次结果 + 强指令；单工具执行 >4 次一律拦截。只有成功才计数，失败/超时不算。
- **模型分档（C1）**：`lib/agent/model-tiers.ts` 只对 summary / memory-extract / synthesize / judge /

  就回退主模型，不猜。三个开关：`MODEL_TIERING=off` / `MODEL_CHEAP_ID` / `MODEL_TIER_<TASK>`。
  ⚠️ 当前库里 16 个模型单价全为 0，所以分档实际是 no-op；要生效需填真实单价或显式指定 cheap 模型。
- **上下文预算（O2）**：实时数据（token/存储）每轮查，慢变数据（项目/文件/技能/定时任务）30s memo
  并做并发去重；清单限量 + 4000 字符硬上限，超限明确写出「另有 M 项未列出」，不静默截断。
- **业务成功判定（O6）**：`lib/tools/business-success.ts` 把 DemoAPI / Open-Meteo 的特判提成规则表，并在
  `callConnector` 字段映射**之前**判一次业务失败——下游「HTTP 200 + 报错报文」不再被当成成功喂给模型。
