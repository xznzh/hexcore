# 优化记录 · v8.7 通道健康度

> v8.6 把运行时校验接到了每条通道，但结果只落到 `operation_logs` 的一行文本里。
> 这一轮给它补一个出口：**观测数据没人看得见，等于没有观测**。

## 1. 缺口的确切形状

v8.6 之后，三条通道都会做运行时校验：

| 通道 | 写什么 | 写在哪 |
|---|---|---|
| 对话 `chat` | `eval_runtime`（`block:` / `warn:` 规则摘要） | `operation_logs` |
| 技能 `skills/run` | `eval_runtime`，detail 前缀 `channel · skill/<技能名>` | 同上 |
| 定时任务 `scheduler` | `eval_runtime`，detail 前缀 `channel · schedule/<任务名>` | 同上 |
| 三条通道的出口护栏 | `guardrail_output_block`，规则在 `target` 列 | 同上 |

问题在于：要回答「哪个技能这周一直在报 `empty_answer`」，只能自己去翻日志表、肉眼数。
于是这个功能上线后**没有人会用它**——不是不好用，是根本不知道去哪儿看。

## 2. 设计取舍

### 2.1 解析 `detail` 文本，而不是加结构化字段

看起来正确做法是给 `operation_logs` 加 `channel` / `rule` 列，然后 SQL `GROUP BY`。没有这么做，两个原因：

1. **规则数量会增长**。`empty_answer`、`fabricated_source`、`ungrounded_capability`、`dangerous_copyable`… 每加一条就改一次 schema，是把「日志格式」问题变成「迁移」问题。
2. **detail 的主要读者是人**。排障时直接看 `channel · skill/周报 · block:empty_answer(最终回答为空)` 一眼就懂；改成 JSON 或拆列，人读的成本上去了，换来的是统计方便——方向反了。

所以这里承认 detail 是**人和机器共用的可读格式**，用解析器读它，并把这个格式用测试锁住。
格式一旦变动，`tests/channel-health.test.ts` 变红，而不是统计悄悄归零。

### 2.2 「0 个问题」有三种含义，必须区分开

这是本轮最重要的一个决定。统计数据为 0 时，可能是：

| 情况 | 真实含义 | 该怎么办 |
|---|---|---|
| 这段时间没有通道触发规则 | 质量好 | 显示 0，正常 |
| 这段时间通道根本没跑 | 无数据，不是好消息 | 显示 0，但要能看出来 |
| 日志格式变了，解析全失败 | **统计坏了** | 必须报警，不能显示 0 |

前两种在数据层无法区分（都没有记录），所以不处理；第三种**必须**处理，否则页面会长期显示一个干净但错误的 0。

做法：聚合结果里显式带 `unparsed`（解析失败行数），非零时页面上出黄色警告条。

同时定了另一条规则：**`eval_runtime` 解析出 0 个 issue 视为解析失败**。理由是这类日志只在「有问题」时才写（`recordChannelVerify` 和对话通道都是这个口径），一条记录解析不出规则，说明格式对不上了，不能当成「没问题」混进正常数据。

还有第三层：明细行数上限（`MAX_ROWS = 20000`）触发时响应带 `truncated: true`，页面同样提示。**悄悄截断会让「问题变少」看起来像「质量变好」**，这和 `unparsed` 是同一类陷阱。

### 2.3 对话通道不进「技能 / 任务」榜

标签榜只收带 `label` 的记录。对话通道没有标签（它是「谁在问」而不是「哪个配置在跑」），如果用一个空名字混进去，榜单第一行永远是一个没有意义的巨无霸，真正的坏技能会被挤下去。

### 2.4 不新建表、不新建页面

- 数据源就用 `operation_logs`，已有的 `idx_operation_logs_action ON operation_logs(action, created_at)` 正好覆盖 `action IN (...) AND created_at >= ?`，不需要加索引。
- 页面挂在管理后台已有的「评估」Tab 里。那个 Tab 本来就是质量相关的（RAG 自检 + LLM-judge），再多开一个 Tab 会让「质量」这个概念散在两个地方。

### 解析器的三个细节

1. **先剥 `[trace:xxx] ` 前缀**。`logAction` 会自动加，不剥则第一条记录就解析失败。
2. **只按第一个 `/` 切通道与标签**。技能名可能自带斜杠（「日报 / 周报」）。
3. **issue 用全局扫描 `block:rule(` 而不是按 ` | ` 切**。issue 的原因文本里可能含 ` | `（被拦下的原文里就有），按分隔符切会多出无主片段，统计里就冒出一个 `unknown` 规则。

## 5. 怎么看这个页面

进「管理后台 → 评估 → 通道健康度」，选时间窗。读的顺序建议：

1. **先看警告条**。有 `unparsed` 就先解决解析问题，否则下面的数字都不可信。
2. **看「按规则」**。规则名直接指向问题类型：`empty_answer` 是通道产出为空，`fabricated_source` 是编来源，`ungrounded_capability` 是声称用了能力但没调。
3. **看「问题最多的技能 / 任务」**。`最常见规则` 那一列比「问题数」更能说明问题——同一个技能 8 次全是 `empty_answer`，比另一个 8 次分散在 5 条规则上更容易定位。
4. **最后看「最近记录」**里的「观察模式」标签。带这个标签说明 `CHANNEL_GUARD=off` 期间命中了但被放行，是「应急开关开了多久、放行了什么」的唯一证据。

页面上的 `没有记录 = 这段时间没有触发规则，不代表该通道没有运行` 这句话是刻意写的。这类页面的 0 最容易被误读成「一切正常」。

## 6. 仍未闭环

1. **没有告警**。只能人去看，不会主动通知。要做的话得先定阈值（比如「同一技能 24 小时内 3 次 block 就通知」），以及通知给谁——技能 owner 还是管理员。
   > **v8.8 已补**：阈值按「同一「通道 · 名称 · 规则」在 60 分钟内 3 次」，通知给启用状态的管理员。
   > 详见 [`优化记录-v8.8-质量告警.md`](优化记录-v8.8-质量告警.md)。
2. **没有环比**。现在只能看「这段时间有多少」，看不出「比上周多了 3 倍」。趋势图有，但没有对比线。
3. **`runtime-judge`（R4-b）仍只挂 chat**，这是同一模式的第五次。它的成本模型不同（每次都是计费调用），接线前要先定「哪些通道的失败值得花钱复审」，不适合顺手带上。
4. **异步摘要有界滞后**（v8.3 遗留，仍未动）。需要先量化实际滞后量。
5. **明细上限 20000 行**。规则触发率高到撞上这个上限时，统计只覆盖最近一部分——`truncated` 会提示，但没有分页或预聚合。真到那一步就该落聚合表了。
