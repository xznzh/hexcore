# 优化记录 · v8.9 出站投递与成本边界

> v8.8 让告警「会来找人」，但它只会找**登录了平台的人**。这一轮补的是四件事：
> 一条统一的外发通道、把告警接上去、把 v8.3 那个「缺口有界」的错误判断修正掉、
> 并让语义抽查（judge）覆盖非对话通道——同时给它装上成本闸。
>
> 四项里有两项是**既有缺陷**，不是新功能：`scheduler` 的裸 `fetch`、摘要水位线越界。

## 1. 出站投递：一处裸 `fetch` 的四个问题

`lib/scheduler.ts` 在定时任务完成后往用户的 webhook 推一条 JSON。原来是这么写的：

```ts
await fetch(s.webhookUrl, { method: 'POST', headers: {...}, body: JSON.stringify({...}) });
```

四个问题叠在一起，而且**都不报错**：

| 问题 | 后果 |
|---|---|
| 没有超时 | Node 的 `fetch` 默认不设上限。接收端挂住，定时任务被吊到进程重启；锁有 10 分钟 TTL，释放后下一轮再来一次 |
| 没过 SSRF 校验 | `webhook_url` 由用户自己填。`http://169.254.169.254/latest/meta-data/` 就是一次云主机凭据读取——平台别处早已统一走 `safeFetch`，只有这里漏了 |
| 没有重试 | 接收端一次 502 就永久丢失 |
| 失败静默 | `catch {}` 后什么都不留，「到底推没推成功」事后无从判断 |

新建 `lib/outbound.ts` 把传输层做对一次：`safeFetch`（含逐跳 SSRF 校验）+ `AbortSignal.timeout`
+ 有限重试 + 进程级熔断 + 响应判定 + 错误脱敏。

### 1.1 为什么拆成 `postJson` 和 `deliverWebhook` 两层

因为定时任务的 payload 结构（`{schedule, status, aborted, result}`）**已经被外部接收端依赖**，
不能为了统一而改掉。所以：

- `postJson(url, payload, opts)`：只管传输加固，不管组包；
- `deliverWebhook(url, msg, opts)`：按渠道组装 payload 后交给 `postJson`。

两者共用同一套加固，各自的契约都不用动。`scheduler` 改调 `postJson`，
payload 一个字节都没变，只是多了超时、SSRF 校验、重试，失败时会打一行 `console.warn`。

### 1.2 重试只对「可能自己好」的失败

网络层异常、5xx、429、408 才重试。4xx 不重试——URL 写错、密钥失效这类问题重试三次
只是把同一份错误抄三遍，还会触发接收端风控。这不是省事，而是「重试」在语义上
只对暂时性故障成立。

### 1.3 熔断按「每次 HTTP 尝试」计数，不按「整轮投递」

第一版是整轮投递完了记一次失败。按告警 10 分钟一趟算，要 5 轮 ≈ 50 分钟才熔断，
期间每轮都要白等一次完整超时。改成每次尝试都计数后，两轮即可熔断。

熔断 key 用 `origin` 而不是完整 URL：同一个坏掉的服务，换个路径也一样坏。
用完整 URL 会让熔断形同虚设（每个 key 各失败一次）。

## 2. HTTP 200 不等于投递成功

这是给企微 / 钉钉 / 飞书做机器人时最常踩的坑：

```
HTTP/1.1 200 OK
{"errcode":93000,"errmsg":"invalid webhook url"}
```

只看 `res.ok` 会把「密钥过期」记成「发送成功」，于是告警系统在被最需要的时候
安静地什么都不做。所以 `inspectWebhookBody()` 必须读 body：

- 企微 / 钉钉：`errcode`（钉钉新版偶尔用 `code`）
- 飞书：`code` / 旧版 `StatusCode`
- `raw` / `slack`：无统一约定，只看 HTTP 状态
- 不认识的 body（纯文本 `ok`、多出字段）：**一律当成功**

最后一条是刻意的。把「网关多返回了一个字段」判成失败会造成大量假告警，
而假告警比漏判更难排查——它会让所有人开始无视通知。

还有一个长度陷阱：企微 text 消息上限 2048 **字节**（不是字符），中文按 UTF-8 算 3 字节，
实际只能放约 680 个汉字。超长时企微返回 `errcode 40058`，而那正好是最需要看告警的时刻。
所以正文按渠道分别收敛（`TEXT_LIMIT`）。

## 3. 质量告警外发：站内通知的前提是「有人登录」

`QUALITY_ALERT_WEBHOOK`（可多个，逗号分隔）+ `QUALITY_ALERT_WEBHOOK_KIND`。
三个决定：

1. **合并成一条消息**。站内按 key 各发一条是对的（能单条已读），但 IM 群里一次 5 条
   机器人消息会把人推走。所以外发只发一条摘要，内含全部条目——代价是没有「逐条已读」，
   因此摘要必须自带定位信息（通道 · 名称 · 规则 · 次数），让人不登录也能判断严重性。
2. **顺序是「站内 → 外发 → 写状态」**，不是「外发成功才写状态」。后者会把「站内已经
   通知过」的事实一起丢掉，下一轮对全体管理员重复通知。用一个小概率的漏发，
   换掉一个必然的重复轰炸。
3. **失败要留痕**。外发是「最多一次」语义（cooldown 已写入，不会补发），
   所以结果进 `AlertState.lastExternal`，接口与页面都暴露。页面上 `null` 的措辞
   必须同时覆盖「没配 webhook」和「还没产生过告警」两种情况，不能写成「未配置」。

**目标数上限 5 个**，理由是锁的 TTL：一次检查持有 Redis 锁（`intervalMin × 2` 分钟），
单个目标最坏 `3 × 8s` 重试，5 个约 2 分钟，仍在最短 TTL 边缘内。不设上限时
运维配了 20 个群就会让本轮超过 TTL，下一轮在锁过期后对着同一批日志再发一遍——
重复告警恰好是 v8.8 最想避免的东西。

## 4. 摘要缺口：v8.3 那个判断错在哪里

v8.3 把摘要移出首字路径时，文档里写的是：

> 本轮新被挤出的那几条消息，本轮既不在 history、也不在（上一轮的）摘要里。
> 所以门槛设成新增 ≥6 条才触发，缺口有界（那 6 条上一轮还在窗口里，模型刚看过）。

这个推理**只对「触发摘要的那一轮」成立**。实际有两个错：

### 4.1 不足 6 条时，缺口会一直累积

第 1 条被挤出 → 不触发摘要 → 它不在窗口里，也不在摘要里，下轮依然不在。
要等到第 6 条才一起处理。这段时间里它是**彻底不可见**的——「被挤出」的意思就是
模型看不到第二次，不存在「刚看过」。

### 4.2 水位线越过了未摘要的内容（这是永久丢失，不是滞后）

```ts
const body = droppedNew.map(...).join('\n').slice(0, 6000);
...
const upto = droppedNew[droppedNew.length - 1].createdAt;  // ← 推进到最后一条
```

`slice(0, 6000)` 保留的是**开头**（最早的对话），被截掉的是**尾部**（最新内容）；
而水位线却宣布「这些都已经进摘要了」。于是中间那一大段从此既不会被摘要、
也不会再被读到。

### 4.3 两处一起修，缺一不可

- `packForSummary()`：按时间正序累加到字符上限，返回**实际覆盖到的那一条**（`lastAt`）。
  水位线只推进到这里。`lastAt === null` 时不动水位线——推了就等于宣称「已进摘要」。
  单条超限时截断但**照样计入覆盖**，否则一条巨长的消息会让水位线永远卡在原地。
- `buildSummaryGap()`：把「已滑出窗口且还没进摘要」的原文按 token 预算注入本轮，
  闭合滞后那一半。**不看 6 条门槛**——门槛只决定「要不要花一次摘要调用」，
  「这一轮能不能看到这些内容」是另一件事。

只做前者，最早的内容仍会被摘要截断丢掉；只做后者，摘要永远追不上
（每轮只挤出 1~2 条，到不了门槛，水位线不动）。所以必须一起做。

注入方向的取舍：从**最新**往回取。缺口的语义是「刚滑出窗口的那几条」，
越新越相关；从旧往新取会让模型拿到一段和当前话题无关的远古对话，还白花 token。
预算取历史预算的 15%，夹在 `[400, 1500]` 之间——低于 400 连一轮问答都放不进去，
高于 1500 就等于把刚省下的首字延迟又还回去。

`omitted` 会写进文本（「更早的 N 条因长度预算未列出」）。不写的话，
「缺口已闭合」就是假的——这和 v8.7 `unparsed` 是同一类陷阱。

## 5. judge 接非对话通道：先定成本，再接

v8.6 把确定性 V 层接到了 skill / schedule，但 judge 一直只挂在对话上。
而那两条通道恰恰更需要它：产出直接进通知与 webhook，用户看到之前没有人复核。

但「顺手接上」会让成本从「每轮对话抽一次」变成「每次技能运行 + 每次定时任务都抽一次」，
定时任务可能每小时跑几十次——这是数量级的变化。所以三件事一起做：

| 闸 | 环境变量 | 默认 | 作用 |
|---|---|---|---|
| 采样 | `RUNTIME_JUDGE_SAMPLE` | 20 | 按「日期 + 通道 + 问题 + 回答」的确定性哈希取模 |
| 日预算 | `RUNTIME_JUDGE_DAILY_MAX` | 200 | 滚动 24 小时，超了跳过并留一行 `judge_skipped` |
| 高风险过滤 | — | — | 只判用过 `HIGH_RISK_TOOLS` 的轮次 |

采样**不用 `Math.random()`**：多副本各判一次会得出不同结论，事后也无法回答
「为什么这条没被抽到」。确定性采样同时解决了这两点。种子带日期，所以同一份内容
第二天会重新洗牌，不会永远卡在未采样区间。

日预算是**防失控的闸，不是精确计费**：多副本时 Redis 可用则共享计数，
不可用则退化为各算各的，实际上限会略高于配置值。这个误差可以接受，
因为闸的目的是「挡住某个循环任务把额度烧穿」，不是对账。

### 5.1 轨迹归一：漏了不报错的那一步

两种通道的轨迹形状不同：

- 对话通道：`{type:'tool_call',name}` + `{type:'tool_result',name,result}`
- 技能通道：`{type:'tool',tool,output}`（一个节点同时含调用与产出）

如果直接把技能轨迹交给 `digestTrace`（只认 `tool_result`），摘要会是空字符串，
judge 看到的是「本轮无工具结果」——于是任何具体数字、来源都会被判成「凭空捏造」，
**误报率 100%**，而日志里看起来像是模型真的有问题。

所以 `normalizeJudgeTrace()` 把技能节点一次展开成「调用 + 结果」两条，
并在 `judgeChannelAnswer()` 入口统一调用。**不在调用点各写一遍**——写两遍就一定会
有一处忘掉，这是 `channel-verify.ts` 文件头已经记录过的同类教训
（v8.4 的空 context 事故）。

### 5.2 一个顺带发现的 bug：judge 日志污染了 `unparsed`

原来 judge 和确定性校验共用 `eval_runtime` 这个 action。但 `channel-health.ts` 的解析器
要求 detail 里出现 `block:rule(` / `warn:rule(` 结构，而 judge 的 detail 是
`judge(model,tier): score=1 reason=…`——解析必然失败。

后果是：**只要 `RUNTIME_JUDGE=on`，健康度统计就会持续出现「日志无法解析」，
进而每天误报一条「质量告警自身异常 · 校验日志无法解析」。**

换成独立的 `eval_judge` 后两件事都干净了：解析器不必猜；judge 的抽样数据也不会混进
「确定性校验次数」的排名里——抽样的分母不是全量，放一起比次数是错的。

## 6. 配置清单

```bash
# 质量告警外发（不配 = 只发站内通知）
QUALITY_ALERT_WEBHOOK=https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx
QUALITY_ALERT_WEBHOOK_KIND=wecom        # raw | wecom | dingtalk | feishu | slack

# 出站传输
OUTBOUND_TIMEOUT_MS=8000
OUTBOUND_MAX_ATTEMPTS=3

# 运行时抽查（默认关闭）
RUNTIME_JUDGE=on
RUNTIME_JUDGE_SAMPLE=20
RUNTIME_JUDGE_DAILY_MAX=200
```

企业内网自建的通知服务需要 `SSRF_ALLOW_PRIVATE=true`（与平台其它出站路径共用同一个开关）。

## 7. 反向验证

按「可能的错法」逐条改坏、跑测试、确认变红，再还原：

| 改坏什么 | 期望变红的测试 | 结果 |
|---|---|---|
| `packForSummary` 把水位线推回数组末尾 | 「装不下时 lastAt 指向实际最后一条」 | 1 条红 |
| 去掉 `normalizeJudgeTrace` 的 `type==='tool'` 展开 | 轨迹归一 + digest 非空 + 高风险判定等 5 条 | 5 条红 |
| `inspectWebhookBody` 直接返回 null（只看 HTTP 状态） | 业务码判定 3 条 | 3 条红 |

### 7.1 反向验证本身也踩了一个坑

写 `tests/outbound.test.ts` 时，响应替身漏了 `headers` 字段。`safeFetch` 会读
`res.headers.get('location')` 判重定向，于是每次调用都在 `safeFetch` 里抛 TypeError，
被上层当成「网络层失败」重试三次。

三条断言 `attempts === 3` 的用例因此**假绿**——它们「通过」了，但一个字节的业务逻辑
都没测到。发现方式是另一条断言 `attempts === 1` 变红。这和 v8.8 那次
「反向验证④第一次是绿的，因为代码根本没改」是同一类教训：
**绿不等于对，要看它是因为什么才绿的。**

## 8. 已知未做

  留待确认。webhook 已覆盖企微 / 钉钉 / 飞书 / Slack / 自建接收端。
- **judge 结果进告警**：`eval_judge` 的 `judge_fail` 目前只写日志，尚未接入通道健康度
  与质量告警。要接的话得先解决「抽样分母」问题——否则「3 次 judge_fail」无法解释
  是「3 次里 3 次失败」还是「300 次里 3 次失败」。
