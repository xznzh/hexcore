# 优化记录 · v8.8 质量告警

> v8.7 做出了「能看见」的页面，但那是**拉取式**的：没人打开管理后台，一个连续三天
> 全量 `empty_answer` 的技能不会惊动任何人。这一轮把它改成**推送式**。

## 1. 缺口的确切形状

v8.7 之后平台有了通道健康度：能按通道、规则、技能聚合，能看每日趋势，能翻最近记录。
这些都在 `GET /api/admin/quality` 背后，需要有人主动打开页面。

缺的不是数据，是**触发条件**。观测数据的价值取决于「谁在什么时候会看到它」，
只做到「能查到」等于把发现问题的责任转给了「碰巧想起来去看一眼的人」，
而那个人通常正是最忙的那个人。

## 2. 设计取舍

### 2.1 为什么不用「失败率」做阈值

做告警最自然的第一反应是失败率：`失败率 > 20% 就告警`。**这个数据不存在。**

`operation_logs` 只在「有问题」时写行，成功执行不留痕（这个口径从对话通道沿用至今，
见 `channel-verify.recordChannelVerify` 的注释）。所以分母是未知的，
任何「率」都是拿绝对数除以一个编出来的分母——一个看起来很专业、实际算不出来的指标。

换成更可靠的信号：**同一个对象在同一个窗口内反复触发同一条规则**。

- 偶发一次：用户输入古怪、模型抖动、上游返回空 —— 都有可能的，不值得半夜叫人;
- 一小时内同一个技能连续三次 `empty_answer` —— 这几乎只能是它坏了。

代价必须说清楚：**本模块无法区分「不忙」和「坏了」**。所以：

- 恢复通知的措辞是「未再达到告警条件」，不是「已修复」；
- 页面上「没有记录」的既有提示继续保留（v8.7 定的口径），告警不改变它。

### 2.2 告警 key 是「通道 · 名称 · 规则」，不是「通道」

如果按通道汇总（「skill 通道 3 次问题」），三个技能各崩一次就会误报——
它们分别都没坏。所以 key 到具体对象，`alertKey(channel, label, rule)`。

对话通道没有标签，key 退化为 `chat/#<规则>`。

key 只用 `#` 连接、**不反向解析**：标签里可能带 `/`（技能名形如「日报 / 周报」），
想把 key 拆回三元组一定会拆错。需要结构化字段的地方单独存。

### 2.3 静默期是必须的，但它制造了一个新问题

检查每 10 分钟一次。没有 cooldown，一个坏掉的技能一天会产生 144 条通知，
然后所有人开始无视通知——**这比不发更糟：它把「通知」这个通道本身弄坏了**。

但 cooldown 带来一个新问题：**「在静默期」和「已修好」在外部看起来一模一样**。
所以：

1. 状态（每项的 `at` / `count`）通过 `GET /api/admin/quality` 的 `alerts` 字段暴露，
   页面上直接写「当前有 N 项处于静默期」并列出 key；
2. `suppressed` 计数被显式返回——「压掉了几条」本身是信息，静默丢弃不是。

这与 v8.7 的 `unparsed` / `truncated` 是同一类设计：**别让「没看到」伪装成「没问题」**。

### 2.4 恢复通知合并成一条，问题通知不合并

十个技能同时恢复时，十条「已解除」会盖掉真正重要的那条问题告警。所以恢复**合并**、
`kind: 'recovery'`、一条通知列出所有 key（超过 20 个折叠）。

问题告警不合并：不同对象、不同规则，合并后就失去了「点开就知道该看谁」的价值。
代价是可能一次涌出多条，用 `maxAlertsPerRun`（默认 5）兜住，按次数从多到少截断。

### 2.5 通知发给管理员，而不是广播

`notifications.userId = null` 是全局广播，所有用户都能看到。绝对不能用于这里——
通知标题里带技能名和定时任务名，成员会看到别人的东西。

所以查 `role = 'admin' AND status = 'active'`，逐个 `createNotification`。
管理员数量是个位数，N 条插入无所谓。

**没有可用管理员时**：日志留 `status: error`，接口返回 `notified: 0`。
不能在「一个人都没通知到」的情况下返回成功——那会让「告警配了但没人知道」这件事
永远查不出来。

### 2.6 状态存在 `settings` 表，不加表

形态是 `key → JSON`，正好是 `settings` 的形状（`register_mode` / `brief_enabled` 已在用）。
为此建 `quality_alert_state` 表需要一次迁移，收益只是「看起来更正规」。

规模上限与过期清理必须自己写：`fired` 最多保留 500 项、超过 30 天的条目丢弃。
否则技能数增长会把这一行撑成一坨没人敢动的 JSON。

### 2.7 判定是纯函数，I/O 在外层

`planChannelAlerts(rows, policy, now, prev)` 不碰数据库、不读当前时间。
告警逻辑的每个分支都是「时间 × 次数」的组合，掺进 I/O 就只能靠等真实时间来验证。

外层 `runQualityCheck` 只做三件事：查窗口内的日志、调纯函数、把结果发出去并落状态。

## 3. 改动清单

| 文件 | 改动 |
|---|---|
| `lib/agent/quality-alert.ts` | 新增。策略读取、纯函数判定（`planChannelAlerts`）、执行（`runQualityCheck`）、节流入口（`maybeRunQualityCheck`） |
| `lib/scheduler.ts` | 每分钟 tick 顺带调 `maybeRunQualityCheck()`，不新起定时器 |
| `app/api/admin/quality/route.ts` | 响应增加 `alerts`（策略 + 状态 + 静默期中的项） |
| `app/api/admin/quality/check/route.ts` | 新增 `POST`，管理员手动触发；`dryRun` 只算不发 |
| `app/admin/AdminClient.tsx` | 「评估」Tab 顶部加告警状态条 + 「试算」按钮 + 试算结果弹窗 |

### 三个实现细节

**1. 状态写入放在发送之后，接受「最多一次」**
`createNotification` 内部吞异常，所以调用方无法区分成功与失败。选择「最多发一次」
而不是「保证发到」：重复的告警会让所有人开始无视通知，比漏一条更严重。
代价是发送失败时本轮静默丢失——为此把计划与结果都写进状态，让「本该发而没发」
至少留下痕迹。

**2. `maybeRunQualityCheck` 先占位再 `await`**
否则同一次 tick 内的重入会跑两遍，并发写同一份状态。节流变量在 `await` 之前赋值。

**3. 多副本：`tryLock` + 复用 `SCHEDULER_ENABLED`**
`SCHEDULER_ENABLED=false` 的副本本就不该做平台级周期工作，复用同一个开关；
再加一把 `quality_alert_lock` 兜住「多个副本同时判断都该跑」的情况。

### 反向验证（四处）

| 动作 | 结果 |
|---|---|
| 撤掉静默期判断 | 「cooldown 内重复命中」「恢复后复发」「读状态接上 cooldown」**3 条变红** |
| 恢复判定改成「窗口里没有出现过」 | 「从 5 次降到 2 次算恢复」**1 条变红** |
| 收件人改成 `userId = null` 广播 | 「给每个管理员各发一条」**1 条变红** |
| 删掉调度 tick 里的 `maybeRunQualityCheck()` | 「每分钟 tick 会顺带跑检查」**1 条变红** |

第四条第一次跑出来是**绿的**——因为 `String.replace` 在 CRLF 文件上没有匹配（静默返回原串），
代码根本没被改掉。按行替换后才是真红。**反向验证本身也要被验证**：
一个什么都没改的「反向验证」看起来和通过一模一样。

## 5. 阈值与开关

全部走环境变量，改阈值不需要发版：

| 变量 | 默认 | 含义 |
|---|---|---|
| `QUALITY_ALERT_ENABLED` | 开 | 关掉 = 完全不检查 |
| `QUALITY_ALERT_WINDOW_MIN` | 60 | 观察窗口（分钟） |
| `QUALITY_ALERT_MIN_COUNT` | 3 | 同一 key 在窗口内多少次才告警 |
| `QUALITY_ALERT_COOLDOWN_MIN` | 360 | 同一 key 告警后静默多久 |
| `QUALITY_ALERT_RECOVERY_MIN` | = 窗口 | 至少多久没达条件才说「已解除」 |
| `QUALITY_ALERT_MAX_PER_RUN` | 5 | 单次最多发几条问题告警 |
| `QUALITY_ALERT_INTERVAL_MIN` | 10 | 检查间隔（分钟） |

数值都被夹在安全区间：`MIN_COUNT=0` 会被当成无效并回退默认——
「0 次就告警」等于每轮都吵。

### 怎么确认它真的会响

进「管理后台 → 评估 → 通道健康度」，点告警条上的**试算**：走 `POST /api/admin/quality/check`
的 `dryRun` 分支，返回「本轮会发什么」，不发通知、不写状态。阈值调完再让它真跑。

## 6. 行为变更

1. **管理员开始收到站内通知**（前提：`fired` 条件成立）。成员不受影响。
2. **状态写入 `settings` 表的一行**（`quality_alert_state`），不涉及 schema 迁移。
3. **调度器的 tick 多了一件活**。`SCHEDULER_ENABLED=false` 的副本完全不参与。

## 7. 仍未闭环

1. **通知只在站内**。没人登录就没人看到。要真正「叫人」，需要外部通道（邮件 / 企业微信
   / webhook），这涉及其它系统的凭据与限流，不适合和这一轮混在一起。
2. **没有「忽略此项」**。一个已知会长期存在的规则（例如某技能故意产出命令）会每 6 小时
   提醒一次。需要按 key 的静音名单，且要有到期时间——否则名单会变成垃圾桶。
3. **没有环比**（v8.7 遗留）。`byDay` 有趋势，但没有「比上周多 3 倍」这类基线判断，
   所以「缓慢恶化」仍然不会被发现。
4. **`runtime-judge`（R4-b）仍只挂 chat**，同一模式的第五次。成本模型不同（每次都是计费调用），
   接线前要先定「哪些通道的失败值得花钱复审」。
5. **异步摘要有界滞后**（v8.3 遗留，仍未动）。需要先量化实际滞后量。
