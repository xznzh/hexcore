> 设计台账：2026-11-01 · V8（重构轨）· 轨道=重构 · 审计材料=`app/api/chat/route.ts`、`lib/agent/{engine,executor,verdict}.ts`、`lib/tools/registry.ts`、`lib/llm.ts`、`lib/ai/{rag,memory}.ts`、`middleware.ts`、`lib/cache.ts`、`lib/quota.ts`、`README.md`(V1–V7.10) · 独立评审=建议后续子智能体复审（本轮未跑，见 §八）

## 3. V8 优化方案（按优先级分组）

### 3.1 风险级（必须先修，按依赖序）

**R1 · 统一工具真相源（收掉 G2）**
- 目标：`chat/route.ts` 的 12+ 内联工具**全部迁到 `registry.ts` 注册**，对话路径统一经 `invokeRegisteredTool()` 走"权限→审批→超时→审计→PII 脱敏"包装；`capability-tools.ts` 与 `mcp-tools.ts` 继续以 registry 形式挂载。
- 落点：`lib/tools/registry.ts` 扩充 `ToolDef`（加 `source`、`idempotency` 选项）；新建 `lib/tools/chat-tools.ts` 存放原内联工具定义；`chat/route.ts` 改为 `listRegisteredTools(ctx)` 拼装。
- 价值：审计/超时/脱敏一处生效，SSRF/熔断/限流对全工具一致。

**R2 · 记忆可信度与失效治理（收掉 G3）**
- 落点：`schema.ts` 的 `memories` 加 `credibility`(low/med/high)、`sourceType`(extracted/confirmed)、`expiresAt`、`evidenceVersion`；`extractMemories` 默认 `credibility=low`，被用户显式确认/在后续对话复现才升 med/high；检索时 low 权重降权；超 `expiresAt` 不召回。
- 价值：防"未验证推测升级为事实"（你 V7 系列已反复踩"模型编造"的坑，记忆层是同类隐患）。

**R3 · 工具副作用幂等（收掉 G4）**
- 落点：`invokeRegisteredTool` 与内联 execute 统一接收 `idempotencyKey`（对话内用 `${conversationId}:${toolCallId}`）；`create_todo`/`run_skill`/写类 connector 先查 `operation_logs` 同 key 已成功则跳过。
- 价值：streamText 重试/网络抖动不再重复建待办、重复跑技能。

**R4 · 运行时 V 层（收掉 G1，最大架构增量）**
- 分两步，零成本先行：
  - **V-a 确定性后校验（必做，零额外 LLM 成本）**：回答落库前跑 `verifyAnswer()`——① 是否含未解析占位符/空话术；② 引用来源是否真在 `sourcesList` 中（防幻觉来源）；③ 是否仍含可被复制执行的破坏性命令（复用 `guardrails.checkOutput`）。不通过则打标 + 记 `eval_runtime` 日志。
  - **V-b 可选独立 LLM-judge（按需）**：对高风险回答（调用了 connector/生成了文件）用**另一档/另一实例**模型做事实性/指令遵循抽查，独立上下文、只看产物与轨迹（`trace`），不看推理过程。受预算开关控制。
- 落点：新建 `lib/agent/runtime-verify.ts`（纯函数，可单测，复用 `evals/judge.ts` 的判定器经验）。

### 3.2 成本浪费级（直接省钱）

**C1 · 模型分档（形态 B，收掉 G6）**
- 先做低风险降级（不动 chat 主推理，维持形态 A 默认）：① 记忆抽取 `extractMemories`；② chat 收尾合成（空文本兜底那次 `generateText`，`chat/route.ts:989`）；③ 个人快照类"我有哪些项目/文件"可用 cheap 档；④ Critic 重试可用 cheap 档。
- 建 `lib/agent/model-assignment.ts` = 任务-模型分派表（步骤×档位×理由），并监控"cheap 处理不了→升级强模型"的升级率（升级率过高=降档失败，回查分派表）。
- 价值：后台/收尾/抽取这类高频步骤从强模型移到 cheap 档，成本看板（O16）会立刻体现。

**C2 · 语义缓存前缀稳定（收掉 G7）**
- `cache.ts` key 改为 `stablePrefix(model, roleLabel, kbScope) + prompt`，把每轮变动的 `personalContext`/`conversationSummary`/`attachment` 移出 key；同时把 system 拆"稳定前缀区（角色/语言/时间/拒答纪律）+ 可变尾部（快照/资料/项目）"，稳定前缀利于供应商 KV 缓存复用。
- 价值：同用户同知识域的重复问题命中率提升 → 直接省 token。

### 3.3 优化级（质量/体感/架构）

- **O1 · E 原地打转检测（G5）**：在 `fullStream` 循环里维护"工具名+参数指纹"滑动窗口，连续 N 次（默认 3）相同则强制打断并追加"请基于已得信息直接回答"。
- **O2 · 上下文预算与快照 memo（G8）**：`personalContext` 以 `userId+period` 做 30s memo；system 各段加字节预算（资料/附件超阈值则截断并提示）。
- **O3 · 统一 hook 框架 + 危险动作分级（G9）**：`registry` 增加 `risk: 'read'|'write'|'destructive'`，`run_skill`/`generate_ppt` 默认 `write` 级可配 human-in-loop。
- **O4 · 评测进运行时（G10）**：对话后 best-effort 跑 `evals/judge.ts` 的轻量判定，命中退化则记 `eval_drift` 告警（不阻断用户）。
- **O5 · `chat/route.ts` 拆分（G12，是其他项的前提）**：拆为 `context-assembler.ts`（组装 system/history/快照）、`chat-tool-defs.ts`（工具定义，迁 R1）、`stream-handler.ts`（流式+落库+verify）。先拆后改，降低回归面。
- **O6 · 工具回执业务成功体系化（G11）**：`callConnector` 抽象 `assertBusinessSuccess(res)` 钩子，各连接器可注册自己的"成功判定"（替代特判 Open-Meteo）。

## 4. 优先级与方案（重构决策卡）

- **改什么（按序）**：R1（统一 T，含 O5 拆分）→ R3（幂等）→ R4（运行时 V）→ R2（记忆治理）→ C1（模型分档）→ C2（缓存稳定）→ O1/O2/O3/O4/O6。
  - 理由：R1/O5 是其他项的地基；R3/R4 是风险；R2 防失控；C1/C2 立刻省钱；O 系列改善体感与可维护性。
- **不改什么（及理由）**：
  - 不改 SSRF 三层 / 熔断 / traceId / guardrails / 离线 evals 套件 / 跨通道额度 / 流式断连中止 / 成本看板——已验证有效，V8 只在其上叠 V 层与分档，不重写。
  - 不引入分布式 agent 派发（维持单机 Next.js）——目标"类似 WorkBuddy 小团队"，分布式是过度设计。
  - chat 主推理保持单强模型（形态 A 默认）——不强行上多 Agent；分档只落在后台/收尾/抽取（形态 B）。
- **迁移顺序（最小可验证步）**：
  1. O5 拆分 `chat/route.ts`（行为不变，仅移动）→ `tsc` + 现有 292 单测绿。
  2. R1 把内联工具迁 registry（经 invokeRegisteredTool）→ 单测覆盖一个新 chat 工具。
  3. R3 幂等键（先 create_todo/run_skill）→ 重试单测。
  4. R4-a 确定性后校验（纯函数+单测，零成本先上）→ R4-b 独立 judge（预算开关，默认关）。
  5. R2 记忆字段迁移（加列 + 向后兼容 ALTER）→ 抽取单测。
  6. C1 分档表 + 升级率埋点 → C2 缓存前缀稳定。
- **回滚点**：每步独立 commit/PR；schema 变更一律 `ADD COLUMN IF NOT EXISTS` + 幂等 ALTER（沿用项目既有约定）；R4-b、C1 降档用 `MODEL_TIERING=off` / `RUNTIME_JUDGE=off` 特性开关，默认关、出问题一键回退；O5 拆分保留旧文件 git 历史，可 `git revert` 单步。

## 5. 风险与回滚

| 改动 | 风险 | 回滚方式 |
|---|---|---|
| O5 拆分 route | 行为漂移 | git revert 单 PR；`tsc` + 全量单测门禁 |
| R1 工具迁 registry | 工具签名/权限错配致对话工具失效 | 特性开关 `CHAT_TOOLS_REGISTRY=on`；关则回退内联；单测覆盖每个迁移工具 |
| R3 幂等 | 误判 key 导致正常重复被吞 | key 仅作用于写类工具；`IDEEMPOTENCY=off` 关闭 |
| R4 运行时 V | V-a 误标好答案为坏（误伤）；R4-b 增成本 | V-a 只记标不拦截；R4-b `RUNTIME_JUDGE=off` |
| R2 记忆治理 | 旧记忆无 credibility 字段，迁移需回填 | ALTER 加可空列，默认 NULL=按现有逻辑；回填脚本可选 |
| C1 模型分档 | 降档致质量下降 | 升级率监控；`MODEL_TIERING=off` 全回退强模型 |
| C2 缓存前缀 | key 改错致缓存穿透/命中错乱 | key 版本前缀 `v2:`；异常清空 `llmcache:*` |

## 6. 经济性三视角（每份设计必答）

- **成本**：C1（形态 B 分档）把抽取/收尾/快照类高频步骤从强模型移到 cheap 档，成本看板（O16）会直接反映下降；C2 提升语义缓存命中省 token；R2/R3 防失控烧钱（重复跑技能/重复建待办）。
- **缓存**：C2 把 system 拆稳定前缀+可变尾部，既提升语义缓存命中，也利于供应商 KV-cache 复用（前缀稳定时命中前缀缓存）；现状 key 含完整 system 是主要失分点。
- **体感**：O1 防"打转"降低首字与总时延；O2 快照 memo + 资料截断降首字；O4 实时感知质量退化；O1/C1 不增加用户侧等待（分档在后台）。

### 10.2 第二轮：C2 语义缓存修复 + O1 防打转（同日追加）

审计时判断 C2 是「命中率偏低」的性能优化；读代码后确认它实际是**两个 bug**，因此优先级上调：

**Bug ① 读写缓存用的不是同一段 system。**
`getCached(resolved.name, system, ...)` 用的是**追加前**的 system，`setCached(resolved.name, sys, ...)` 用的是**追加后**的 `sys`（比 system 多出「注入防御说明」`injectionDefenseNote` 与「资料≠指令」`UNTRUSTED_DATA_NOTE` 两段）。
只要本轮命中了知识库资料、或触发了注入特征，**读写 key 必然不等 → 该条缓存永远不可能命中**，而 `logCache` 却按 miss 记账，命中率看板因此长期偏低且原因不可见。

**Bug ② key 里含分钟级时间与实时用量，缓存实际等同没有。**
system 含 `【当前时间】2026-11-01 周日 11:28`（精确到分钟）与 `Token：已用 x / 额度 y（剩余 z）`（每次回答后变化）。
即使用户在同一分钟之外重复问同一个问题，key 都不同 → TTL 600s 的语义缓存基本不生效。

| 项 | 落点 | 关键实现 |
|---|---|---|
| C2 缓存键稳定化 | 新增 `lib/agent/cache-key.ts`，`lib/cache.ts` 改用它 | ① 命中判定移到 `sys` 定稿之后，读写同源；② `normalizeSystemForCache()` 把**时分**归一为 `<time>`（**保留日期**，跨天必须失效）、把 Token/存储用量行替换为 `<volatile>`；③ **知识库参考资料不做归一化**（它决定答案内容，抹掉会串答案）；④ key 前缀升为 `llmcache:v2:`，旧键自然过期，无需清 Redis |
| C2 缓存准入闸门 | `chat/route.ts` | 显式关联能力（`/能力`）的轮次跳过缓存（否则会跳过必须发生的工具调用）；问实时用量/时间的问题（`isVolatileQuestion`：token/额度/存储/几点…）跳过缓存——用量已被归一化抹掉，命中会返回过时数字 |
| O1 工具防打转 | 新增 `lib/agent/loop-guard.ts`；`chat/route.ts` 用 `toolGuard.wrap(tools)` | 在**工具执行层**硬短路，不改 12 个内联工具：相同 (工具+参数) 成功执行过一次后，再调直接回放上次结果 + 强指令；单工具执行 >4 次一律拦截并要求出正文；**只有成功执行才计数**（失败/超时不算，不阻止换法重试）；触发时落 `tool_loop_guard` 审计 |

> **为什么落在执行层而不是循环控制层**：本项目用 `ai@4.3.19`，没有 v5 的 `prepareStep` / `stopWhen` 钩子，无法在 `maxSteps` 循环中途改 `toolChoice`。包一层 `execute` 是这版 SDK 下唯一能做到"真拦截"的位置，且与既有工具定义零耦合。
> **与 R3 的分工**：R3（`idempotency.ts`）是**跨请求**幂等，防重复副作用与重复扣额度；O1 是**单轮内**防打转，防步数浪费与重复结果注入。

**验证**：`npx tsc --noEmit` exit 0；`npx vitest run tests` = **282 passed / 1 skipped**（新增 `cache-key` 11 条、`loop-guard` 13 条，既有 26 套件无回归）。

**一个自查发现的自身缺陷（已修）**：`normalizeSystemForCache` 初版把整个 `【当前时间】2026-11-01 …` 替换成 `<same-day>`，连日期一起抹掉 —— 单测「跨天必须失效」直接失败。这会让跨天复用昨天的答案（"今天/昨天/本周"的解读依赖日期），已改为只抹时分、保留日期。

### 10.3 第三轮：R1-lite 工具策略层（同日追加）

R1「统一工具真相源」的完整解法是把 13 个内联工具迁进 `registry.ts`，前提是先把 1112 行的 `chat/route.ts` 拆开——大改动、回归面最大，不在本轮做。
但 R1 缺口的**实际痛感**不必等到那天才缓解：这些工具连最基本的执行契约都没有。本轮用零侵入包装先补齐。

| 缺口（改前实况） | 后果 | 本轮做法 |
|---|---|---|
| 工具 `execute` **无任何超时** | `call_connector` 打到挂起的上游会一直等到 stream 的 120s abort，用户干等两分钟；`generate_ppt`/`run_skill` 更是没有任何边界 | `withTimeout()` + 按工具设定上限（连接器 45s、生成文件 90s、工作流 120s、检索 20s、读文件 15s、默认 30s） |
| 工具抛异常**直接炸掉工具链** | `streamText` 整条链路报错，前端只看到「生成中断」，模型拿不到失败原因、无法自我修正 | 异常转为**可读文本喂回模型**（含失败原因 + 「不要原样重试、不要编造结果」），整轮继续 |
| 工具结果**无上限** | MCP/连接器返回的超大 JSON 直接灌进上下文，挤掉对话与资料 | `truncateToolResult()` 保留**头 70% + 尾 30%**（只留头部会丢行尾的下载链接） |
| 工具层**无审计** | 哪个工具慢、哪个总失败，事后查不到 | `audit` 回调落 `tool_invoke`，只记**失败/超时/慢调用(>5s)**，避免高频成功调用灌满 `operation_logs`（完整链路仍在 `messages.trace`） |

**串联顺序（有意为之）**：`withToolPolicy(toolGuard.wrap(tools))` —— 策略层在最外层。这样
① 防打转的短路返回不会被记成一次真实执行；
② loop-guard 内部的异常能被策略层捕获成可读文本而不是炸链路；
③ 只有真跑过的调用才计入 strategy 审计。

**顺带修掉一个看板失真**：`logCache(false)` 原先无条件执行，导致「强制能力轮次」「实时用量类问题」这些**本就不该查缓存**的请求也被记成 miss，分母虚高、命中率被系统性低估。已改为仅在 `cacheEligible` 时记 miss。

**验证**：`npx tsc --noEmit` exit 0；`npx vitest run tests` = **298 passed / 1 skipped**（新增 `tool-policy` 16 条）。

**仍未做**：工具的**权限/审批**统一化（内联工具里只有 guest 与零散的 admin 判断，没有 capability 那套 `requiresApproval` 流程）——这项依赖把工具迁进 registry，属于 R1 主体，需先拆 route。

### 10.5 第五轮：R1 闭合——14 个工具迁入 registry（同日追加）

承接 §10.4，把 14 个内置工具从「自己实现的 execute」改为 `registerTool` 注册 + `invokeRegisteredTool` 调用，接入 registry 的**权限校验 → 审批 → 超时 → PII 脱敏审计**四道处理。这是「工具双轨制」的闭合点：此前只有能力工具走这套，对话工具完全绕过。

**最关键的约束：registry 是全局 Map。**
`registerTool` 写的是模块级 Map，若工具定义闭包请求级变量（`userId`/`conversationId`…），并发请求之间会**串用户**。因此工具定义必须是**模块级常量**，身份一律从 `invoke(args, ctx)` 的 `ctx` 读。改造方式是机械替换：把 `execute: async ({a,b}) => {` 换成
```
invoke: async (args, toolCtx) => {
  const { a, b } = args as {...};
  const { userId, role, conversationId, prompt, convProjectId, allowedKbIds } = toolCtx as ChatToolContext;
```
**函数体一行未改**——这样 470 行代码的行为可保证不变，而 14 个函数的变量名也不必逐个重写。

**撞到一个隐蔽回归（已修）**：`invokeRegisteredTool` 内部 `catch` 后返回 `{ok:false,text}`，**永不抛错**。而上一轮加的防打转（loop-guard）用「是否抛错」判断失败、失败不计数——一旦不抛，失败会被当成成功，模型换个参数重试反而被误短路。修法不是让 registry 抛错（那样审批/权限拒绝的文案会丢），而是：`chat-tools` 在 `!r.ok` 时抛 `ToolInvocationError(r.text)`（自带已可读的文案），策略层识别该类型后**原样返回**，不再套一层「工具执行失败：… 报错：…」。

**职责重划（避免双层重复）**：
| 能力 | 归属 | 原因 |
|---|---|---|
| 超时 | **registry**（`ToolDef.timeoutMs` 取 `TOOL_TIMEOUT_OVERRIDES` 同一份配置） | 两层超时谁先触发不确定，排障说不清 |
| 审计 | **registry**（入参/返回 `redactPii` 后落 `tool_invoke`） | 比 policy 的「只记失败」更完整；双层会导致同一次调用记两条账 |
| 结果截断 | **policy**（`withToolPolicy`，`timeoutFor: () => 0` 关掉超时） | registry 不做截断，超大 JSON 仍需保护上下文 |
| 防打转 | **loop-guard**（在 policy 内层） | registry 没有这个概念 |

**风险等级只标注、策略留白**：`WRITE_TOOLS`（`run_skill`/`generate_ppt`/`create_todo`/`call_connector`/`propose_skill_install`）设 `permission: 'member'`，只读工具设 `'guest'`——入口已拦访客，故**行为不变**。`requiresApproval` 一律保持 `false`：**审批开关是产品决策**，一开则普通成员建一条待办都要管理员批，体验会变，不该由重构顺手决定。

**验证**：脚本对比迁册前后（归一化掉 `execute`↔`invoke` 签名差异）：工具名 14/14、9 个函数体逐字一致，其余 5 处差异与 §10.4 **完全相同**（R3 幂等 ×2、`roleLabel` 重命名、`capabilityCallHint` 参数、`read_file` 格式）——即迁册本身零行为变化。`DEFS` 内无任何 `ctx` 引用（并发安全）。`tsc --noEmit` exit 0；`vitest run tests` = **298 passed / 1 skipped**。

**收益**：新增工具只需在 `DEFS` 加一项 + 决定是否进 `WRITE_TOOLS`，权限/超时/审计/截断/防打转全部自动具备；api/skill/schedule 通道将来可直接复用同一份注册表。

**回滚**：本轮回滚粒度=单文件/单函数级 `git revert`；schema 变更全部 `ADD COLUMN IF NOT EXISTS`，旧库兼容，不阻塞回滚；新增函数均为纯/无副作用模块，删除即回退。

### 10.6 第六轮：C1 模型分档 + R4-b 独立 judge + O2 上下文预算 + O6 业务成功（同日追加）

前五轮把「风险级 + 工具统一」做完，本轮处理剩下的**成本浪费级**与三条**优化级**。四项互不耦合，各自独立可回滚。

#### C1 模型分档（收 G6，形态 B 落地）
此前 `resolveModelWithFallback()` 在每个入口都解析成同一个主模型——记忆抽取、会话摘要、收尾合成、judge 抽查全用最贵的模型跑。

新增 `lib/agent/model-tiers.ts`（纯决策）：
- **白名单**：`DEGRADABLE_TASKS` = summary / memory-extract / synthesize / judge / critic。`chat` **不在表内**——主线质量不参与省钱。
- **选档**：`pickCheapest` 只在「有价格数据」的候选里挑，按 `priceIn*3 + priceOut` 加权（输出更贵）；排除主模型自身（否则是假降档）；同价按 id 排序保证决策稳定。
- **没有价格数据就不猜**：全部为 0 时直接回退主模型，reason 写明 `no-cheap-model`。`local-7b` 这种无价格的自建模型不会被误选。
- **三个覆盖口**：`MODEL_TIERING=off`（全回退）、`MODEL_CHEAP_ID`（全局指定）、`MODEL_TIER_<TASK>`（按任务指定，非法 id 自动忽略）。

落点：`lib/llm.ts: resolveModelForTask(task, primaryId)` 负责查库+解析实例+失败回退，候选清单 60s 缓存并与 `invalidateModelCache()` 联动。接入三处：`memory.ts: extractMemories`、`route.ts` 会话摘要、`route.ts` 收尾合成。

**升级率怎么算**：降档目标被停用/删除时记 `logLlm(tier-escalate:<task>)`，judge 日志里也带 `tier` 与 `reason`——「本可降档但没降」和「降档后回退」都留了痕，不用另建指标表。

#### R4-b 独立 LLM-judge（收 G1 后半）
新增 `lib/agent/runtime-judge.ts`，三条硬约束：
1. **独立上下文**：只喂「问题 + 工具结果摘要 + 最终回答」，**不喂历史、不喂 reasoning**。`digestTrace` 直接过滤掉 `reasoning` 条目并截断到 3000 字符——带着原推理去评审，模型会自我合理化（正是 `engine.ts` critic 的短板）。
2. **不阻断**：结论只写 `eval_runtime`（pass/fail/error 三态），绝不改写用户已看到的回答。
3. **默认关闭**：`RUNTIME_JUDGE=on` 才启用；且只为「动过高风险工具（connector/能力/技能/PPT/读文件）且确实产出回答」的轮次付费。纯检索、闲聊不抽查。

解析用**严格 JSON**：没有明确 `verdict` 就返回 `null`，不把「解析失败」当 `fail`（否则日志里全是假警报）。

#### O2 上下文预算与快照 memo（收 G8）
拆两类数据，别再一起 memo：
- **实时**（每轮查）：token 用量、存储占用——用户下一句就在问「我用了多少」。
- **慢变**（30s memo，`createTtlMemo`）：项目/文件/技能/定时任务，每轮省 5 次往返。

**真实发现（不是代码 bug，但影响 V8 结论）**

1. **C1 分档在当前库里是 no-op**：16 个模型的 `price_in/price_out` 全为 0。`decideAssignment` 按设计返回 `no-cheap-model` 并回退主模型——「省钱」尚未真实发生。要生效需二选一：给模型填真实单价，或 `MODEL_CHEAP_ID=<模型id>` 显式指定便宜档（例如本地 `llama3.2`）。
2. **迁移依赖请求触发**：`ensureInit()` 由 85/87 个路由在请求时调用（chat 路由第 93 行）。旧进程（10-31 启动）不会执行新增的 ALTER，因此「先上新代码再发一次请求」才会建列；本轮已通过调用 `ensureInit()` 完成建列，**无需手工迁移**。但这意味着**新库/新部署的首个请求会承担建表成本**，冷启动时延略高。
3. **写工具的副作用真实存在**：对抗轮次中模型主动调用 `create_todo` 建了一条「联系 DBA 走审批」的待办。这不是 bug（工具按设计工作），但说明「未开启审批的写工具 + 对抗输入」会产生用户没要求的副作用。是否对 `create_todo` 之类开启 `requiresApproval`，仍待产品决策（见 §10.5）。
4. **知识库相关性闸门偏松（既有问题）**：提问「删除 users 表的权限审批」，召回的第一条是《示例接口使用手册》。词面重叠够但语义无关，模型自己也识别出「与此无关」。属 `filterRelevantHits` 的既有阈值问题，非本轮引入。
