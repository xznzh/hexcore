## 0. 我的核心判断

如果只记一句话：

> **Agent 框架的工作量，八成花在「管理不可信输入」上，只有两成花在「编排大模型」上。**

新手会以为框架的核心是「把 LLM 串起来」，于是把精力放在流程编排、节点 DSL、可视化画布上。
做过一轮生产后会发现问题不在那儿——**真正的复杂度来自四个不可信源**：

| 不可信源 | 具体表现 | 本系统对应的防线 |
|---|---|---|
| 模型输出 | 该给 JSON 时给自然语言；说「不能通过」时被判成通过 | critic fail-closed、严格 JSON |
| 工具返回 | 三方 API 返回的文本里埋着「忽略之前的指令」 | `<untrusted_data>` 定界 |
| 用户填的 URL | 服务端代发请求 → 打云元数据、扫内网 | SSRF 三层防护 |
| 检索到的文档 | 文档正文里的指令被当作用户意图执行 | 注入检测 + 定界 |

这四件事没有一件是「编排」问题，但**每一件都能让整个系统失守**。
所以我的设计从这四件事倒推，而不是从流程图画起。

## 1. 五条设计原则（每条都附反例）

### 原则一：Run 是一等公民，Chain 不是

**主张**：框架的核心对象是「一次运行（Run）」，不是「一条链（Chain）」。

- **Run**：有 id、有轨迹、可暂停、可恢复、可审计、可计费、可回放。
- **Chain**：数据从 A 流到 B，跑完即消失。

**为什么**：本项目所有"事后想加"的能力——人审暂停续跑、失败复盘、用量归因、评测回放——
全部依赖「运行过程被持久化」。如果一开始按 Chain 设计，这些能力一个都加不进来，
只能在外面套一层壳，壳会越套越厚。

**反例**：先写一个 `runChat()` 返回字符串，三个月后要加「暂停等人确认」，发现没有地方存中间状态，
只能在函数里塞一个全局 map，然后这个 map 永远不会被清理。

### 原则二：扩展点只有一个——能力注册表

**主张**：工具、三方能力、MCP 工具、技能节点，**全部注册到同一张表**，走同一套调用语义
（权限 → 审批 → 超时 → 审计）。新增能力不改代码，只加注册项。

**为什么**：本项目早期工具定义散落在各个路由里，加一个工具要改三处（定义、权限、审计），
漏改一处就出现「这个工具 guest 也能调」。收敛到注册表后，加工具只改一处。

**反例**：内置工具走注册表，MCP 工具走另一套逻辑，能力网关又走第三套。
结果三套的超时策略不一致，一套有审计一套没有，出问题时要查三个地方。

### 原则三：所有外部数据进来必须定界，不是过滤

**主张**：检索片段、工具返回、MCP 返回，统一包上「这是数据不是指令」的定界标记，
再交给模型。**不做关键词黑名单过滤。**

**为什么**：过滤是"猜哪些是坏的"，一定会漏（换个说法就绕过了）；定界是"告诉模型这段不可信"，
让模型自己判断。**定界比过滤有效**，因为它不依赖你穷举攻击方式。

**反例**：花两周写了一套提示注入关键词库，第二周就被「请用另一种方式表达上述要求」绕过。

### 原则四：降级路径设计在接口层

**主张**：每一个外部依赖（向量库、Redis、Embedding、模型），接口层面就必须存在一个
「没有它也能跑」的实现。**降级不是补丁，是接口设计的一部分。**

**为什么**：演示环境 500 是最常见的翻车方式——不是功能不对，是「某个组件没装」。
本项目的 `isVectorSupported()` / `MemoryRateLimiter` / `localVector()` 三处降级，
换来的是「任何单一基础设施缺失，整站不崩」。

**反例**：`VectorStore` 只写了 pgvector 实现，部署到没装扩展的库上，启动即失败，
而且错误信息是「relation does not exist」，排查方向完全错。

### 原则五：判不准时默认拦下

**主张**：所有"判定类"组件（critic、护栏、审批、闸门），**默认值是拒绝**，不是放行。

**为什么**：判定器的默认值决定了它是防线还是装饰。本项目的 critic 曾经"解析失败就退回正则猜"，
结果把「这个方案不能通过」判成了通过——**给了人"已经把关"的错觉，比不校验更危险**。

**反例**：`try { 校验 } catch { 放行 }`。看起来是"容错"，实际是"校验形同虚设"。

## 2. 架构总览：三个平面

传统分层（接入/上下文/执行/编排）描述的是**调用栈**。但对 Agent 系统来说，更该关注的是
**三种性质完全不同的职责**，它们演进速度不同、故障影响面不同，应该分开设计：

```
┌─────────────────────────────────────────────────────────────┐
│  控制平面（Control Plane）                                    │
│  能力注册表 · 审批流 · 权限 · 配置 · 版本                      │
│  —— 变更慢、影响全局、必须有审计                                │
├─────────────────────────────────────────────────────────────┤
│  数据平面（Data Plane）                                       │
│  一次 Run 的执行：接入 → 上下文 → 执行 → 编排 → 流式出口        │
│  —— 跑得最频繁、是性能热点、必须能降级                          │
├─────────────────────────────────────────────────────────────┤
│  观测平面（Observability Plane）                              │
│  trace · 轨迹 · 用量 · 成本 · 评测 · 告警                      │
│  —— 横向切面、只读、不允许阻塞主流程                            │
└─────────────────────────────────────────────────────────────┘
```

**为什么要这么切**：

- 控制平面的改动（加一个工具、改审批规则）不该影响正在跑的请求 → 所以它有独立缓存 + 失效通知；
- 数据平面是唯一有 SLA 要求的部分 → 所以它的每个外部依赖都必须有降级；
- 观测平面**只能 fire-and-forget** → 任何"等日志写完再返回"的设计都会抬高首字延迟。

**这三个平面之间的唯一通信方式是事件**，不是直接调用。这条约束保证观测平面永远无法阻塞数据平面。

### 数据平面内部的分层

```
         ┌──────────────────────────────────────┐
         │  流式出口（自定义事件协议）              │  ← 唯一对外的通道
         └──────────────────────────────────────┘
                          ▲
         ┌──────────────────────────────────────┐
         │  编排层（Run / Step / 检查点）          │
         └──────────────────────────────────────┘
                          ▲
    ┌──────────┬──────────┼──────────┬──────────┐
    │ 执行层    │ 上下文层  │ 记忆层    │ 接入层    │
    │ 工具调用  │ 检索闸门  │ 两套记忆  │ 模型/降级 │
    └──────────┴──────────┴──────────┴──────────┘
                          ▲
         ┌──────────────────────────────────────┐
         │  护栏（定界 · 注入检测 · PII · 输出体检）│  ← 横向切面
         └──────────────────────────────────────┘
```

## 3. 核心抽象（八个接口，语言无关）

这是整个框架最重要的部分。**接口定对了，语言随便换；接口错了，换语言也救不了。**

### 3.1 `ModelGateway` —— 模型接入

| 项 | 内容 |
|---|---|
| 职责 | 把「模型 id + 消息 + 选项」变成「流式 token 序列 + 用量」 |
| 关键语义 | **必须暴露能力标记**（是否支持 tools / vision / 流式），调用方据此决定要不要塞工具 |
| 关键语义 | 配置来自**存储**（表），不是配置文件；支持运行期失效 + 缓存 |
| 关键语义 | failover：指定的模型不可用时按优先级降级，且**降级要能被观测到** |
| 隐藏职责 | 动态 `maxTokens`：按输入上下文长度计算，防止思考型模型「想完了没额度写正文」 |

**为什么能力标记是必需项而不是锦上添花**：把工具塞给不支持 tools 的模型，
现象是「模型反复调工具却不出正文」——**不报错，只是答不出来**。这类故障最难排查。

### 3.2 `Retriever` —— 检索（不是 VectorStore）

| 项 | 内容 |
|---|---|
| 职责 | 问题 → 候选片段（已过闸门、已排序） |
| 关键语义 | **必须内置相关性闸门**，不能只返回 topK。闸门条件：分数够高 **或** 词面有实质重合 |
| 关键语义 | **按 embedding 模型分组**，不同模型的向量不可混算 |
| 关键语义 | 返回结构里带 `degraded` 标记——降级结果必须让调用方知道 |
| 不做 | 不做"取几条"的决策（那是编排层的事） |

**注意接口命名的区别**：叫 `VectorStore` 就把实现锁死在向量上了（将来加 BM25 混合检索要改接口）。
叫 `Retriever` 才对。

### 3.3 `MemoryStore` —— 两套记忆

| 类型 | 语义 | 生命周期 | 检索方式 |
|---|---|---|---|
| 会话记忆 | 本轮对话的消息序列 | 一次会话 | 按会话 id 直取 |
| 长期记忆 | 跨会话的事实与偏好 | 长期 | 词面预筛 + 向量排序 |

**关键约束**：长期记忆的**写入必须异步**（fire-and-forget 且吞异常），
**读取必须先做词面预筛**（不能全表加载后内存排序）。

**为什么拆成两个接口**：它们的写入频率、检索方式、失败影响面完全不同。
合成一个「Memory」接口的结果是——为了兼容两种语义，两边都做不好。

### 3.4 `ToolRegistry` —— 能力注册表（唯一扩展点）

| 项 | 内容 |
|---|---|
| 注册项 | 名称、给模型看的描述、参数 Schema、权限等级、是否需审批、超时、实现 |
| 调用链 | **权限 → 审批 → 超时 → 审计**（顺序固定，不可调换） |
| 关键语义 | 审批通过后要能「标记已批准」再入队，避免二次进审批 |
| 关键语义 | 审计要记**入参**（不只是返回），且入参做 PII 脱敏 |
| 关键语义 | 超时是**必填项**，不是可选项——没有默认值，强迫调用方想清楚 |

**为什么审批在超时之前**：审批可能等很久（人工确认），不该被工具超时计时器杀掉。
**为什么审计在最后**：审计要记真实耗时和结果，包括超时失败。

### 3.5 `Runner` —— 执行器

| 项 | 内容 |
|---|---|
| 职责 | 一次 Run  = 一串 Step，每步有类型、输入、输出、状态 |
| 节点类型 | `llm`（角色化生成）/ `tool` / `condition` / `loop` / `human`（人工确认） |
| 关键语义 | **每一步都落轨迹**（角色、输入、输出、耗时、工具名） |
| 关键语义 | **检查点**：`human` 节点暂停时持久化「恢复到第几步 + 上一步产出」 |
| 关键语义 | 硬上限 `maxSteps`（防死循环）+ 重试上限 `maxRetries` |
| 不做 | 不做 DAG 可视化编排（见 §7「明确不做的事」） |

**为什么节点类型只有 5 种**：多了就变成通用工作流引擎，少了就表达不了「人工确认」。
5 种是「能覆盖线性业务流程」的最小集。**不要一开始就设计 20 种节点**——
本系统实测，5 种节点 + 2 个占位符（原始输入 / 上一步产出）能表达全部内置技能。

### 3.6 `Judge` —— 判定器

| 项 | 内容 |
|---|---|
| 职责 | 把「一份产出 + 判定标准」变成「通过 / 不通过 + 理由」 |
| 关键约束 | **只接受结构化输出**，不解析自然语言 |
| 关键约束 | 解析失败 → **带着具体错误重试一次** → 仍失败 → **fail-closed** |
| 关键约束 | 原始输出必须写进轨迹（否则无法复盘为什么判错） |

**这是全框架最容易写错的一个组件**，因为它看起来最简单。
判定器的实现质量直接决定「自动校验」这件事是真做了还是装样子。

### 3.7 `EventSink` —— 流式出口

| 项 | 内容 |
|---|---|
| 职责 | 把执行过程中的事件按顺序发出 |
| 事件类型 | `trace` / `think` / `tool_call` / `tool_result` / `delta`（正文）/ `done`（用量） |
| 关键约束 | **必须支持自定义事件类型**，不能只有"文本片段"一种 |
| 关键约束 | 客户端断开后：**停止上游，但继续收尾落库**——两者要分开 |
| 关键约束 | 写入失败要吞掉并记日志，不能抛到业务层 |

**为什么必须支持 `think` 单独通道**：推理型模型的思考内容如果混进正文，会污染最终答案；
如果直接丢弃，用户会觉得"它卡住了 30 秒"。

### 3.8 `Guard` —— 护栏（横向）

| 能力 | 默认行为 |
|---|---|
| 提示注入检测 | **命中不硬拦**，把风险写进系统提示 + 记日志（硬拦误伤率太高） |
| 间接注入定界 | 所有外部数据包定界标记 |
| PII 脱敏 | 写日志前脱敏（日志不该成为新的泄漏源） |
| 输出体检 | 只记录不改写（改了用户拿不到已生成内容） |

**为什么注入检测默认不硬拦**：正常的提问（"忽略大小写"）也会命中规则。
硬拦的代价是用户莫名其妙发不出去消息，而收益有限——真正的防线是定界。

## 4. 六个关键决策（选 A 不选 B 的理由）

### 决策一：自研轻量编排，而不是引工作流引擎

| | 自研 5 节点 | 引 Dify / LangGraph / 通用 BPM |
|---|---|---|
| 学习成本 | 半天 | 数天到数周 |
| 暂停续跑 | 存一个整数下标 | 序列化整个图状态 |
| 可控性 | 完全 | 受框架版本影响 |
| 代价 | 表达不了并行子图 | 过度抽象 |

**判断线**：流程是**线性 + 人审**就用自研；需要**并行分支、子图、任意断点恢复**才上图框架。
本项目全流程都能用线性表达，所以 238 行就够了。**不要因为"框架听起来更专业"就引入。**

### 决策二：向量和业务数据同库（pgvector），而不是独立向量服务

| | pgvector | Chroma / Milvus |
|---|---|---|
| 运维组件 | 0 个新增 | 1 个 |
| 事务一致性 | 同库同事务 | 跨库，最终一致 |
| 扩展性 | 单表 10 万切片以内够用 | 大规模友好 |

**判断线**：切片数 < 10 万、无需读写分离 → pgvector；超过或需独立扩缩容 → 拆。
**但降级路径必须留**：没装扩展时能退回内存余弦，否则演示环境直接 500。

### 决策三：能力注册表包住框架原生工具，而不是直接用注解

框架的 `@Tool` / 装饰器方式把**定义、实现、暴露**绑死，缺权限、缺审批、缺动态注册。
正确做法是**保留原生注解做"函数签名"，但唯一入口走注册表**。

### 决策四：判定器 fail-closed，而不是 fail-open

`try { 校验 } catch { 放行 }` 是最常见也最危险的写法。
**判定器的默认值是它作为防线还是装饰的分水岭。**

### 决策五：观测全部异步，而不是同步等写完

任何「等日志落库再返回」的设计都会直接抬高首字延迟。
本项目 LLM 日志、记忆抽取、用量统计全部 fire-and-forget，代价是"极小概率丢一条日志"，
换来的是「首字延迟不被观测拖累」。

### 决策六：评测用规则判定为主，LLM-as-judge 为辅

| | 规则判定 | LLM-as-judge |
|---|---|---|
| 成本 | 0 次 LLM 调用 | 每条 1 次 |
| 稳定性 | 完全确定，可写单测 | 同输入可能不同结论 |
| 适合 | 有确定答案的问答 | 开放式生成质量 |

**判据**：如果用例的答案能用「必须包含 X 且不得出现 Y」表达，就用规则。
**用 LLM 判「答案对不对」，会得到一个每次跑分都不一样的评测，比没有评测更糟。**

## 5. 数据模型（六张核心表）

只列「必须有」的字段，不列索引细节。

| 表 | 作用 | 关键字段 | 为什么需要 |
|---|---|---|---|
| `runs` | 一次运行 | id、类型、状态、输入、最终产出、用量、trace_id、检查点 | 没它就没有可恢复、可审计的运行 |
| `run_steps` | 轨迹 | run_id、序号、角色、类型、输入、输出、耗时、错误 | 失败复盘和效果归因的唯一依据 |
| `tool_calls` | 工具审计 | 工具名、入参（脱敏）、返回、耗时、是否失败、来源 | 权限追溯 + 成本归因 |
| `approvals` | 审批 | 操作 id、能力、状态、批准人、时间 | 「审批 → 执行」必须可追溯 |
| `chunks` | 切片 | 文档 id、序号、内容、向量、**embedding_model** | 缺 `embedding_model` 就无法做跨模型隔离 |
| `memories` | 长期记忆 | 用户 id、内容、向量、来源会话、创建时间 | 长期记忆必须可检索、可归因 |

**三个容易漏的字段**：

1. `chunks.embedding_model` —— 漏了就永远不知道自己查到的是哪套向量；
2. `runs.trace_id` —— 漏了就没法把「检索 → 工具 → 模型」的日志串起来；
3. `tool_calls.入参` —— 漏了就出问题时无法复现「当时传了什么」。

## 6. 落地路线（四个阶段，每阶段有验收标准）

**关键原则：每个阶段都是"可用的"，不是"半成品"。**
不要按"先把所有模块搭好再联调"的方式做，那会在第 3 周发现自己同时有 8 个未验证的模块。

### P0：单轮对话闭环（1 周）

| 交付 | 验收标准 |
|---|---|
| 模型接入 + 存储配置 | 换模型不改代码 |
| 流式输出（含 think 通道） | 首字 < 3s，思考内容不污染正文 |
| 运行与轨迹落库 | 每次对话能在库里看到完整轨迹 |
| 双中止源 | 关页面后上游停止，且已生成内容落库 |

**这一阶段不碰 RAG、不碰工具。** 先把"一次对话"做扎实，
因为后面所有能力都挂在这条链路上。

### P1：上下文（1–2 周）

| 交付 | 验收标准 |
|---|---|
| 分块器 + 单测 | 中文不断句、小数不断行、无重复块 |
| 检索 + 相关性闸门 | **问「你好」返回 0 条**（这是闸门的唯一有效验收） |
| 跨模型隔离 | 换 embedding 模型后老数据不被混算 |
| 长期记忆（异步抽取 + 预筛） | 记忆抽取不抬高首字延迟 |

**闸门的验收标准就一条：问无关问题返回空。** 做不到这条，RAG 就是装饰。

### P2：执行与编排（2 周）

| 交付 | 验收标准 |
|---|---|
| 能力注册表（四段式） | 加工具只改一处；guest 调用受限工具被拒 |
| 5 节点编排 + 检查点 | 人工确认后能从断点续跑 |
| Judge fail-closed | 「不能通过」判为 fail（要有这条回归用例） |
| 护栏定界 | 工具/MCP 返回都被定界 |

### P3：生产化（2–3 周）

| 交付 | 验收标准 |
|---|---|
| 降级三件套 | 停掉 Redis / 不装 pgvector，整站不 500 |
| SSRF 三层 + 密钥加密 | 填内网地址被拒；库里看不到明文密钥 |
| trace 全链路 | 一个 id 串起一次对话的全部日志 |
| 评测 + 质量门禁 | 改动破坏能力时能被自动发现 |

**顺序不能颠倒的原因**：P1 的闸门决定 RAG 有没有用；P2 的注册表是 P3 所有安全策略的挂载点；
P3 的评测需要 P0–P2 的轨迹数据才能跑。

## 7. 明确不做的事（架构师的一半价值在这里）

| 不做 | 理由 | 什么情况下才做 |
|---|---|---|
| 通用工作流引擎（DAG 画布） | 目标用户不是开发者，画布对他们等于空白 | 产品转向「给实施人员配置流程」时 |
| 多租户强隔离 | 单团队场景，隔离成本远大于收益 | 对外 SaaS 化时（要重做数据模型） |
| 自研推理加速 / 模型微调 | 与业务价值无关 | 有明确的效果瓶颈且 API 方案已验证到顶 |
| Prompt 版本管理平台 | 用 Git 管提示词够用 | 提示词数量 > 50 且需 A/B |
| 可视化调试器 | 轨迹表 + trace_id 已够定位 | 非技术用户需要自助排障时 |

**这张表的作用**：它提前回答了「为什么不做 X」。
没有这张表，每个新需求都会被讨论一次「要不要做个画布」，团队每季度消耗一次。

## 8. 三个我会重点盯的风险

| 风险 | 表现 | 我的应对 |
|---|---|---|
| **首字延迟劣化** | 功能越加越多，7s → 15s，用户觉得"变笨了" | 所有非必要调用一律异步；首字延迟进监控，超过阈值告警 |
| **降级路径腐化** | 降级代码长期不跑，某天真的降级时发现是坏的 | 降级路径要能被测试（用一个开关强制走降级） |
| **评测与实际脱节** | 分数很高，用户还是不满意 | 评测用例必须来自真实失败；不看绝对分，看趋势 |

**第一条最容易被忽视**：它是「能力增加」的必然副作用，且没有报错、没有告警，
只有用户感觉到"怎么越来越慢"。**首字延迟必须当成一级指标**，和其他功能一起排期。

## 9. 这套设计的三份实现对照

| 设计要素 | TypeScript（本项目） | Java | Python |
|---|---|---|---|
| `ModelGateway` | `lib/llm.ts` | Spring AI `ChatModel` + 自研 failover | LiteLLM 或裸 SDK |
| `Retriever` | `lib/ai/rag.ts` | 自研（`VectorStore` 之上） | 自研或 LlamaIndex |
| `MemoryStore` | `lib/ai/memory.ts` | 自研（`ChatMemory` 不够） | 自研 |
| `ToolRegistry` | `lib/tools/registry.ts` | 自研包 `@Tool` | 自研 + Pydantic |
| `Runner` | `lib/agent/engine.ts` | 自研状态机 | LangGraph 或自研 |
| `Judge` | `lib/agent/verdict.ts` | 自研 | 自研 |
| `EventSink` | `app/api/chat/route.ts` | WebFlux `Flux` | `StreamingResponse` |
| `Guard` | `lib/guardrails.ts` | 自研 | 自研 |

**注意最后三行**：`Judge`、`Guard`、`Retriever` 在三个生态里**都是自研**。
这不是巧合——它们正好是「业务语义」最重、框架最难覆盖的三块。
**如果你只打算自己写三个组件，就写这三个。**
