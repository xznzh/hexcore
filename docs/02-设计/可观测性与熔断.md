# 可观测性与熔断

> 面向运维与二次开发：这一版新增了什么信号、怎么抓、告警怎么配，
> 以及三件**刻意不做**的事和它们的理由。
>
> 相关代码：`lib/metrics.ts`、`app/api/metrics/route.ts`、`lib/resilience.ts`、
> `lib/agent/channel-governance.ts`。

## 1. 在这之前能看见什么

| 信号 | 位置 | 局限 |
|---|---|---|
| 存活/就绪 | `GET /api/health`、`/api/health?full=1` | 只知道「通/不通」 |
| 每次模型调用 | `operation_logs`（`action='llm_call'`） | 事后逐条翻，无法聚合出趋势 |
| 慢请求 | `PERF_LOG=1` 或超 2.5s 时的一行日志 | 只有慢的，没有分布 |

缺的是**时间序列**。后果很具体：K8s HPA 只能按 CPU 扩容，而本系统的瓶颈是
模型首字延迟与 token 吞吐——CPU 打满之前用户已经在骂了。

## 2. 指标清单

所有指标前缀 `hexcore_`，进程内累加，由 Prometheus 抓取时按实例聚合。

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `api_requests_total` | counter | `route` `method` `status` | 所有走 `withApi` 的路由 + 手写的 `/api/chat` |
| `api_duration_ms` | histogram | `route` | 到响应开始为止的耗时（流式接口即 TTFB） |
| `chat_turns_total` | counter | `result=ok\|error\|cancelled` | 轮次结果；取消单独一档，不算失败 |
| `chat_ttft_ms` | histogram | — | 首字耗时：用户感知的「快不快」几乎只取决于它 |
| `chat_turn_duration_ms` | histogram | — | 整轮耗时（含工具调用与落库） |
| `llm_calls_total` | counter | `label` `ok` | 按用途拆（`chat-stream` / `summary` / `judge` …） |
| `llm_duration_ms` | histogram | `label` | 单次模型调用耗时 |
| `llm_tokens_total` | counter | `kind=total\|prompt\|completion` | token 用量，输入输出分开 |
| `guardrail_hits_total` | counter | `source` `rule` `mode` | 护栏命中；`mode=observe` 与 `block` 必须分开看 |
| `circuit_failures` | gauge | `breaker` | 连续失败数（**本进程视图**） |
| `circuit_open` | gauge | `breaker` | 是否熔断（1/0，本进程视图） |
| `circuit_opened_total` | counter | `breaker` | 熔断打开次数 |
| `queue_jobs` | gauge | `state` | 文档索引队列各状态任务数；Redis 不可用时**不输出**（0 ≠ 不知道） |
| `process_*` | gauge | — | RSS / 堆 / uptime |
| `build_info` | gauge | `version` | 恒为 1，版本在标签里 |

**标签基数**：`route` 已把 id 段归一化成 `:id`（`lib/api/route-label.ts`），
每条指标再有 200 条序列的硬上限，超出收敛到 `overflow="true"`。
这两道是为了防基数爆炸——它不会报错，只会让抓取慢慢变慢、内存慢慢涨。

## 3. 抓取

```yaml
# prometheus.yml
scrape_configs:
  - job_name: hexcore
    metrics_path: /api/metrics
    scrape_interval: 30s
    static_configs:
      - targets: ['hexcore:3000']
```

K8s 里用注解发现（每个 Pod 各抓一次，counter 天然可累加）：

```yaml
metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/path: "/api/metrics"
    prometheus.io/port: "3000"
```

**鉴权**：与 `/api/health` 一样不使用登录态（抓取端没有 Cookie）。
默认开放；要收紧就设 `METRICS_TOKEN`，之后必须带 `Authorization: Bearer <token>`，
未带或带错都返回 401。

```bash
# 开箱验证
curl -s localhost:3000/api/metrics | head -20
```

## 4. 建议的告警

| 告警 | 表达式（示意） | 为什么是它 |
|---|---|---|
| 接口错误率 | `sum(rate(hexcore_api_requests_total{status=~"5.."}[5m])) / sum(rate(hexcore_api_requests_total[5m])) > 0.05` | 用户已经在失败，不需要等日志 |
| 首字变慢 | `histogram_quantile(0.95, sum(rate(hexcore_chat_ttft_ms_bucket[10m])) by (le)) > 8000` | 感知层的劣化，先于「报错」出现 |
| 熔断打开 | `max by (breaker) (hexcore_circuit_open) == 1` | 外部依赖挂了，重试只会放大 |
| 队列积压 | `max(hexcore_queue_jobs{state="waiting"}) > 200` | 索引跟不上上传，检索会「新文档搜不到」 |

阈值都是起点，不是结论——按自己机器的 p95 调。

## 5. 熔断器：为什么从进程内改成集群共享

旧实现把失败计数挂在 `globalThis` 的 `Map` 上。单副本没问题；多副本时它是
**放量器而不是保护器**：同一个死上游，A 副本已熔断、B 副本刚启动一无所知，
照样把请求打出去，副本数 N 就放大 N 倍。而它保护的恰恰是外部依赖。

对照很刺眼：同一个 `lib/redis.ts` 里，限流器早就是集群正确的
（Redis `INCR` 优先、抖动时回落内存计数）。相邻两套容错策略一个集群级、
一个进程级，纯粹是历史顺序造成的。

现在的分层：

1. **Redis 是权威源**：`breaker:<key>` 哈希存 `failures` / `openedAt`，
   TTL 是冷却期的两倍（太短会在刚熔断时过期→退回放量；太长会让已恢复的下游被无谓拦截）。
2. **进程内 Map 是镜像**：Redis 未配置或抖动时兜底，也用于本进程的 `/metrics` 视图。
3. **读取时合并取失败数更大者**：Redis 被清空时不至于让刚熔断的副本立刻恢复放量。

刻意保留的语义：

- **4xx 不计失败**：说明下游活着，只是我们请求不对。
- **半开期允许多个并发试探**（不做单飞锁）：最坏是多打几次请求，实现简单且不误伤。
- **API 是 async 的**：共享状态必须读 Redis。一次外部 HTTP 调用前多一次 Redis 往返
  （同机房 1~2ms），相对于它要保护的那次调用的超时窗口可以忽略。

## 6. 出口治理：为什么收成一个门面

非对话通道的产出要外发，治理是三段：

1. `finalizeChannel` —— 出口护栏（命中即截断，带通道上下文）
2. `auditChannelAnswer` —— 运行时 V 层（声称用了某工具，轨迹里到底有没有）
3. `judgeChannelAnswer` —— 语义抽查（采样 + 预算，默认关闭）

顺序不能换：护栏必须在审计之前（审计的对象是**真正会外发**的文本），
judge 在护栏之后（不为已被截掉的片段再花一次采样额度）。

原来 `skills/run` 与 `scheduler` 各自装了一遍。两条都记得装，所以测试是绿的——
但这是靠「记得」。第三条通道（webhook 触发、workflow 运行）漏装时**不会报错**：
只是静默地没有审计、没有护栏，而评测只跑已有通道，抓不到这种退化。

现在：

- `governChannelAnswer(text, ctx)` 是唯一实现（`lib/agent/channel-governance.ts`）；
- `runSkillGoverned(...)` 把「运行 + 治理」合成一步，是技能通道的默认入口；
- `tests/source-guards.test.ts` 会在源码层拦住绕过门面的写法：
  裸 `runSkill(` 需在白名单内登记，三个治理函数只能出现在门面与定义处。

新增一条通道时只需三步：调 `governChannelAnswer`、传全 `question` 与 `trajectory`、
把 `blocked` 显式告知用户（拦截不能是隐形的）。

## 7. 刻意不做的三件事

写下来不是省略，是决定。

### 7.1 多租户

36 张表里没有一张带 `org_id` / `tenant_id`，隔离粒度是 user。做成 B2B SaaS 等于
每条查询加谓词 + 上 RLS + 全部索引重做，是重写级工作量。
本项目的定位是**自托管、单团队、私有部署**——不需要多租户，这不是欠债，是产品边界。

### 7.2 OpenAPI 契约

90+ 路由没有机器可读契约。前端是自家的，类型靠 TS 端到端，是自洽的。
只有当要开放第三方集成时才痛；现在做是给不存在的客户写文档。

### 7.3 沙箱不是安全边界

`lib/tools.ts` 的 `runSandbox` 用 worker 线程 + 内存上限 + 超时，
worker 不可用时降级到 `node:vm` 并如实打日志。

必须说准确：**`worker_threads` 与 `node:vm` 都不是安全边界**。它们只防「跑飞」
（死循环、吃内存），不防「恶意」——`node:vm` 有公开的逃逸手法，
worker 与主进程共享同一个 Node 运行时。

在当前形态下这是合理的：单租户、自托管、跑的是管理员自己写的技能代码。
但它是个**有条件的合理**。一旦允许普通成员提交技能、或做技能市场，
这个前提就塌了，那时必须换独立容器（gVisor / Firecracker / 受限的 `docker run`）。
所以这条写在这里，而不是等出事再解释。
