## 0. 一句话结论

**功能层与防御层已达生产水准，欠账集中在「通道不对称」和「经济性」两块：前者是同一套防护只装了三条通道里的一条，后者是省钱的开关装好了没人合闸。**

比经济性更该先修的是 **R2/R3/R4**：技能与定时任务这两条通道，入口不做不可信定界、出口没有护栏、LLM 调用连超时都没有。而它们恰恰是无人值守、直接对外推送的通道——用户不在现场看着，也没法在推送前拦下来。

## 2. 缺口清单

> 定级：**风险** = 特定条件下故障（安全/一致性/失控）；**成本浪费** = 功能正确但资源错配；**优化** = 可用但有提升空间。

| **R7** | **额度闸门只装在四条链路的一半** | `quota.ts:19-21` 注释写明「技能运行、定时任务也能复用同一套预算约束，避免绕过对话通道烧穿额度」。修复前 `checkQuota` 仅出现于 `skills/run`、`scheduler`；`docs/generate` 与 `ppt/generate` **只有 `checkRateLimit(20, 60)`，无任何额度判断** | 被 `block` 的用户在对话框里被拒，却能从「生成文档」「生成 PPT」继续烧 —— 这两条恰是单次几千 token 的重消耗链路。**额度机制在最贵的地方失效**，且失效方式与对话通道完全相反（那边严、这边空）。`brief` 刻意不加（300 token 上限 + 已有频率限制），属取舍而非遗漏 |

> **R6 / R7 与 R1–R5 不同型**：那五项是「某个机制只存在于一条通道」，这两项是「**某个机制在多数入口都装了，只漏了一部分**」。单读任一文件都自洽 —— `kb-access.ts` 的注释是真的（它确实被两个入口调用了）、`quota.ts` 的注释也是真的（它确实被技能与调度复用了）。只有把同类入口横向摆在一起比对才会暴露。**这也是 §7 那 12 项检查表查不出来的形态**，见 §7 末的说明。

## 3. 经济性三视角（必答）

### 成本

| 项 | 现状 | 判断 |
|---|---|---|
| 档位预算分配 | 只有总量 60k | 未按档位分配，必答 Q2 未满足 |
| 单位任务成本核算 | `logLlm` 落 token + `user_id`，成本看板按「日×模型×用途」聚合 | **采集闭环，口径未闭环**：不区分输入/输出 token；摘要/合成/judge 的 token 不在任何预算内 → 看板能看到「花了多少」，看不到「本可以不花多少」 |
| 最该省的三处 | ① 摘要每轮重算（W3）② 缓存命中仍付 embedding + 精排（W2）③ 前缀缓存未命中（W1，金额待证） | 全是「机制在、开关没合」型浪费，不是能力缺失 |
| 用大炮打蚊子 | judge/critic 已在降档白名单，但因 W4 按价选档失效，实际全用主模型（含思考型）跑结构化判定 | 判定只需输出一个 JSON，是最典型的错配 |

### 缓存

| 层 | 现状 | 判断 |
|---|---|---|
| 供应商前缀缓存 | 未利用（W1） | 修法不是加机制，是**调顺序**：稳定留头部、易变沉尾部 |

### 4.2 不改什么（及理由）

| 保留项 | 理由 |
|---|---|
| **chat 的 `output-guard` 流式机** | 它是**有状态**的（`pushDelta`/`flushGuard`，`output-guard.ts:342-450`），价值在「违规片段不出网」。抽成事后纯函数会让 chat 退化成事后截断，丢掉 `:686-687` 的设计目的。**只给另两条通道补事后检查，不动 chat** |
| `loop-guard` 的「只成功才计数」 | 语义正确：失败不应阻止换参数重试 |
| `idempotency` 的 DB + 内存双层 | 已覆盖并发共享 promise / 跨进程账本 / 失败释放 / 不可序列化不落库四种边界 |
| `engine.ts` 保持纯函数 | 预算与护栏靠注入，是正确的可测性边界。不要为 R1/R2 把 IO 塞进 engine |
| `call_connector` 的 GET 放行 / 写操作才幂等 | 注释已论证：GET 去重会把旧价格当现价返回 |
| 单 Agent 主循环，不上多 Agent | 未命中三条硬墙；替代清单未试满。折叠决策卡不触发 |
| `evals/` 离线评测体系 | 行业水准之上，本次不动 |
| 语义缓存的键设计 | V8 已修过读写不一致的真 bug，键结构正确 |

```
P0  R4（超时 + 租约锁）        ← 独立，最高优先

    R7（额度闸门补两条链路）    ← 独立，两处各约 8 行
```

## 5. 风险与回滚

| 改动 | 风险 | 回滚 |
|---|---|---|
| R2 出口护栏 | 技能/调度产出的形态与 chat 不同（webhook 文本 / artifact），套 chat 的替换话术会产出「解释性合规话术」出现在不该出现的场合 | 先只接「命中即截断」，不接替换话术；且这两条通道 `guardCtx` 为空，语境规则本就不生效 |
| R3 入口定界 | 技能 prompt 里 `{{prev}}` 被定界后，模型可能不再像以前那样直接沿用上一步结果 | 定界只加标记不改内容；观察一轮步骤通过率 |
| W3 异步摘要 | **本轮被挤出的消息，本轮既不在 history、也不在（上一轮的）摘要里 —— 对这一轮是「上下文消失」，不是「滞后一轮」** | 同步兜底开关保留；且只在新增 ≥6 条时触发，消失窗口有界 |
| W1 分段 | 若把时间精确度降到日，会破坏「现在几点」 | 时间移入 tail 保留分钟精度，不降精度 |
| W2 向量缓存 | 模型或维度变更后旧向量失效 | key 含 `ref + dim` |
| W4 升档 | 升级重试 = 双倍成本；判据过严会每轮升级 | 只允许 1 次 + 只在 critic 明确 fail 时触发；升级率 >20% 自动关 |
| X1 gateway | 10 处逐点迁移，迁错会导致某链路拿不到模型 | 每处配路由级冒烟；未迁移点保持原样 |
| R6 范围 fail-closed | **这是唯一一个「修完反而会少给内容」的改动**：漏传范围的调用会从「全库」变成「查不到」，用户看到的是「知识库无相关片段」，看起来像功能坏了 | 逐处确认 `retrieve(` 全部调用点；`undefined` 只保留给 `observability` 评测与巡检，并在调用处写注释 |
| R7 额度闸门 | `warn` / `downgrade` 策略下 `exceeded=false`，行为完全不变；只有 `block` 用户会在生成入口首次遇到 429 | 两条路由各自 revert，互不影响 |

**12 项之外的一条（R6 / R7 暴露的检查表盲区）**：这 12 项每一项问的都是「**某个机制存在吗、设计对不对**」，没有一项问「**它是不是装在了全部入口上**」。于是出现这样一类缺口：机制存在、单测通过、注释里还写着「统一口径 / 所有入口」，但实际覆盖不全 —— 而 12 项里没有任何一项会因为「`kb-access` 只被 2 个入口调用」而亮红灯。

补一条可操作的检查动作（不是加第 13 项指标，而是加一个动作）：**凡是注释里出现「统一」「唯一」「所有入口」「避免绕过」的模块，把它的调用点全部 grep 出来，与「应该调用它的入口清单」做差集**。本轮据此抓到 R6（`kb-access` 差 3 处）与 R7（`quota` 差 2 处）；同类自查过的 `projects.ts`、`api/handler.ts` 未发现缺口，但这是抽样，不等于不存在第三个。
